## 经验与返工原因

### 先确认用途，再决定删留

初次 HUD 审查受“美食”旧名称影响，把该入口视为可能多余。负责人指出后，沿 UI、配表、升星、存档和战斗赋值链确认，它已承担局外兵种养成，应保留。

以后审查旧模块必须查真实数据与收益消费者。原“主角单位更新赋值美食属性”的 `ADD_ATTR` 目标实际是 `playerHeroList` 中的主角，改名为“刷新主角兵种养成附加属性”后仍保留这一行为。进入战斗时，小兵另由“创建英雄队伍单位 → 根据升星属性给队伍小兵赋值”处理。名称相似不能把两条属性链混为一条，后续属性回归需分别观察。

### 分批改名，让每次试玩能定位影响

本次按玩家文案、编辑器可读名称、运行时契约和存档核对逐步推进，每批获得试玩反馈后继续。文件／函数名同步索引，事件同步注册／监听／内部重发，预制件同步真实子路径，全局数组同步声明／初始化／读写。单改一处会造成编辑器能显示而运行时失联的风险。

修改使用指定节点或精确字符串映射，保护原 ID 和未知字段，解析后核对预期差异。编辑器保存可能改变 JSON 排版或键顺序，本次最终 14 个文件与候选的字节不同但解析内容一致，不能仅因哈希变化就整份恢复旧候选。当前发布快照取自实际工程。

工程启用了主地图触发器／物编和 UI 共享，仍有其他地图的同 TID 配表副本。此次只同步字段和池键，各图原有行、投放与权重保持，不能直接拿主图整表覆盖其他地图。

### 抽取报错暴露的是候选缺口

23:38 的日志有 9 条 Error、93 条 Warning，其中两次十抽在 `CREATE_ITEM_EX` 和材料存档写入节点报错。静态检查发现权重／保底会选到品质 3–5，而当时合法子项材料全为品质 2。缺少底层异常正文，故将空池列为与配置一致的定位结论，未把报错时间直接归因于函数改名。

按负责人选择“先补齐品质 3–5 的材料配置”，复用原有条目与物品，不新增材料 ID，不重建养成记录。品质 2／3／4／5 的合法候选数分别为 **5／5／3／2**，13 档权重的所有非零品质均有候选。保留原抽取消耗、权重和保底阈值。

普通档与所有保底档须一起检查。配置补齐也不能替代失败处理，**当前尚未实现空池扣费保护／失败回滚**，以后删材料或改品质仍可能重新制造缺口。

### 存档兼容键是已有进度的读写约定

界面显示“练兵材料”，旧存档里仍用 `食物材料` 保存余额。游戏继续通过同一字段读取和保存，才能接上已有进度。存档契约保留如下。

| 保留项 | 当前用途 |
| --- | --- |
| 槽 8 的 `食物材料` | 货币余额字段，原货币存档链及相关查询继续读写 |
| 槽 17 的 `playerFoodRecord` | 养成存档声明名称 |
| `configPlayerFoodRecord` | 槽 17 的初始表引用，保留既有行 ID、材料数量、星级与状态 |
| 槽号、类型、加密设置 | 沿用原存档契约，未重建或改写玩家档案 |
| 物品标签 `美食升星材料` | 仍被奖励物品判断使用，属于有效运行时标签 |
| 部分旧局部变量名 | 保留原局部作用域内实现，本次未做无差别全文替换 |

本次只在内存中核对本机旧档，确认槽 8 有旧货币字段、槽 17 有 20 条含非零培养进度的记录，未导出账户存档。发布时 26 个相关存档文件哈希均保持。归档复查时 25 个静态文件仍保持，`archive_storage.json` 随后试玩发生变化，不能用它与发布前哈希不同判断迁移破坏存档，也不能由此证明每个保存场景都已验证。

旧键如需继续改名，应单独设计有版本标记、可重复执行的旧值迁移，并验证有进度旧档、重登和重复迁移。本次不再推进此项。
