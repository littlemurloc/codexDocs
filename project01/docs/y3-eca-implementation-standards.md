# Y3 编辑器 ECA 实装规范

更新：2026-11-06。适用于本项目英雄、军略卡牌、技能与 Buff，以及公共流程、关卡入口、局内装备和 UI 调用的新增、批量生成、重构和排错。依据各阵营军略、英雄技能、性能优化、HUD及装备首轮实装经验整理。具体玩法仍以项目负责人最新口径和 [项目上下文](project-context.md) 为准。

本文规定实装方法和证据要求，不授权扩大任务范围。原有模块、其他阵营、卡池和特效是否改动，按当次任务确定。本文建立后续标准，不代表历史交付已经满足全部条款。

配套使用：[ECA 交付验收清单](../tests/y3-eca-delivery-checklist.md)。

## 01 原生格式与事件参数必须逐项核对

- 动手前确认当前项目、地图、对象 ID 和实际调用链，读取本图同类 ECA；不得沿用上次会话的路径或资源关系。
- 模板必须匹配触发语义。获得、等级变化、失去、施法、伤害及延迟回调分别检查可用参数，不能跨事件套用同名对象。
- 表达式的参数类型、变量作用域、引用形式、枚举和可选参数，按原生实例核对，不凭 JSON 字段名称猜测。未知字段保留；不能把参数丢失、变量变常量或引用变空视为无害格式变化。
- 区分地图等资源引用与单位、技能等运行时实例；每个 API 都要核对允许的操作数类型，不能因名称通用或 JSON 可保存就认定适用于所有对象。新用法应核对官方定义及本图原生实例，未核实的类型组合不得当作已支持。地图 `MAP` 不在 `TYPE_IS_EXIST` 的允许类型中，不能用该动作检查地图资源是否为空；空值判断按对应类型的原生规则实现。
- 可选参数逐项核对位置、类型和启用状态。生成、测试与回读都必须保留已启用参数，不得只计算固定参数，或把禁用参数当作已启用执行。本次 `STR_JOIN` 提示拼接遗漏启用参数是测试模型缺陷，不能通过删减正确 ECA 来迁就模型。
- 表资源常量与运行时表表达式必须区分：`TABLE/VARIABLE`、`GET_TABLE_KV`、函数返回表等表达式直接作为表参数传入，不能再包成 `arg_type=100011, sub_type=1, args_list=[表达式对象]`。后者会被编辑器误读为表资源标识而标红。表资源常量只接受实际资源标识；离线解释器不得递归执行这个常量里的表达式来“容错”。循环长度、逐行读取、参数映射等公共辅助函数均须覆盖这项检查。
- 该边界同样适用于动态字符串键。拼接后的 KV 键直接传入字符串表达式，不再包成 `STRING/sub_type=1/args_list=[表达式对象]`；公共读写辅助函数须区分普通字符串与表达式，离线模型拒绝常量内嵌表达式。群雄按路线拼接阶段／完成状态键的案例不能依赖递归容错。
- ID 必须精确保留。生成器应使用不会丢失大整数精度的读写方式；函数、事件和元素 ID 检查冲突，复制资源同步检查残留引用。
- 主动施法事件的目标、施法方向与 Buff 伤害事件、被动定时器的可用参数分别核对。不能在 Buff 伤害事件中凭 `DAMAGE_ABILITY` 取得主动施法 runtime 目标，也不能为被动弹道无条件启用 `GET_ABILITY_RELEASE_DIRECTION`；所需数据应在有可靠上下文时保存。主动弹道已有的合法方向参数不随被动修复一并禁用。

吴国案例：`ABILITY_LEVEL_CHANGED` 不能沿用获得事件的直接 `ABILITY_OWNER`；本图使用 `GET_ABILITY_OWNER(CUR_ABILITY)`。这是已核实的事件用法，不推广为所有生命周期都应重查当前技能。

蜀国案例：03、15、18 函数的“无效的表”来自 8 处表表达式编码错误，并非缺少预设表。排查此类标红时，先检查资源登记、变量声明、作用域和参数编码，再决定是否确需新增表；不能用补一张预设表掩盖错误引用。

UI资源常量同样不能用空字符串伪造空引用。本图HUD使用已声明、未赋值的原生UI局部变量表示尚未选到详情；不能改为`UI_COMP/sub_type=1/args_list=[""]`，也不猜测未经核对的NONE_UI接口。模型应拒绝非法空资源标识，不能自动当作None。

镜像入口案例：函数10把地图资源用于实例存在判断，编辑器保存和原模型的34项检查未发现错误。改用地图类型空引用比较并纠正模型后，负责人确认按钮恢复正常；这不代表镜像整场战斗的其他边界都已验收。证据见[入口回归修复记录](../deliverables/玩家镜像挑战按钮入口回归修复-2026-10-19.md)。

## 02 每类数据明确唯一来源

| 数据 | 默认维护位置 | 约束 |
| --- | --- | --- |
| 设计配置、报价、合成路线 | 已有配表或明确的静态配置 | 不另建一份易失同步的名单 |
| 当前持有、有效技能实例、所属玩家 | 现有运行时记录 | 核对记录有效性、归属和更新时序 |
| 每张卡的数值与分类 | 对应物编 KV | 公共代码按规则读取，避免再抄一份数值 |
| 跨卡共用属性语义 | 集中的映射配置或初始化函数 | 新属性明确对应属性类型及计算方式 |
| 计算结果、版本和刷新标记 | 有明确来源与生命周期的缓存 | 标明何时失效、重算和清理 |

预设表和动态表按数据性质选用。稳定的设计配置适合预设表；实时持有状态不应靠手动维护第二份预设表。动态创建不能消除属性语义和新玩法本身的配置工作。

已有属性的新卡应能沿用公共汇总逻辑；全新机制、合成条件或档位变化，仍需修改其对应逻辑，不能宣称“新增任何卡都自动完成”。

旧资源名、旧子归类、设计名和实际路线含义不一致时，明确映射并使用已确认的身份／路线字段，不凭显示名推断机制。配置成员与后继关系继续读原表，数值读物编，避免再复制成员清单。设计中的新术语若确认对应现有资源，沿用已有结算链并记录口径；群雄“帝王碎片”本次对应声望，不另建货币。外部表提取还须核对实际行数、对象数和字段数；工作簿声明范围异常时检查真实数据，不能将截断读取视为空设计。

收集门槛等可调整规则由有类型的公共变量集中维护，所有资格判断调用同一入口；修改时全量搜索旧调用实参及写死值，不能只改变量声明。候选结果从已有配置按分类与当前持有状态筛选；未持有集合为空时跳过授予，不用重复发牌兜底。魏国本次八虎骑门槛为 8，这一数值不推广到其他阵营。

暂不匹配设计的旧资源按当次授权单独登记。只获准加“待替换”备注时，不顺带补 KV 或 ECA、重命名 ID、改报价或剔除其收集资格。显示名称不是分类主键；明确其是否仍占原卡池与资格名额，不能因备注或缺少新身份 KV 就擅自排除。魏国旧曹修本次仍占八虎骑名额，其他旧卡是否如此须另查实际配置。

复用旧函数、属性或配表前，必须核对收益来源、接受单位、判定对象、结算时机、叠加方式和公式入口。名称相同不能作为语义相同的依据。蜀国案例：旧公共结算中的阵营／站位增伤按受击目标判断，不能直接用于本次输出单位的阵营／站位收益；兵种并集也不能被两个独立分支重复累计。

数组查值与数组索引分别处理。`DICT_HAS_VALUE` 查值，不查键；本图判断技能拥有者是否为参战玩家，应查询 `playersDetail` 玩家数组，不能拿玩家对象在 `玩家队伍` 单位组数组中查值。取队伍时再用现有玩家索引函数换算。PVE/PVP、玩家/NPC分别核对己方与敌方返回顺序，以及调用方实际读取的 `call_rt_index`。

公共函数返回的现有队伍组按借用引用处理，不以 `CLEAR_GROUP` 清理本技能缓存；否则可能清空共享队伍。刷新引用与创建独立可修改的组是两件事，不凭局部变量名称认定它是副本。

### 高频计算优先复用本次调用的数据

- 伤害来源、目标及用于本次判断的单位类型等稳定读取，可在具备原有有效性前置条件后保存到有原生类型的局部变量；先确认本次调用中不会发生语义变化，再替换重复读取。保留原比较、计算、取整、分支及副作用顺序。
- 缓存限于已确认的有效范围。下一次伤害／函数调用重新赋值，不跨攻击复用目标、类型或瞬时属性。属性可能在本次伤害、事件重入或状态变化中改变时，不因“只读API”就把所有属性读取提前；缓存对象引用也不能替代后续有效性检查。
- 对照实际原ECA验证输出与副作用，区分静态表达式出现次数、一次代表路径实际读取次数及原生耗时。减少读取只证明工作量发生变化，不能单凭次数认定帧耗时按比例下降。

本次伤害上下文与兵种克制均只做调用内复用；具体范围见[第01步](../deliverables/自动战斗性能优化-第01步伤害上下文复用-2026-10-30.md)和[第02批](../deliverables/自动战斗性能优化-第02批克制判断与追踪开关-2026-10-30.md)，不据此授权缓存所有战斗属性。

## 03 按职责组织，保持编辑器内可读

- 单卡入口说明何时触发、传什么对象；跨卡重复计算抽为具名公共函数；Buff 负责与自身生命周期相关的监听和清理。
- 单卡简单效果可直接编写，不为减少行数把每个小动作拆成函数。抽取函数应具有明确职责，避免读者在多个文件间反复跳转。
- 通用统计使用遍历、筛选和映射，不在每个事件中复制整套卡牌 ID 判断。确有不同语义的固定分支应保留清晰条件，不为了通用化隐藏规则。
- 按读取与校验、筛选、计算、提交、清理排序；变量说明业务含义，注释解释特殊口径和时序。长逻辑用具名折叠段分组。
- 对象存在检查与依赖它的读取有先后关系时，使用有保障的执行顺序。未确认条件短路语义，不为减少嵌套而合并空对象检查。

## 04 以真实写表时序安排刷新

- 梳理添加技能、获得事件、写入实例记录、合成消耗、移除技能和失去事件的实际顺序。
- 获得事件早于持卡记录写入时，先初始化、确保控制器存在并标记待刷新；写表完成后再主动通知汇总。
- 失去事件可能先于引擎删除实例，不能立即把旧记录当成最终状态；需要后续校验覆盖该时序。
- 区分“记录尚未建立”和“已确认没有持卡”。不能在首次写入前提前清掉控制器。
- 汇总涉及多个字段时，明确一次提交与失败处理方式，避免读者取得半套新旧缓存。
- 当前持卡快照先校验实例有效性、载体归属及分类，再按规则去重。汇总和套牌资格检查使用本次校验后的快照；重入改变持卡状态后重新读取，不能把半更新状态当成合成完成。
- 报价屏蔽、路线解锁、组件技能移除、套牌结果持有及持续收益撤销分别核对。原流程只屏蔽报价时，不擅自认定组件已被删除，也不凭“吞噬”文案替它执行删除。
- 自动授予终极结果时，先完整检查已确认的资格，再在调用原合成／授予流程前设置重入保护，完成后按约定解除；重复回调不得再次授予。蜀国本次资格为六套牌结果齐备且 base 达到 5 级，该数值条件不推广为其他阵营默认规则。

### 动态单位采用增量登记

动态加入单位须核对开局初始化之外的增量登记链：单位创建、技能授予、队伍加入、原生UI绑定、技能池登记、最终刷新分别确认。开局能用不代表局中招募、重建或镜像入口自动补齐记录。本次动态英雄在授予和归队后、最终HUD刷新前追加“卡牌技能池-表”，按所属单位与实际技能实例去重；保留已有抽取／锁定状态，初始锁定读取当前自动施法状态，空技能筛选沿用已核对的开局口径。不能为补登记重跑会清空卡池、重置状态或补发道具的全量初始化。其他创建／移除路径须另按实际需求审查，不以本次一条路径通过代替全部生命周期。

### 多种获得路径必须拆开持有、完成与展示状态

- “持有结果牌”“自然合成已完成”“组件已折叠”“结果是否可报价”分别建模，不能共用一个解锁／持有布尔值替代。随机赠送可以先取得结果牌；之后组件集齐时，跳过重复发结果牌，仍须按原流程完成组件折叠、后续解锁及一次性的合成结算。
- 自然合成完成标记按玩家与结果类型隔离。结果牌自己的属性依有效持有判断；路线吞噬收益依自然完成状态判断，除非设计明确赠送也算完成。重获结果或重复通知不得重复完成收益／合成抽奖。
- 界面折叠不等于删除技能，隐藏的组件是否继续生效按原实装口径处理。诊断同时核对有效实例、展示标记及实际 UI 消费链；`界面展示=False` 只能证明记录字段，不能单凭该字段断定界面根因或技能失效。
- 至少覆盖“先随机得结果，再集齐组件”与“未持有结果，正常集齐组件”两条路径，并检查再次通知及失去／重获。不能只测正常合成。

魏国案例：旧分支以结果“是否解锁=False”限制整段合成收尾，随机提前获得 UR 后会留下界面小卡。修复仅解除这项耦合，保留原折叠与持续收益语义；负责人已确认折叠恢复。该问题及状态拆分见[魏国实装记录](../deliverables/魏国军略卡牌实装与验收记录-2026-10-26.md)。

### 分支路线、待授予结局与报价资格分别维护

| 状态 | 说明及约束 |
| --- | --- |
| 路线已解锁阶段 | 表示目前可收集哪一组，不代表已完成；初始化只执行一次，重建控制器不重置 |
| 某组自然完成 | 以有效实例集齐并成功取得结果为依据；只结算一次声望、折叠及完成收益 |
| 待授予终局类型与来源 | 在规定资格成立时固定；授予失败保留原候选，阻止继续开阶，重试不重新选择结局 |
| 本局已领取与最终类型 | 按玩家记录实际领取；不因失卡、换波或控制器重建重新开放资格 |

- 明确锁定发生在选线、解锁、集齐还是发卡时，不用一个“已选路线”开关代替。若规则允许另一线收完当前组，锁定只禁止开启下一组和再次授予终局，仍执行当前组正常收尾。
- 特殊结局依赖另一线进度时，明确比较“已解锁”还是“已完成”，在终局资格成立的边界读取并保存结果。群雄本次为首条末组完成时检查两线是否均已解锁末组，不要求另一线也完成；普通／特殊UR是替换关系，不同时发放。这是本次玩法口径，不推广为所有分支系统的规则。
- 合成资格、普通报价资格与自动奖励资格各有入口和筛选。不能因合成检查排除了终局牌，就认为解锁函数也会排除；下一组只开放对应阵营、组别、身份的普通组件，终局资源从普通解锁路径排除。共用解锁函数不满足本模块语义时，在模块入口收紧，不擅自改变其他阵营共用行为。
- 配表纠正与脚本约束互相补充。群雄将UR移至“帝业与天命”，同时在函数19排除三张固定终局类型；固定结局ID用于规则边界，不据此复制全量卡牌名单。后续增加结局类型时，须同步审查终局候选、普通解锁排除及回归用例。
- 下一组配置为空、为“无”或没有合格组件时，不推进阶段，也不打印已经解锁。不得只改阶段号制造路线已开放的假象。

## 05 生命周期与异步对象必须完整处理

按功能实际涉及范围检查：获得、等级变化、合成、失去、重新获得、补兵、队长变化、换波、死亡及来源销毁。不适用的路径可标注原因，不为凑阶段增加无用动作。

定时器、事件监听、收益来源、缓存与持续表现均应有对应清理。延迟或运动器回调、伤害结算之后、移除 Buff 之前，重新检查后续实际使用的单位、技能或 Buff 实例；外层早先有效，不代表此刻仍有效。不得把空 Buff 实例当作必有对象继续读层数或删除。

本图英雄的特殊死亡由项目流程维护“已死亡”标签，引擎仍可能报告存活；治疗、选敌、自动施法、循环和状态收益都须排除这种状态。小兵仍以原生死亡判定为主，不能要求其具有英雄专属的自定义状态。对象存在、原生存活、项目战斗资格分别校验，先存在再读属性、位置或 KV。

伤害结算可以同步引发死亡、波次切换、技能失去及循环重建。后续附加状态、删除标记或返还资源前重新校验其实际依赖，不能把伤害前的检查当作整段回调的通行证。校验旧循环时比较原实例与当前实例，不仅比较 Buff 类型；无关联核心本来就不是该技能前置条件时，不得为防错把基础技能一并禁用。

英雄主动技能的自动施法动作判断统一复用函数库 `new/功能执行/英雄主动技能-检查自动施法动作状态`：每次先把允许标记设为 False；检查施法单位，未施法时只把标记设为 True，正在施法时缓存当前记录技能，仅在实例存在后读取其释放类型，沿用原模板枚举条件；末尾统一设置一次返回值。不要重新复制“未施法 OR 读取当前记录技能类型”的旧写法。各技能原有冷却、阶段、自动施法标记和目标条件继续由单卡入口判断。

每次重新搜索先清空旧目标，写入与读取保持同一作用域；自动目标与手动施法事件覆盖分清。单位目标技能核对命令中启用的目标单位参数，不以只填写目标点替代。目标筛选以设计为准，允许普通敌人时不能只按某个英雄标签搜索；保持实际施法范围，缺少范围内目标不能靠擅自扩大射程解决。

ECA 的 `400342` 返回值动作与 `RETURN` 退出执行动作分开核对，不把设置返回值自动解释为结束函数。布尔判断优先采用“初始化结果 → 分支更新结果 → 末尾统一返回一次”的结构。离线解释器不能用 Python 异常把返回值赋值模拟成提前退出；必须覆盖前面为 True、后续又设置 False 的覆盖缺陷。2026-10-18 自动施法回归由这一错误假设引入，见交付记录后续修正段。

伤害结算中的“单位 → 所属英雄 → 阵位”等链式读取，先校验来源和 KV，再缓存引用、检查对象有效性，最后读属性。每次伤害重新清零本次缓存；缺少阵位时只跳过对应条件收益，不中断其余伤害结算。不依赖 AND／OR 短路来保护后续解引用。2026-10-18 修复仅保留既有阵位分组及“自身或所属英雄”口径，不借修复改成其他排位规则。

跨事件保存必要引用或快照时，明确作用域、所属玩家、是否随等级更新及失效方式。旧实例失效后重新获得同类卡，应使用新实例，不复用旧句柄。

不能把所有 `local` 机械改成 `actor`。技能实例级状态可按实际回调需要保存到 actor，但它仍可能被后续搜索覆盖；并发弹道应各自保存目标、必要来源、波次和原循环身份，命中时读取本颗弹道的数据，不再读取外层遍历对象或不断变化的 actor 目标。目标失效时跳过效果仍须清理弹道；未能命中的弹道保留有依据的超时销毁。韩当、张郃、祝融的本轮实现与实测见复盘，不把其 4/8 秒时限推广为所有弹道默认值。

循环 UI 清理独立于旧 Buff 是否存在和英雄能否重建。按各自 KV/句柄清理旧能量格、数据表及面板，再检查旧循环实例并移除，最后仅对具备战斗资格的单位重建；添加新 Buff 成功后才读取名称、上限等信息。失败重试时格子增多，要分别检查显示残留与真实数值，不能直接判为层数上限增长。

## 06 收益必须可重复刷新和准确撤销

编写效果前先明确归属、结算时机、去重标识及失效条件。以下是本次蜀国口径的实例，其他效果依已确认设计填写，不能只照抄数值。

| 效果类型 | 状态范围与必要检查 |
| --- | --- |
| 持续属性 | 依当前有效持卡计算；失去后撤销本系统贡献，重复刷新不累加 |
| 首次领取奖励 | 玩家＋卡牌类型；明确失去重获是否再次领取，本次金币不再次领取 |
| 每波奖励或随机效果 | 玩家＋真实波次；同波重复通知只结算／抽取一次，并检查等级等上限 |
| 本单位击杀收益 | 绑定实际击杀单位；队长、小兵及所属玩家分别核对，回复不突破上限 |
| 本局单位永久成长 | 区别于持卡期间贡献；明确失卡、换波、死亡重建与跨局规则，本次成长不转移给替代士兵、不写跨局存档 |

“本局至多领取一次”应由玩家级领取记录约束，不能只检查当前是否持有卡牌，或把记录仅存在可销毁的控制 Buff 上。并发／同步重入保护与本局领取记录职责分开：授予前阻断嵌套入口，确认实际授予成功后提交领取状态；按约定处理失败和解锁。验收包含重复请求、丢失后再请求、控制器重建，以及玩家隔离。魏国EX、群雄终局UR本次均至多一张，不将此上限推广到其他奖励。

- 同一配置重复刷新，最终贡献应相同；来源数量与有效实例去重规则明确。
- 默认只设置、替换和撤销本系统自己的属性贡献，不覆盖其他来源的贡献。
- 明确基础值、百分比与总属性加成的差异；引擎属性和自定义属性分别核对存储及实际公式。
- 生命上限变化明确采用何种生命处理口径。若要求保持生命比例，增加与撤销时都检查，避免刷新产生额外治疗。
- 条件交集、套牌继承、UR／EX 互斥和上限逐条写清，并在相应分支验证。已经写入公共伤害属性的收益，不再额外监听伤害重复乘算。
- 普通终局与特殊终局的基础属性、单卡被动、共同终极和历史套牌收益分别列明，不能因名称“特殊”就只给它共同收益，或让替换终局重复获得两套终局加成。群雄三张UR本次均有单卡群雄+30%与共同群雄+50%／骑兵+40%，按既有贡献通道相加；具体数值与叠加口径不推广到其他卡牌。
- 百分比单位写在读取、存储和写入边界。本图已核实采用百分点的内置属性写入路径按 `10=10%` 换算；技能 KV 的小数比例和名称手写带 `%` 的自定义属性不能据此全局乘 100，不按数值大小猜单位。分别检查基础层与可见点数换算，以及等级分支是否重复累加或反向下降。
- 存档星级超过已配置档位时，先定位表边界，不直接归因于整数溢出。本次获批方案为不改存档、按当前最高配置档临时计算并明确提示；配置补齐后应能读取新档位。七名早期英雄“保留一级、后续系数不下降”是本次授权口径，不代替未来英雄的设计曲线。
- 区分真实技能消费与 Buff 到期、重复覆盖、死亡、换波移除；高星消费联动不能只看层数下降。重复施加是否刷新持续时间，须同时核对叠加模式和覆盖时间选项；张辽震慑的模式/枚举是本图实例，不能推广到所有 Buff。

## 07 事件驱动与周期兜底分工明确

主流程在完成状态变更后主动通知。周期校验负责覆盖删除时序、漏通知或新单位，不代替所有主流程通知。

共用规则初始化后复用；用变化标记或版本避免未变化时重复汇总和逐单位应用。循环间隔按实际成本确定，不把吴国当前间隔当成所有系统的固定标准。不得在各单位高频回调中反复创建相同表、重复注册监听或全量扫描不相关资源。

每波效果使用现有战斗阶段入口与真实波次编号去重，不把事件通知次数当作波次数。去重状态应覆盖同波重入；明确初始化或途中获得卡牌是否追补当波收益。蜀国本次不追补，并保留原获得／合成声望与每波声望并存，概率升级独立结算且不突破现有上限；这些是本次口径，不由技术复用自动推广。

按“累计战斗时间”结算的效果只在确认的战斗阶段推进，备战暂停；周期调度间隔与累计步长必须同源维护，不能改了循环频率却漏改计时。明确失卡、换波、重新获得后的进度保留／清零规则，并验证阈值前后与阶段切换。魏国贾诩本次为累计 120 秒战斗时间、失卡清零；尚无完整长时间实战证据，不因计时规则已写入而视为验收通过。

### 显示刷新与玩法结算分别安排

- 高频层数事件先区分玩法动作和显示动作。伤害、真实层数、属性与满层联动保持原结算时序；经确认允许只显示最终状态的格子／数字可合并刷新。每次事件都有独立含义的飘字、粒子或提示，不随面板数字一起机械合并。
- 待刷新标记按单位与实际Buff／技能实例隔离，同一来源最多保留一个待处理刷新。延迟回调读取最新显示状态，明确重入、失效和计时器清理；不能让每次层数事件各创建一个延迟全量刷新，也不能用新的高频全图轮询抵消合并收益。
- 保存上次成功显示的必要状态，只更新实际变化部分。缓存失效条件至少覆盖本功能涉及的首次创建、界面重建、实例替换、颜色／显示规则和拥有者变化；控件尚未建立或刷新未完成时，不标记整份显示已成功。
- 界面重建完成后主动使显示缓存失效并请求首次刷新。延迟期间先检查对象，再检查来源仍是单位的当前循环实例，最后读取层数、表和控件；旧实例尚存在也不能覆盖新实例界面。异步变量捕获采用本图已核对的原生写法，仍须实测多单位和重建交错。
- 保留原玩家／NPC接收范围和点数换算，不借优化修订玩法。本次“下一帧刷新、可见点数=层数－1”为能量面板实现，不推广为所有UI的固定延迟或层数规则。

当前实现、失效用例和验证边界见[第03批能量显示优化](../deliverables/自动战斗性能优化-第03批能量显示与旧日志收口-2026-10-30.md)。

### HUD选择、绑定与阶段显隐

- 展示选择、原生单位选择、镜头动作是三个职责。头像请求先校验本方有效队伍与当前控件映射；只有请求被接受后，才执行已授权的清旧选择、选新单位和一次性聚焦。定时刷新或动态绑定不自动拉镜头；无效缓存不清掉原选择。
- 保留原生技能、装备、血条等控件绑定及UID；切换时选择对应详情并控制显隐，不为每次点击销毁重建。已隐藏详情不等于未占用槽位，动态分配读取真实队伍记录。多人、显示容量与实际上阵上限分别处理，不能因UI有十槽就改玩法上限。
- Y3 栏位常量中，物品栏（装备生效栏）为 `1`，背包栏为 `0`。装备发放、栏位读取、HUD 绑定及物品 ECA 必须指向同一物品栏；不能为修正图标显示而把装备改放背包栏。参见 [Y3 栏位常量定义](https://github.com/y3-editor/y3-lualib/blob/main/doc/API/Const.md)。
- 技能／装备提示和自动施法从事件所属控件反查当前英雄，避免使用注册时拼进事件名的旧单位身份；换英雄或重绑后关闭旧提示。镜像模式本就不发默认道具时，空装备格不直接判为绑定损坏。
- 阶段显隐的入口和周期刷新必须服从同一已有阶段状态。只在战斗入口隐藏、却允许刷新循环重新显示，会造成反复打开；返回备战时明确恢复，并保留有效选择。新增英雄触发的强制刷新也须服从阶段限制。

### 奖励事件必须携带来源，隔离额外授予的重入

- 将选卡、自然合成、随机赠送、终极授予作为不同来源传入共用授予链。获得事件本身不能证明玩家进行了选卡或自然合成。魏国本次随机赠卡只刷新持卡收益，不再次触发选卡／合成抽奖。
- 若既有授予函数的签名不便改动，可使用按玩家隔离的上下文；进入前保存上级来源，绑定目标类型或本次授予标识，调用完成后恢复上级上下文。同步嵌套授予不得误继承来源；异步回调需要独立保存上下文，不能依赖已恢复的外层变量。
- 单卡概率按已确认的事件分别结算，来源实例先校验并按类型去重；同次操作涉及多个来源或同时触发选卡与合成时，分别记录，不擅自合并为一次或重复遍历抽取。日志沿用原本的唯一掷骰结果，不为打印再调用随机函数。
- 多个符合条件的独立试次会增加总体中奖机会；只有在独立且试次均实际发生等前提成立时，才用 `1−∏(1−p)` 计算至少一次成功概率。体感高频不直接证明概率写错；统计需要来源、事件和全部有效试次分母，只有中奖日志不能验收长期命中率。

魏国实测：选择曹植时，已持有的曹彰、温恢分别赠送一张八虎骑；刚选中的卡与提供奖励的卡是两个对象，日志必须能区分。来源隔离及 EX 的实际记录见[试玩日志核对](../deliverables/魏国军略试玩日志核对-2026-10-27.md)。

### 函数移动、复制与重复ID清理

- 同一地图的独立函数／触发器按各自身份命名空间扫描：函数FID和根级触发器ID均须检查唯一性；跨地图复用和内嵌触发器／元素ID的作用域另行核对，不把全项目所有数字ID混在一起重编号。
- 移动既有函数时保留身份与调用，核对新旧文件及两端目录登记，不能只在新目录增加文件而留下旧副本。真正创建独立函数副本时另分配身份，并审查自递归、子触发器和外部调用的绑定；只改显示名称不能消除身份冲突。
- 清理重复定义前比较完整JSON、签名、动作及未知元数据；字节差异可能仅来自保存格式。同ID但实现不同必须先确认权威版本，不能按路径、时间或文件大小直接删除，也不能为消除警告盲改其中一个ID。
- 完整相同的重复定义，保留明确的目录位置及原ID，精确移除多余文件与对应`index.txt`项；核对外部及递归调用仍能解析，范围外登记与保留定义保持。备份、定向删除后重新全量扫描，并实际重开检查启动提示。

本次两组相同函数删除2份旧副本并清理1份索引，见[启动重复函数ID排查](../deliverables/地图启动重复函数ID警告排查-2026-10-30.md)；源文件扫描无重复与实际启动警告消失分别验收。

### UI事件声明、监听注册与派发分开核对

- 对齐UI具体命中控件的事件声明、监听事件名、根初始化入口及配置子触发器注册，不能因子触发器定义存在就认为监听已启动。本图已核对的配置子触发器由根动作中的整数ID节点注册，配套`enabled=false`、`is_conf=true`及所属根ID；四项动作引用不是该注册方式。此结论限于已核对的原生结构，不机械改写全部闭包。
- 输入由实际可点击按钮承接，图片、头像装饰及选中框不额外吞输入；处理器读取实际事件控件，不能在事件移到按钮后仍按旧图片父级路径取序号。保留静态唯一事件名，换波／刷新不重复注册同名监听。
- 排查按根入口是否执行、子监听是否建立、点击事件是否进入、处理对象是否正确、可见行为是否发生逐段留证。“初始化：注册监听”日志只证明打印执行，不证明注册成功。结构工具通过、页面无红字、日志无Error都不能替代原生点击验证。

### 局内装备按配置、实例与展示三层核对

- 报价投放、价格、权重及穿戴限制读唯一配置表；物编维护固定属性与单件触发效果；运行时玩家库存记录购买后未穿戴的数量及必要的剩余次数。公共函数负责抽取、交易、转移和刷新，不按每件物品复制整条购买/显示流程。
- 物编类型 ID、语言键、表行、函数/触发器 ID 和 UI UID 分别校验。报价卡传动态物编 ID 时不得把运行时参数误读为写死旧道具；发现悬空引用须列出实际节点和缺失 ID。
- 穿戴物品的添加、读取、物编 ECA 与 HUD 绑定一致使用物品栏 `1`；背包栏 `0` 不作为装备生效栏。双格限制按目标英雄检查。购买先校验资格及余额，记录购买前库存，写入后按同一装备 ID 和剩余次数回读数量，确认精确增加一件才扣费，再刷新行囊。入库校验失败时走单独提示。
- 库存表、动态行创建及控件显示分别核对。出现扣费但列表为空时，先查库存写入与回读，再追踪元件实例创建和绑定；已有库存但动态行创建失败时，修复显示路径，避免再次发放同一件装备。
- 重复报价卡和行囊列表优先使用容器/元件与动态遍历。改父子层级须保留旧控件 UID 与事件、换算局部坐标，并验证点击命中和实际画面；不能只看 JSON 树或静态坐标。
- 预制件的字体、对齐和溢出行为从同工程可用的原生文本控件核对，禁止把常见 UI 枚举值直接套进 Y3。以非空库存触发首个动态实例，检查长文本、描边和满行边界。装备行旧版的 `alignment=(0, 8)` 可通过 JSON 解析，但运行时创建文本控件时抛出 `KeyError: 0`；本图已有原生左／中／右对齐示例 `(1, 8)`、`(2, 8)`、`(4, 8)`。
- 函数标红按 `valid`、声明、变量、资源/物编、目录登记和编辑器回写依次排查；`valid:false` 是需要定位的状态，不是可无条件翻成 `true` 的修复法。ECA 结构校验不覆盖全部原生资源引用。

### 装备扩量与单件效果的维护规则

- 一件新装备至少核对物编类型、中文名称/描述映射、`局内装备池配置表` 行、实际效果、穿戴限制、成功触发日志及编辑器目录。物编 ID、语言键、触发器 ID、自定义事件 ID 不能互相代用；新增 Buff 还要核对物编、内嵌 ECA 和目录登记。
- `最低难度` 是入池门槛，`报价权重` 才控制同一合格池内的相对抽取机会。当前 40 件按门槛分为 28/8/4，权重均为 100；这不是已完成的稀有度概率分层。调整权重须另作设计、模拟和实测，不把门槛数字当权重。
- 固定属性优先放物编附加属性；伤害、治疗、站位、小兵和消耗效果放各自道具内嵌 ECA，公共函数只做通用流转。使用本图已可运行的事件/动作节点作模板；变量类型、事件参数作用域、物品栏类型、Buff 来源与叠层规则都要逐项核对。不要以庞大的物品 ID 枚举替代读表和动态遍历。
- 战斗开始/结束判定使用现有 `游戏战斗阶段切换` 自定义事件及战斗场次序号，不用高频轮询推断阶段。一次/场、一次/目标等状态按实际语义选择物品实例、英雄或目标作用域；同编号波次重打仍是新场次。同名双持默认允许，但增益是否加法叠加必须在实战核对，不能由 `layer_max` 数字单独宣称。
- ECA 缺少可靠事件参数时，桥接只负责取得引擎事实并发送窄自定义事件，效果、库存与日志仍在道具 ECA。`龙胆铭` 的 Lua 桥接只读取引擎闪避结果并发送英雄参数；桥接脚本、`main.lua` 入口、`customevent.json` 声明和道具 ECA 四处须同时核对。原生 API 名称须由项目或官方源码验证，不能猜测。
- 成功触发日志使用稳定前缀 `[装备日志/v1]`，标明装备、效果和英雄；穿戴日志不等于效果成功。计数须结合发生事件、英雄和场次，属性类同次打印两条可能是物理/魔法两个动作，不直接判为双重生效。高频伤害日志要留意量级和性能，后续可加调试开关，但不能在未验收前删除唯一证据。
- 行囊操作日志由所有英雄共用的穿戴／交换和卸下入口输出。记录操作、目标英雄、槽位、装备名称及 ID，替换补充回库装备。需要依赖旧物品实体的字段应在移除前读取。效果日志按物品自身条件触发，核对行为时按操作或效果、英雄和时段筛选。
- 批量候选先校验 `valid`、触发器/元素 ID 唯一性、闭包、物编/Buff/自定义事件引用，再保存关闭编辑器、备份目标、定向安装和哈希回读。静态通过不等于 ECA 可打开；编辑器加载与逐件打开、集中试玩和延迟刷盘后的日志核对仍是独立关卡。旧错误须按 `trigger_id/element_id` 与历史会话对照归因。

## 09 先备份和核对范围，再写回

- 保存可用的编辑器工作状态，在可写工作区生成候选；备份实际将改的文件，记录变更前后哈希或语义差异。
- 发布前核对目标文件仍符合预期；发生并发编辑时重新比较，不能用旧候选覆盖用户新内容。
- 保留已确认的对象 ID 和无关逻辑；检查关键公共函数的改动只包含本次接入内容。回滚按清单逐项核对，不覆盖整个地图。
- 使用导入、保存或重载后回读实际结果。直接修改已打开地图时，明确磁盘与编辑器内存的先后关系，防止旧内存再次保存覆盖新文件。
- MCP 的 UI 热更和导出只能确认画板、预制件等 UI 内容的加载情况；涉及 ECA 时还须让编辑器重载对应内容或重新打开工程，再用新对局验证。外部写入后遇到旧会话或未保存的用户修改，先确认差异和保留方式，再决定保存或重开。
- 修复必须同步维护中的生成器或模板，避免下次重复生成同一错误。历史备份保持原样；过期工具标明适用版本，不为验证重跑旧迁移器。
- 正式工程发生过启动故障后，本轮采用保存并正常关闭客户端/编辑器、备份当前地图和 `header.project`、核对原哈希后定向发布的流程。保留范围外变化，不强制结束用户进程。官方恢复工具自身的启动权限报错与最初地图打不开须分别归因。
- 编辑器回写的可选参数、目录排列等变化逐项判断是否改变语义；保留未知及有效元数据，不以旧候选整体覆盖。保留元数据时也要重新扫描本次明确应撤除的诊断节点，避免把临时日志一并带回。
- 局部修复保留原函数FID、触发器ID、签名和范围外元数据，只替换必要动作、声明与说明；已发布工程不得重跑初始全量迁移器。发布校验同时绑定实际测试候选哈希、当前目标原哈希和用户已修改配置的哈希；用户已修好的配表不能被历史备份或候选覆盖。
- 临时探针、强制概率／自动发卡与有意保留的调查日志分别登记前缀、所属资源、节点及开关。发布前拒绝本次应撤除的探针残留；按准确登记删除，不按宽泛“含日志动作”清理。退役的测试生成器禁止再次发布，维护中的生成器与最终修复同步，历史备份不重写。
- 经负责人确认，可将边界清晰、可分别回退的小改动合并为一次备份、发布和代表试玩，避免为每个局部变量反复重启。仍需列出每项独立变更与回退范围、原哈希及候选检查；共用函数的代表验证要求继续按第10节执行，合批不等于全部资源已实测。

验收后清理过程文件，先按依赖迁移固定测试输入与必要失败／成功证据，再删候选、重复导出、整图过程备份及退役发布入口。不能让测试继续依赖已删tmp；发布入口的退役不能只依赖tmp里的published标记，否则清理标记后可能重新启用。保留维护用纯构建函数、固定样本与正式记录，历史回执不重写；另记被删除备份不再可回退、原版局部样本的实际覆盖范围。删除须限于逐项核对过的工作区路径，清理后重跑适用回归，并确认正式地图及范围外资料未改。

## 10 验证分层，交付结论不得越级

| 层级 | 必查内容 | 能说明什么 |
| --- | --- | --- |
| 静态结构 | 类型、声明、ID、引用、参数及批量入口 | 文件与引用结构符合已核对规则 |
| 离线逻辑 | 数值、重复刷新、撤销、事件先后、隔离等相关行为 | 测试模型覆盖的逻辑通过 |
| 编辑器 | 加载、重载／保存后回读、实际页面与事件参数 | 实际加载内容及已检查页面正确 |
| 实战 | 获取、升级、合成、失去、战斗与相关边界 | 已执行场景中的引擎行为通过 |

`valid=true`、导出一致、离线测试通过均不能单独证明编辑器和游戏可用。离线解释器必须限制事件参数可用性，不能无条件替引擎补出事件没有的对象。

独立触发器／函数根结构与物编内嵌`trigger_dict`封装分别验证。工具只支持独立根结构时，应按支持范围逐个校验内嵌触发器或使用对应导出检查；不能将封装缺少根字段的工具报错直接认定为物编损坏，也不能将工具不支持记为验证通过。目录／调用解析、磁盘内容一致和编辑器实际加载分别留证。

离线模型还必须约束原生 API 的操作数类型及可选参数语义。不支持或未实现的表达式明确失败，并区分“引擎不支持”与“模型尚未实现”；不得用宿主语言真假值、默认对象或自动类型转换替引擎虚构能力。测试替身的边界须列出，不能把其成功返回当作实际引擎成功执行。

**影响多个资源的共用函数，批量接入并发布前必须先通过代表场景的最小实战验证。** 记录调用输入、实际判定结果和最终行为，再扩大接入；例如自动施法至少覆盖单位空闲、普攻中、施放其他主动技能中，并确认允许场景确实执行了施法命令。其他函数按其事件及失效边界选择代表场景，不套用固定英雄名单。暂不能实战时保留候选与未验证状态；若负责人明确要求离线交付，则按该范围交付，不把离线结果写成实战通过。

关卡入口类代表场景应追到“实际选关参数 → 查表结果 → 模式按钮 → 切图”，不能仅以按钮事件进入、窗口显示或模型返回有效行号代替切图验证。负责人试玩反馈可以作为实战证据，但只登记其明确确认的范围；“按钮恢复正常”不自动证明胜负、重试、奖励隔离及全部异常分支通过。

同模板批量修改，应全量扫描全部实例的入口与参数；编辑器逐类事件、不同参数写法和关键资源页面检查，注明实际打开范围。抽查一张不能写成“全部页面通过”。有条件时扩大页面检查；未检查的范围明确记录。

测试关注独立的预期结果和故障边界，不能只让测试解释器复述生成器的假设。每次返工将实际缺陷加入检查；复用型批量实装至少覆盖重复应用、失去重获、无效实例、玩家隔离及本次涉及的更新时序。

UI模型必须从实际启动入口按原生注册格式建立监听，并只允许声明在实际事件控件上的事件进入；禁止直接遍历定义调用处理器来绕过注册。失败样本应能重现“根执行但无点击”“空UI资源标红”等旧问题。单位／技能池测试区分技能类型与运行时实例，覆盖动态加入、重复登记、原状态保留及开关对新行的实际更新；模型正确不等于引擎命中、绑定、渲染或施法已通过。维护构建器重建版本和实际发布样本分别标明，不能只验证旧重建结果。

自动测试必须区分 PASS、FAIL、SKIP。新对局或持卡前提不满足而跳过时，不算通过，也不能假定其临时强制概率／补卡步骤执行过。直接读取实际会话日志核对，再决定是否可用该样本解释掉率和推进发布；负责人已确认的正常试玩行为也只记入对应代表路径。

英雄回归另须覆盖全军阵亡后重试、英雄伪死亡但原生存活、小兵原生死亡、伤害致死后继续加状态、多颗弹道并发、旧循环移除后同类重建，以及玩家/NPC两种敌我方向。异步回调的局部捕获属于必须验证的边界，离线模型不能凭空提供原事件已经失效的对象。

返工必须先让检查重现旧缺陷，再验证修正版；不支持或不合法的表达式应明确失败，不能默默容错。蜀国表参数和后续返回值回归分别加入“表资源常量内嵌运行时表达式必须被拒绝”“设置 True 后再设置 False 会覆盖结果”的检查。修正生成器时同步修正测试解释器，历史通过次数保留其当时的模型限制。

### 路线和报价要验证完整候选集合

- 不能只由测试预先指定正确组件ID，再以合成成功认定报价正确。逐阶检查所有已解锁、未抽取、非结果候选，断言终局、其他阵营和不合格身份没有误开放；再从候选集合推进收集。若检查的是实际报价过滤前的较大集合，明确该范围，不冒充UI权重或随机报价验收。
- 配表与脚本同时修复时，保留故意污染的旧配置用例：先用旧脚本重现，再证明新脚本能拒绝错误组别／身份下的终局资源。仅用修好的表测试，可能掩盖脚本仍无边界检查。
- 分支系统覆盖普通左右两线、特殊结局及两种完成先后、另一线差一阶、锁定后当前组收尾、失败授予后另一线继续变化、空或错后继配置。未实测的分支保留待验证，不能用一种特殊结局通过替代全部结局。
- 唯一性同时核对历史获得流水和当前有效持有，不只统计“授予成功”日志。测试和实战分别检查终局前未持有、只出现一次合法来源、后续完成另一线未再授予、最终快照仍只有规定数量。

群雄原20项测试执行了真实解锁ECA，但只选择指定普通组件，漏掉终局UR已被开放。修复后27项增加完整候选集合与错误配置回归；实际新局确认双线特殊终局只有巨象兵，日志未记录所有三选一选项，因此不将其扩大为完整报价UI验收。原失败与通过证据均保留，见[群雄实装记录](../deliverables/群雄军略卡牌实装与验收记录-2026-10-27.md)。

镜像入口返工进一步覆盖“`TYPE_IS_EXIST` 接收 MAP 必须拒绝”“字符串拼接保留启用的可选参数、跳过禁用参数”。若发现原模型错误放行，必须在历史记录旁标明限制，不能继续引用旧通过次数证明该用法正确。

验收必须有正向行为证据：属性实际生效、奖励实际到账、允许的技能实际释放，以及失去效果后正确撤销。警告减少或没有报错只能作辅助证据；主体逻辑未执行也可能没有警告，不能因此判为修复成功。

编辑器保存后的异步校验可能补写元数据或改变 `valid`，必要时等待后再次保存和回读，不以写入后立即读到候选值代替最终加载结果。保留实际有效的元数据，不只把无效标记改成 true。旧测试若把查值误模拟为查键等，补记模型缺陷及纠正范围，历史通过数量不再用于证明相关语义；也不能因此笼统宣布全部历史测试无效。

### 性能定位与改善必须有同口径证据

- 先由采样定位高频调用链，再阅读对应ECA；区分原生API自身成本、它触发的子事件／子调用，以及脚本重复读取和显示。按实测耗时与可消除的工作量排序，不能把“造成伤害”总耗时全部归给某个可编辑函数。
- 火焰图中的CPU时间`ms`不是FPS；区分曲线可见峰值、实际选中帧、悬浮帧和下方表格的统计对象。`Total`包含子调用，`Self`是自身耗时；不同层级的Total不能直接相加，表中百分比分母未核对时不能当作整帧占比。
- 前后对照记录地图／脚本版本、阵容与星级、卡牌、波次、兵力、运行模式／倍率、采样区间和选择范围；保留普通战斗与尖峰样本。不对齐的两张截图只能分别说明观测结果，不能据此宣称性能提升比例。
- 分别报告行为等价、API调用／UI写入数量、代表试玩反馈及帧耗时实测结果。新增计时器、KV和条件检查也有成本；减少写入、日志或警告不能代替实测收益。关闭追踪后用正向玩法观察验证，不能继续以已关闭日志的缺失认定技能未执行。

2026-10-30三批优化已有离线对照及代表性运行证据，但前后采样场景未对齐，性能提升比例未验收；原截图及限制见[第01步记录](../deliverables/自动战斗性能优化-第01步伤害上下文复用-2026-10-30.md)。

## 11 排错必须定位并保留因果边界

定位本轮最新日志，记录时间、地图、报错数量、不同节点及完整调用链。按“触发器类型、触发器 ID、元素 ID、物编资源 ID”匹配历史；复用的 ID 必须结合对象和调用上下文消歧。

当前日志为空可能是尚未刷盘，应核对本轮文件与起止时间，不用旧会话日志冒充最新样本；一个文件包含多次会话开始时注明范围。错误条数、不同节点数及业务问题类别分别统计。报错源与备份相同能证明该文件未改，不足以单独排除所有间接影响。

分别记录：本模块直接报错、共享链中的错误、已存在的旧问题，以及尚未证实的间接影响。错误发生在改动之后，不足以证明由改动产生；没有本模块报错栈，也不足以证明其全部分支已经运行。缺少底层异常正文时，静态推断必须标为排查方向。

多项校验共用失败出口时，提示或诊断应提供足以区分失败阶段的必要输入与中间结果，如关卡编号、难度、配置行；不要只有“配置不存在、地图为空或难度无效”一类笼统合并消息。错误信息显示只证明该失败出口已执行，仍须结合实际值核对原因，不能把提示文案当成完整异常链。常规反馈保持简洁，临时详细日志定位后按授权移除，不输出整份玩家存档。

用户暂缓的英雄或其他模块问题，只记录，不借排查扩大修复范围。

### 军略获卡与持卡调查日志

- 记录结果前核对写表完成、技能实例有效且属于目标载体。至少包含会话／地图、玩家索引、流水、波次／阶段、实际卡牌 ID 与名称、等级和来源；未读到实例应记核验失败，不只因进入授予函数就打印成功。
- 概率赠送补充来源卡、触发事件、配置概率、原掷骰和实际赠卡；EX 补充资格门槛及实际授予结果。奖励来源上下文与玩法重入状态分开维护，日志开关不得改变奖励或多调用随机数。
- 路线终局记录触发路线、完成阶段、当时其他路线解锁阶段、固定终局类型及实际结果。授予辅助函数可能返回已有实例；“返回有效”不等于“本次新发”，须对照此前流水与快照，已有则区分本次跳过或已持有。不能把一次成功提示作为唯一性证明。
- 历史获得流水与当前持卡快照分开。快照从现有军略目录和运行时持卡记录筛选，校验记录归属及实例实际拥有者，按类型去重，排除英雄技能和失效记录；支持稀疏记录，不把静态配置行号当成动态持卡行号，也不以表长度代替有效数量。
- 快照按玩家编号、快照号和开始／结束行配对；列出有效卡牌及展示标记。持卡与相关状态未变化时周期检查不重复输出。结算、退出、断线的记录时机核对实际生命周期；载体已销毁时引用最后有效快照，不伪造零持卡。强制结束进程不保证末次回调，调查可使用最近完整快照。
- 常驻调查日志保留统一前缀、开关和低频变化输出，临时全量概率追踪另外登记。日志只保留调查所需数据，不输出整份存档；清理会话前归档关键样本。日志功能本身要经过真实新局验证，不从离线字符串断言宣称引擎已输出。
- 分类计数按实际定义解释。通用日志的“EX种数”不必包含另一阵营的“终极UR”；核对本次结果类型、ID及有效实例，不能因计数为0否定已经获得。改变解锁或初始化脚本后使用新局验证，旧局运行时表可能保留错误解锁状态；无选卡来源记录也只证明未记录到该获取，不能反推每一轮UI从未展示该卡。

当前实现与开关见[日志与持卡快照说明](../deliverables/军略卡牌获卡日志与持卡快照-2026-10-27.md)。本次实测覆盖选卡、正常合成、温恢／曹彰赠送、EX 司马懿及阶段／变化快照；其他概率来源、退出／断线／结算与多人仍不能写成已验收。

### 英雄运行追踪

- 区分事件进入、命令提交、原生施法阶段、出手及效果动作前后记录。“命令已返回”不等于成功施法；“伤害动作已返回”不证明最终血量、暴击倍率或治疗收益。记录英雄、星级/技能 ID、触发器与元素 ID，出现同名敌我英雄时补充施法者实例和目标，不能合并次数代替我方验证。
- 记录冷却、实际范围、合法候选、动作状态等可区分断点的信息；临时日志按状态变化或必要关键节点输出。只记录“获得”的被动可能由其他技能/Buff读取开关执行，应追到实际消费者，不能直接判断为空技能，也不能凭开关存在宣称收益通过。
- 本图已经实测原生日志可以承载自定义追踪文本。固定前缀、节点 ID 和登记清单支持精确撤除，删除日志不得整份恢复旧 ECA。临时动态诊断另外登记，不能把统一清理工具视为自动覆盖所有后来增加的探针。
- 原生日志在会话切换/清理后可能不可再读，关闭或重启前按需归档关键样本；尚未核实其容量及保留上限，不承诺永久保存。地图曾打不开的直接原因仍未确认，不能将其归因为“官方日志排斥自定义文本”。

### 高频追踪使用精确、可逆的维护开关

- 常态战斗可按已确认范围关闭逐动作追踪，保留原生错误／警告与有意常驻的低频调查日志。需要离线开关时，精确修改登记节点的`enable`，不在每个高频动作前额外添加运行时IF；交付明确是离线维护还是运行中开关，不能混称。
- 登记至少包含资源路径、节点ID、动作类型及完整参数。字面量日志与动态诊断分别核对；动态参数可能调用函数或随机数，关闭前必须确认不承载玩法写入、不改变随机序列。发现副作用时先拆分，不把关闭打印当作天然无副作用。
- 开关按当前工程精确变更并可逆，未知／重复节点或参数变化须先审查，不能按大前缀删除所有打印，也不能整份恢复旧技能文件。维护中的追加工具读取同一默认模式；历史迁移器保持退役，防止重新带回已撤探针。
- 标准追踪关闭后仍打印时，按实际前缀和节点查来源，再更新对应登记；不能仅因残留文字就断定开关失效。样本没有日志也只证明未输出，不证明所有关闭节点都曾执行。

本次1669条标准追踪与47条旧动态诊断分开登记，未来统一切换；维护入口与限制见[第02批](../deliverables/自动战斗性能优化-第02批克制判断与追踪开关-2026-10-30.md)及[第03批](../deliverables/自动战斗性能优化-第03批能量显示与旧日志收口-2026-10-30.md)。这些数量是本次清单，不作为后续固定覆盖数。

2026-10-18 负责人追加授权修复的公共伤害站位读取及英雄自动施法警告，见 [修复与全英雄主动技能检查记录](../deliverables/战斗重复警告修复与英雄主动技能检查-2026-10-18.md)。此授权不扩大到其他弹道、Buff、UI 旧问题。

## 12 机制与表现分别验收，说明后续维护入口

UI换肤先核对图片透明边缘、九宫拉伸的有效内框、控件锚点、文字对齐与命中矩形。底板外尺寸相同不代表内容可贴边；头像、姓名、高亮框和标题须在实际内框中检查，两排布局及按钮区域分别验证。纯装饰不拦截输入，复用图片不等于新增图片资源。只获准改左侧皮肤时，右侧完整子树及ECA应有差异保护；草图／效果图未获采用不作为发布授权。静态边界通过后仍看原生画面，代表分辨率通过不扩大为全部分辨率／满员／多人通过。

动态列表按任务容量设计。列表可视区以完整行高和行距计算，并在局内验证满员、滚动首尾、长中文说明、禁用态及选中反馈。短扫描信息放行内，完整说明放专用详情区。多个弹窗可以按各自任务使用不同尺寸。

机制、数值、粒子／光环、音效／动画、图标／UI、正式卡池接入分别写明完成度；未配置表现时明确写“机制已实现，专属表现未实现”。

持续表现要有销毁与来源绑定，一次性表现要明确时长和销毁设置；不以图标存在代替特效验收。

交付应让接手者知道：改现有数值到哪里、新增同类卡需哪些字段、新增属性语义改哪里、新机制改哪里，以及哪些项目尚待验证。玩法变更另按当次设计口径执行，不由技术重构顺带决定。
