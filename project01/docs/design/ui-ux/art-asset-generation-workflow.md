# 美术资源出图与切片流程规则

本文档记录项目级美术资源生产流程。后续生成 UI 控件、卡牌、按钮、特效序列帧、HUD 元素等游戏美术资源时，默认遵守本文档。

## 核心原则

美术表现优先由图像生成或人工设计方案完成，脚本只负责工程化整理、切片、校验和批量一致性处理。

除非用户明确要求直接产出最终切片，否则不要跳过审美确认阶段。不要用脚本绘制替代主要美术创作。

审核前的图片只能作为临时预览，不得落入正式资源目录、资源索引或 manifest。若为了预览需要创建实际图片文件，项目负责人明确通过或不通过后都必须清理该轮临时文件：通过时先依据已确认方案导出正式资源，再删除临时效果图和清稿；不通过时直接删除全部临时文件。

## 资源归档根目录

项目正式美术资源统一归档到 `assets/art/` 下。

默认目录职责：

- `assets/art/characters/`：武将头像、半身像、立绘和角色相关 manifest。
- `assets/art/ui/`：UI 控件、HUD、按钮、卡牌、图标、特效序列帧、预览和源图。
- `assets/art/ui-concepts/`：已保留但尚未进入正式切片的 UI 概念图。
- `assets/art/packages/`：阶段性 UI 资源包、控件样板包、效果图包和可实装资源包。

路径规则：

- 新增正式资源必须优先使用 `assets/art/...` 路径。
- `tmp/`、`.tmp/` 只允许存放过程稿、脚本缓存、一次性预览和临时校验图，不登记为正式资源。
- `deliverables/` 只存放文档类交付物；美术资源包必须进入 `assets/art/packages/`。
- 不再新增 `assets/ui/`、`assets/characters/`、`assets/ui-concepts/` 这种旧式并列目录。
- 移动资源时必须同步更新 README、manifest、文档、工具脚本和原型页面中的引用路径。

## 标准三阶段流程

### 1. 氛围图 / 效果图阶段

目标是先解决审美方向。

执行方式：

- 使用图像生成或参考图重绘方式，先产出完整效果图、氛围图或整套 UI 展示图。
- 优先追求整体构图、风格、材质、细节密度、光影、色彩和游戏美术质感。
- 允许图中存在临时文字、占位内容、展示性排版，但需要明确告知用户该阶段不是最终可用切片。
- 产出后必须等待用户审美确认。

禁止事项：

- 不要在用户确认审美前就拆资源。
- 不要因为规格、尺寸、透明背景等工程要求而牺牲第一阶段的美术表现。
- 不要用脚本几何绘制直接冒充最终美术效果图。

### 2. 清稿 / 无文字可拆版本阶段

目标是把已确认的审美方案转成更适合切片的干净图。

该阶段不是每次都需要。如果第一阶段效果图本身没有文字、元素边界清晰、背景可控，可以跳过。

适用场景：

- 效果图里有写死文字，但最终资源不能包含文字。
- 元素之间距离太近，直接切片会互相粘连。
- 背景复杂，透明抠图风险高。
- 用户要求“照着效果图重绘，但不要复制原图像素”。

执行方式：

- 以已确认的效果图为视觉基准，重新生成或重绘无文字、可拆、元素间距更干净的版本。
- 保留已确认的风格、比例、材质和装饰密度。
- 不新增未经确认的视觉方向。
- 完成后再次给用户确认。

禁止事项：

- 不要用粗糙色块覆盖文字。
- 不要从带文字图中硬裁后伪装成干净资源。
- 不要在清稿阶段大幅改变第一阶段已确认的美术风格。

### 3. 工程切片 / 资源校验阶段

目标是把已确认的图整理成项目可用资源。

执行方式：

- 用脚本或图像处理工具完成切片、透明背景、尺寸统一、命名、manifest、预览图和校验。
- 对透明 PNG 做 alpha 边缘检查，确认非矩形控件四周有透明安全边。
- 对矩形背景类资源明确标注其为不透明矩形资源。
- 输出棋盘格预览或组合预览，用于检查透明区域是否干净。
- 修改切片坐标或抠图规则时，只改对应资源，不无故重做已确认资源。

推荐输出：

- `source_*`：已确认的整图或清稿源图。
- `transparent/`：最终透明 PNG 切片。
- `preview_*`：普通预览和透明检查预览。
- `manifest.json`：资源尺寸、来源坐标、九宫格建议、状态说明。
- `README.md`：资源用途、状态和注意事项。

禁止事项：

- 不要让脚本承担主要美术设计工作。
- 不要在最终资源中留下临时文字、背景底色、邻近元素碎片。
- 不要覆盖已通过审核的目录；新版本用独立版本目录保存。

### 4. UI 控件可实装资源包细则

本节适用于窗口、底板、headbar、按钮、页签、HUD 面板等需要进工程的 UI 控件资源。

#### 4.1 清稿版式要求

如果资源需要从图像生成结果进入工程切片，清稿必须优先按以下结构输出：

1. `base assets` 行：只放主体框体、可拉伸边框、角、底纹、按钮底。
2. `overlay ornaments` 行：只放玉扣、徽章、兽头、纸夹、印章、龙纹、盾徽、花枝、铆钉等固定装饰。
3. `recomposition preview` 行：只用于展示 `base + overlay` 组合效果，不作为最终切片来源。

清稿阶段必须保证：

- 元素之间留足安全距离，避免自动切片时互相粘连。
- base 元素不得烘入徽章、玉扣、纸夹、印章、兽头、龙纹、盾徽等可拆装饰。
- overlay 必须是纯装饰件，不得携带底板碎片、矩形背景、邻近控件残片。
- 圆形按钮、页签凸起、角饰等不能贴画布边缘，避免切出缺边资源。
- 源图若只是展示总览或氛围图，不得直接当成最终切片来源。

#### 4.2 9 宫格与装饰分层规则

带装饰的 UI 控件默认采用：

**主体框体做 9 宫格，装饰物单独叠加。**

执行规则：

- `base_9slice.png` 只包含可以被拉伸的主体框、边、角和底纹。
- `overlays/*.png` 固定尺寸叠加，不参与 9 宫格拉伸。
- headbar 中央徽章、页签顶部徽章、窗口角外龙纹、底部玉扣等必须拆成 overlay。
- 圆形按钮默认使用 `base_fixed.png`，只做等比缩放，不做 9 宫格。
- `manifest.json` 必须记录 `scale_mode`、`nine_slice.left/top/right/bottom`、资源尺寸和来源坐标。
- 若某个控件经过工程修复，必须在 `manifest.json` 中记录 `repair_note`。

禁止事项：

- 不要把带徽章或兽头的整条 headbar 直接做 9 宫格。
- 不要把纸夹、印章、玉扣、龙纹等具象装饰烘进 base 后再拉伸。
- 不要从扁平合成图中硬抠装饰，再用邻近像素补丁伪装成无装饰 base。

#### 4.3 透明与 alpha 校验规则

最终 PNG 必须经过透明检查。

必做检查：

- 使用黑色 / 高饱和粉色等高对比背景生成 `preview_alpha_check.png`。
- 检查资源外围是否有非透明白边、浅色底、棋盘格残留、阴影底块。
- 检查 alpha 外接框是否贴到画布边缘；若贴边，应确认是否缺边。
- 检查透明 PNG 是否切到邻近控件碎片。
- 检查 overlay 是否仍带矩形底板或 base 材质。
- 检查 9 宫格拉伸预览，至少覆盖原尺寸、横向加宽、横纵放大三种状态。

alpha 处理要求：

- 从画布边缘连通进来的背景色、近白色低饱和底色、棋盘格残留，应设为 `alpha = 0`。
- 最终资源建议保留 1-2px 真透明安全边，避免边缘高光、角点或软阴影被裁断。
- 如果白色像素是控件内部纸面、瓷面、玉面材质，不应误删；如果是外围描边或背景残留，必须透明。
- 矩形不透明底板资源可以不透明，但必须在说明中明确标注；非矩形控件外围必须透明。

#### 4.4 切片完整性规则

工程切片后必须检查资源是否完整。

常见错误：

- 圆形按钮被切成半圆或缺边。
- 页签被相邻禁用态控件遮挡，右侧或底部缺失。
- 按钮裁切框过宽，带到旁边控件。
- overlay 裁切过紧，装饰尖角、纸夹端点、花枝末端被裁掉。
- base 裁切过宽，外围留下白底或棋盘格。

处理原则：

- 坐标错误导致的缺边或邻居残片，优先修切片坐标并重建。
- alpha 错误导致的白边或底色残留，优先修透明算法并重建。
- 源清稿本身缺边、遮挡或元素不完整时，优先返图重出清稿。
- 只有在用户接受或无法快速返图时，才允许做工程修复；工程修复必须记录 `repair_note`，并在 README 中说明。

#### 4.5 资源包交付标准

可实装 UI 控件包至少包含：

- 每套风格独立目录。
- `base_9slice.png` / `base_fixed.png`。
- `overlays/*.png`。
- `source/`：本包使用的确认清稿或源图。
- `manifest.json`：路径、尺寸、来源坐标、9 宫格参数、scale mode、repair note。
- `preview_assets.png`：资源总览。
- `preview_9slice_stretch.png`：9 宫格拉伸预览。
- `preview_alpha_check.png`：透明通道高对比检查图。
- `README.md`：用途、状态、使用方式、QA 记录、已知问题。

交付前必须确认：

- `manifest.json` 中所有路径都存在。
- 控件数量与需求一致。
- 普通态 / 禁用态按钮都齐全。
- base 和 overlay 的职责清楚，不互相污染。
- 预览图中没有明显缺边、邻近元素残片、非透明白边。

## 用户确认点

默认确认顺序：

1. 用户确认氛围图 / 效果图审美方向。
2. 如需要，用户确认清稿 / 无文字可拆版本。
3. 用户确认最终切片资源。

如果用户只说“继续”，通常表示进入下一阶段，但仍应根据当前阶段说明下一步要做什么。

## 何时可以跳过阶段 2

满足以下条件时可以跳过清稿阶段：

- 效果图没有写死文字，或文字不会进入最终资源。
- 元素间距足够，不会切到邻近元素。
- 背景易于分离，透明区域可控。
- 用户明确表示可以直接切片。

跳过时仍要说明：“当前图满足可直接切片条件，因此进入工程切片阶段。”

## 工具使用边界

图像生成适合：

- 审美探索。
- 整体效果图。
- 高质感 UI 氛围图。
- 材质、光影、装饰密度复杂的图像。

脚本适合：

- 尺寸统一。
- 透明 PNG 输出。
- 切片。
- 状态批量生成。
- 命名和 manifest。
- alpha / 边缘 / 预览校验。

脚本不适合：

- 独立承担主要美术设计。
- 在没有审美确认的情况下直接画最终控件。
- 用低美术表现替代图像生成阶段。

## 当前项目默认结论

本项目三国风 UI、卡牌、按钮、特效资源，默认采用：

**先出氛围图，经用户审美确认；必要时再出无文字可拆清稿，经用户确认；最后再做工程切片和校验。**

后续如无特殊说明，Codex 应主动按此流程执行。
