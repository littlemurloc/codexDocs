# M29 · 受压 +25%/级

> 一句话：M25 只做了等级惩罚的一半——「进本白吃 20 压力」。
> 那一半是**一次性**的，撑过前两场就回本。这一期补上另一半：
> 之后每次受压都 ×(1 + 0.25N)，跟着你走完整趟。

---

## 1. 起点：只做了一半的惩罚

M25 的 `entry_stress()`：

```gdscript
func entry_stress(hid, quest_level) -> float:
    return float(max(0, quest_level - resolve_of(hid))) * 20.0
```

低 2 级的英雄打精英本，进门 +40 压力。听起来挺狠——但它是**一次性**的：

| 阶段 | 压力 |
|---|---|
| 进门 | 120（80 + 40 惩罚） |
| 打 3 场，每场吃 10 | 150 |
| 回城减 40 | 110 |

也就是说，这 40 点是「一笔税」，不是「持续的税」。原版同时给了两笔：

> 进本时每低一级 +20 压力，**并且每次受压 +25%**

后半句才是让玩家不敢硬上的那个——它让那 40 点税**在每个回合都在重收**。

---

## 2. 实现：三层倍率，不能合并

`Combatant.add_stress` 原来有两层：

```gdscript
delta *= (1.0 + stress_taken_mod()) * stress_in_mult
#        ↑ 自身 buff（死门 +33%）      ↑ 环境（光照）
```

现在三层：

```gdscript
delta *= (1.0 + stress_taken_mod()) * stress_in_mult * join_stress_mult
#                                                          ↑ 等级惩罚（M29）
```

**为什么必须是新字段，不能乘进 `stress_in_mult`**：

```gdscript
func set_environment(e: Dictionary) -> void:
    ...
    var stress_mult: float = 1.0 + float(e.get("stress_damage", 0.0))
    for u in party:
        u.stress_in_mult = stress_mult     # ← 每场战斗都整个覆盖
```

`stress_in_mult` 是**光照驱动的**，每场开打都会重算。等级惩罚塞进去的话，
走进明亮区域那一刻它就被 1.0 覆盖掉了——而等级惩罚应该整趟不变。

这是这一期唯一真正的设计决策，测试里专门钉了三条：

```
10 × 1.3（光照）× 1.5（等级）= 19.5   ← 叠乘
set_environment({"stress_damage": 0.0})
  join_stress_mult 仍是 1.5            ← 没被洗掉
  10 × 1.5 = 15                        ← 光照归零后只剩等级
```

## 3. 数据（同一批随机的 20 趟，只切开关）

`bench_expedition` 加了 `--resolve-mult`，和 `--resolve=N` 分开。
两个开关分开是刻意的：它们回答的是两个问题。

| 组 | 完成率 | 团灭率 | 压迫指数 |
|---|---|---|---|
| 不模拟（历史基线） | 0.350 | 0.650 | 2.480 |
| `--resolve=1`（只有进本压力） | 0.250 | 0.750 | 2.985 |
| `--resolve=1 --resolve-mult` | **0.150** | **0.850** | **3.785** |
| `--resolve=3 --resolve-mult` | **0.350** | **0.650** | **2.480** |

三件事：

1. **两条惩罚的贡献几乎相等**：进本压力单独 -10 个点，再加上受压倍率又 -10 个点。
   只做一半，等于把原版的惩罚砍了一半。
2. **压迫指数从 2.480 一路涨到 3.785**（+53%），这才是「全程更疼」的直接体现。
3. 第四行与第一行**逐位一致**——第三个等价性检验。等级够格时倍率是 1.0，
   新机制完全隐身，M9 以来的所有历史数字都还能复现。

## 4. 界面：把代价写在出发前

准备屏的卡片太小（6 列 × 52 高），写不下「这个人会吃多少罚」。
而且那笔罚是**一整队**的事，放某张卡上反而误导。所以在队伍摘要里说：

```
出战 4 人 · 平均装备 0 阶 — 3 人低于任务等级：最多进本 +40 压力、受压 ×1.50
```

报「最多」而不是逐人列：队伍里可能同时有差 1 级和差 2 级的人。
玩家需要的判断只有一句「这趟大概多疼」，不需要一张账单。

同时那些不够格的人的 `Lv` 行会转成警告色——这是「谁拖后腿」的定位，
摘要里给的是总账，两者配合才完整。

### 顺手修的一个真 bug

行程区的选中态原来是：

```gdscript
var sel: bool = _prep_size == row[0] and _prep_quest == row[4]
```

只比尺寸和任务类型，**不比等级**。M26 之后同一个尺寸每周的等级不同，
于是会出现「标题写中程 3 级、高亮的是中程 1 级」。加了 `_prep_level == row[1]` 之后才对。

（这个 bug 只在截图时暴露出来——因为我用 `--prep --level=3` 直接指定等级，
而板子上那一格恰好是 1 级。真实玩家点卡片进来一定一致，所以线上没被发现。）

## 5. 已知限制

1. **倍率不作用于「非受压」的惩罚**。原版的「每低一级受压 +25%」只影响受压，
   不影响掉血、减益。我们一致。
2. **没有「低于任务太多直接拒绝」**。原版是低等级**可以**进（吃惩罚），
   高 2 级才拒绝。我们一致。
3. **进本压力没有上限**。1 级打冠军本 = +80 压力，加上原本的压力会直接压在 200 上限。
   原版也是这样，但原版有「0 级英雄第一次出任务必吃惩罚」这种细节，我们没有 0 级。

## 7. 到这里，「原版核心机制」还有哪些缺口

| 机制 | 状态 |
|---|---|
| 战斗（先攻/死门/崩溃/美德/守护/反击/位移/召唤/僵持） | 已有 |
| 数据管线（15 英雄 × 7 技能 × 5 级、254 怪、490 饰品、170 怪癖、60 奇物） | 已有 |
| 远征（房间图/光照/口粮/休整/陷阱/奇物/首领） | 已有 |
| 城镇（8 座建筑/周次/商店/饰品/补给） | 已有 |
| **难度爬升（决心等级 + 双向锁 + 任务板 + 受压倍率）** | **已有（M25–M29）** |
| 名册（15 人上限 / 招新 / 解雇 / 复活） | 已有（M27–M28） |

剩下的是**没有做的机制**，而不是做了但没接的：

1. **任务目标**只有 `explore` / `kill_boss`。`cleanse` / `gather` / `activate`
   三类任务的地图参数和奇物数据一直都在（`dungeons.json`），但从来没接。
2. **每区域一块任务板**。现在四个区域共用一块，区域只影响遭遇表。
3. **同职业多人**（key 改成 `id#序号`）。
4. **城镇事件**（原版每周随机事件的整套系统）。
5. **压力崩溃的完整表现**——我们有 `affliction` 字段和光环/摆烂，
   但原版的「美德觉醒」是一整段演出。

我倾向 **1**：它是最接近「数据早就在、但没人读」那一类的问题，
和 M13/M19/M20 一个路子，工作量小、内容增量大。
