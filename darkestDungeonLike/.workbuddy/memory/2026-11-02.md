## 项目启动：DD1 数据管线（M0）

目标：把《暗黑地牢 1》安装目录的规则数据抽成结构化 JSON，作为 Godot 重构同类型游戏的数据地基。

游戏路径：`D:/Program Files (x86)/Steam/steamapps/common/DarkestDungeon`（2.7 GB，Unity + FMOD，无加密明文数据）

### 关键事实（后续会反复用到）

- `.darkest` 是行式 DSL：`<类型>: .<字段> 值... .<字段> 值...`；`//` 注释；一行一条记录；以 `.字段` 开头的行是上一条记录的续写。
- 作者笔误：`effects/base.effects.darkest` 第 561 行是单斜杠 `/------`，要按注释跳过。
- 站位用**数字位串**表示：`launch 21` = 己方 1、2 号位可发动；`target 12` = 敌方 1–2 号位单体；
  `~12` 推断为 AOE 全体；`@1234` 推断为友方目标。
- **英雄技能 `.dmg` 是百分比修正，怪物技能 `.dmg` 是绝对区间**。同名不同义，移植必须分开处理。
- 引擎内 Spine 版本 **2.1.27**（从 `.skel` 二进制头读出），Godot 官方运行时只支持 3.8/4.x，
  骨骼**不能直接进 Godot**。需烘序列帧、自己写 2.1 解析器，或换原创美术（推荐后者，顺带绕版权）。
- 逻辑层（效果结算顺序、行动序 tie-break、怪物 AI 评分、地图生成算法）在 `Darkest.exe` 内，数据只给参数不给算法。

## 路线决策：用户确认「机制等价的原创游戏」

问的是「先 1:1 全还原再改，还是现在就开始原创」。我的结论：**都不选，按层切**。

- **规则层** → 1:1 还原（玩法规则不受版权保护，且这是「机制等价」的定义）

- **内容层** → 第一天就原创，色块占位，绝不碰 DD1 美术

关键论证：把 1:1 降级成**测试夹具**而非开发阶段。DD1 当 oracle 用（回归测试断言伤害区间），
但数值从第一天就是自己的，避免路径依赖。M1 用圆点色块占位，不用 Spine 动画——
否则会被"看起来像 DD1"骗过去，且资产绑死。

### 验证结果

同种子两次跑完整场战斗，状态快照逐字节一致。

### 关键数据语义（DD1，易踩坑）

- **`dmg` 双重语义**：英雄技能 `dmg` 是百分比修正（叠在武器区间上），怪物技能 `dmg` 是绝对区间。
- **站位前缀**：`~` = AOE；**`@` = 目标是友方**。漏掉 `@` 会导致所有治疗/增益技能往敌人身上放。
  （最初靠 `heal > 0` 判敌我，是错的——「鼓舞」「信仰壁垒」heal 为 0 但仍是友方技。）
- **`heal` 是区间** `[low,high]`，不是单值；`target` 可能为 null。
- **怪物技能是扁平结构**，没有 `levels` 数组；英雄技能有 5 级。不兼容处理会导致怪物全程「站着不动」且不报错。
- 条件伤害修正来自 effect 的 `monsterType`（unholy/eldritch/man/beast）与 `keyStatus`（如 tagged），
  必须在掷伤害**之前**收集，且目标为 `performer` 作用域。
- 伤害修正**加算**（1+Σ），不是连乘；判别用 20 点基础伤害（×1.65=33 vs ×1.725≈35）。
- 命中封顶 0.95（`cutoffAlwaysHit`），写测试时 acc=1.0 也会 miss 5%——必中场景要显式传 `cutoff_hit: 1.0`。

### 与 DD1 对照得到的硬事实

- 英雄速度 = 武器 spd（十字军 1、麻风 2、盗墓贼 8），闪避/生命/防护 = 护甲，与实机一致。
- 先攻 = 速度 + rand(0..8)：速度 8 对 1 的先手率实测 98.8%（仅当快方掷 0、慢方掷 8 才落后），
  这个分布可反推 `initiative_base 8` 的语义。
- 死门抗性全员 0.67。

### 过程中修掉的自身缺陷

1. `for key in (a, b, c)` —— GDScript 不支持括号分组，必须先用变量接数组。
2. `float([1,1])` —— heal 为数组时崩溃，已按区间处理。
3. 眩晕在 `tick_round` 与跳过回合处双重递减 → 一层眩晕跳两回合。改为只在 `consume_stun()` 递减。
4. 无攻击判定的功能技走了伤害管线，会把武器伤害凭空打出去。改为 `atk<=0` 走效果分支。
5. AI 对眩晕估值过高（7.0）导致英雄一直用最弱的控制技；降到 3.0 且乘命中率后才选对技能。

### 工具坑

- Godot `--headless --script` 卡死时 **stdout 被缓冲，print 全丢**，看不到任何线索。
  解法：把进度写入文件并 `flush()`；或先 `--check-only --script <单文件>` 定位解析错误。
- 依赖脚本解析失败时，Godot 只报「Could not resolve class X」，不报内层行号——
  必须对每个 .gd 单独 `--check-only` 才能拿到真实行号。
- 截图：`godot --path . -- --shot=<绝对路径>`，脚本内 `get_viewport().get_texture().get_image()`。
  用 PIL 量非背景像素包围盒确认内容铺满，别靠预览肉眼判断（预览会缩放，容易误判）。

## M2 数值生成器与手感测量（同日）

### 交付

- `tools/gen_balance.py` 数值包生成器（4 类旋钮：英雄生命/伤害均值/伤害方差/暴击率、怪物生命/伤害、暴击倍率、压力）
- `tools/compare_balance.py` 多包指标对比 + 设计目标判定
- `tests/bench_battle.gd` 战斗测量器（15 项指标，5 个场景含连续遭遇）
- `balance/{faithful,signature,lethal_probe}` 三套数值包（`--data=` 绝对路径加载，规则代码零改动）
- `BALANCE.md` 设计意图 + 验证结论 + 已知局限

### 核心结论

**faithful 规格与 DD1 基线逐项完全相同**（轮数 4.096、溢出 0.115、暴击 0.077），
证明「曲线抽取 → 生成器 → DdDb 加载」整条链路自洽。

**signature 规格全部目标达成**：轮数 4.10→5.30、溢出 11.5%→7.8%、
暴击 7.7%→6.3%（倍率 1.5→1.85，期望持平）、压力 20.4→18.7。

### 重要发现（指向 M3）

**危险度维度在这套系统里是钝的。** 满编四只高难怪、甚至怪物伤害 ×1.6，
实测仍是零死亡、零死门、终局血量 94%+。两个原因：
1. 怪物单次伤害 2-7 点 vs 英雄血量 22-33，比例悬殊
2. 治疗完全抵消累积伤害——连续三场打完血量反而从 44 涨到 57

结论：**压迫感不可能靠调伤害数值做出来**，必须在资源层设计（休整限制、口粮、火把、
治疗次数上限）。这是 M3 的第一优先级。

### 指标设计教训

- 只测「死没死」太钝（二值量）。危险度必须是连续量：终局血量占比、最低血量水位
- 溢出伤害不能用 `raw - damage`：`raw` 是掷骰后未减护甲的值，
  差额里混着护甲减免。必须 emit `gross`（扣血前最终伤害）再相减。
  修之前算出 57% 溢出，修之后 11.5%
- `Battle.events` 每轮开头会被重置（注释写「同时累加」是错的），
  测量必须自己逐轮 `append_array(b.run_round())`
- 连续战斗继承血量要传**比例**不是绝对值，各英雄上限不同；
  写死分母会得到 130% 这种荒谬数字
- bench 必须让队伍装备随难度提升，否则测的是「1 级队打 5 层」这种不存在的场景

### 工具坑补充

- `compare_balance.py` 汇总时要排除 gauntlet 场景（三场合计口径不同，会污染平均）
- `DdDb.shared(base)` 传非空路径会强制重载，用于同进程切换数值包

## M3 资源层与远征（同日，用户选 A 路线）

### 交付

- `src/core/expedition_cfg.gd` 资源策略预设（4 档：lenient/standard/tight/brutal）
- `src/core/route_gen.gd` 从 dungeons.json 的 maps+encounters 生成路线（不是手写固定剧本）
- `src/core/expedition.gd` 远征编排：光照/口粮/休整/撤退/状态延续/崩溃
- `data/expedition.json` 只放「DD1 数据里没有」的策略；光照表、饥饿、营地常量仍读 rules.json
- `tests/bench_expedition.gd` + `tests/dump_expedition.gd` + `tests/test_expedition.gd`
- `tools/compare_expedition.py` 多包对比 + 单调性/目标判定 + markdown
- `balance/signature_v2/` signature 的远征修正版
- `M3_EXPEDITION.md`

### 核心结论

**资源层就是「伤害维度」的放大器。** 同一 lethal_probe（怪物伤害 ×1.6）：
M2 单场 hp_end 0.959→0.940、零死亡；M3 远征 hp_end 0.311→0.035、死亡率 0.392→0.850。
所以 M2 那句「压迫感不能靠伤害数值」要改成：**压迫感来自伤害，危险度来自资源预算。**

只换资源预设（data 包，medium Lv3，60 趟）：完成率 0.867/0.733/0.233/0.017，
压迫指数 0.773/1.385/2.767/3.297，四个包全部单调。
faithful 包与 data 包远征指标**逐项相同**（校准在两个尺度上都成立）。

### 修掉的 M1 遗留缺陷（都只在跨战斗时显形）

1. `is_alive()` 原为 `hp > 0` → 一进死门就从 living/行动序/目标里消失 = 直接退出战场
2. `heal()` 在死门 `return 0` → 死门成了单向陷阱，与 DD1 相反（应能救回 + 恢复期减益）
3. `tick_dots` 调 take_damage 没传掷骰（默认 1.0 必死）→ 死门上挂流血必死

### 找到并修掉的上游设计缺陷

signature（怪物生命 ×1.45，战斗 4.1→5.3 轮）单场指标全绿，远征完成率只有 0.333。
诊断：战斗长 29% = 多挨 29% 打，治疗输出不变 → 净掉血。
`signature_v2`（怪物伤害 ×0.85）把完成率拉回 0.500，长战斗意图保留。
**教训：单场指标全绿不等于这套数值能用。**

### 踩到的坑

- 怪物死亡事件也叫 `death`，不分阵营会得到「每趟死 14 个人」；事件里补 `hero` 标记
- 人均率的分母：sums 存的是每趟平均，除以「趟数×人数」会把 0.975 团灭率算成 0.02 死亡率
- 路线必须先全部生成再喂给各预设，否则差异里混进「这次遇到的怪不一样」
- `run_step` 被外部循环调用时不会自己收尾，会一路越界读 route → 末尾补 `_end("complete")`
- 新 class_name 要先 `--editor --quit` 重建 global_script_class_cache，否则全项目报「找不到类型」
- 光照档位表 `lowest_excluded: true` = 左开右闭，75 属于微光不属于明亮

### 验证

战斗核心 **178 项断言全绿**（原 113 + 远征 65）。

### 关键设计

**不在规则层塞 await。** Battle 是 RefCounted，没有信号；做成「可停可续的状态机」，
两套驱动共用同一段结算逻辑。为此加了一条断言：同种子下逐步驱动（AI 兜底）与同步驱动的
轮数/胜方/每个英雄血量压力生死必须完全一致 —— 界面把规则带歪时这条会红。

### 真玩一遍才发现的事

1. 长图 Lv5 是断崖不是斜坡：贪心策略第 4 步就团灭（4/18 步），短图 Lv1 则 96% 血走完
2. 撤退按钮没有存在感：撤退保住活人，但没有跨远征持久化，撤退=纯亏
3. 技能面板缺「预期伤害」，玩家第一次点技能判断不了值不值
4. 节奏慢得对：一场 4-6 轮约 20 次点击，每次都要判断；缺的是反馈不是速度

### 踩到的坑

- 自绘 UI 别用 emoji 类字形（⚔ 会 fallback 成怪字符），一律用中文标签【遭遇】【崩溃】
- 表现层误报：英雄 `hero_base().acc` 恒为 0（命中率由技能自带），
  面板上写「命中」会恒显 0%，应显示 闪避/护甲/速度/暴击
- 自绘按钮的矩形在 `_draw` 里生成，所以「点不到」这类 bug 只能用端到端自检抓，
  规则测试永远抓不到
- `--shot-at=` 与 `--shot=` 前缀不同，别用 begins_with("--shot=") 一并捕获

### M3 遗留的数字同步

### 关键决定（都踩过坑）
1. **走廊必须只连相邻房间（曼哈顿<=2）**。第一版不限距离，生成出跨半张图的长边，
   图上相邻、空间上隔三间房 → 玩家会觉得「地图在骗我」。长边只作连通性兜底。
2. **必须「先连树再选端点」**。min_final_distance 是图上跳数（中图7/长图10），

3. **格子要正方形**：按宽高各铺满会让房间横稀纵挤，像表格不像地图。
4. **取景按已探明房间包围盒 +1 格**，否则开局两间房铺满整屏像空页面。
5. **光照只在走廊那一步扣**，否则一次移动扣两次，短图补给撑不到出口。

### 核心结论（weald medium Lv3 standard，120 趟）

| | straight | avoid | smart |
|---|---:|---:|---:|
| 完成率 | 0.908 | 0.817 | **0.950** |
| 阵亡 | 0.675 | 0.633 | **0.442** |
| 终局血量 | 0.556 | 0.577 | **0.642** |

**信息综合使用 +4.2 点完成率、少死 34%；单目标优化（只躲陷阱）-9.1 点。**
原因：avoid 为躲已知陷阱走进更多未知战斗房，代价付在看不见的地方。

### 绕路是负期望（重要）

权重扫 1.0/2.0/4.0 → 1.0 与 0 完全一致、2.0 与 4.0 完全一致：
网格图上没有「绕 1 步」的选项，门槛至少 2 步，而 2 步的代价（多 0.8 房 ≈ 多 14 光
→ 提前昏暗 → 压力翻倍）大于一趟 0.5 次陷阱的期望伤害。
所以这层兑现的决策是「要不要为侦察点火把」，不是「绕不绕」。

### 修掉的真问题

1. **M7 的「选路」是假的**：中图 14 房 15 边 = 树 + 1 环，最短路唯一。
   三种加环方案都试过，只有「允许缩到深度下限」同时保住深度(100%)与环数(4/6/8)。
   禁止缩短 = 禁止分岔；无限缩短 = 毁掉深度。
2. **界面 `_drain_queue` 漏了 trap/obstacle**：会掉进 `_:` 被当战斗启动。
   320 项断言全绿也抓不到——规则层测试不走界面路径。
3. **bench 的 smart 分支静默没写进去**：脚本替换源串写错、无断言 → 三组数字一模一样。
   正是这层要防范的「不报错的失效」，先在自己的测量工具上发生。
4. 配额顺序分配让饥饿从 3.5 饿到 0.2（改成按比例 + 保底 1）
5. `shortest` 缓存未在加环后重算（界面「出口 X 步之外」偏大）
6. `--reveal` 只点房间不点走廊；`--to-result` 用线性驱动跑图模式（推进 1/9 就 complete）

### 验证

320 项断言全绿（新增 35：配额分配 12 + 陷阱/障碍 23）；
三档端到端自检 PASS；**线性 bench 一个数没变**（0.835/1.448/2.725/3.278）。
