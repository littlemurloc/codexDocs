## 追加：M71 桌面窗口等比缩放（「界面遮挡严重」的真因）

用户报三屏遮挡（准备屏按钮压出征卡、地图屏按钮压队伍卡、战斗屏技能区被裁），
怀疑是窗口分辨率。**是**，而且不是布局 bug：

- 项目逻辑分辨率是竖屏 750×1334，但**没有设 stretch**，桌面 1:1 开窗 = 750×1334 px。
- 屏幕可用高度只有 1032（1920×1080 减任务栏）→ 窗口底部被截，
  而三屏的「贴底按钮」全在那一块，看起来就像互相压住。
- 布局本身没问题：同一批界面在 750×1334 截图里完整、不重叠（`shots/m71_prep.png`、
  `shots/m71_map.png` 可证）。

修法（`_fit_desktop_window()`，在 `--w` 分支的 else 里调用）：
- `content_scale_mode = CANVAS_ITEMS` + `aspect = KEEP` + `content_scale_size = 750×1334`
  → **逻辑尺寸永远是 750×1334**，布局不随窗口变。
- 窗口按屏幕可用区等比缩到 96%（给标题栏留 4%），居中。
  本机 1920×1032 → 557×990。

三种情况**故意不缩放**：
1. `--w=` 排版验收：依赖「窗口多宽、布局就多宽」（M41 踩过，开 canvas_items 会让 1080 被缩回 750，测了个假的）。
2. `--shot=` 截图：要输出 750×1334 原尺寸，否则所有验收图都变成缩略图。
3. headless / Android：各自已有处理。

**教训**：`size` 是布局的唯一真源。只要窗口尺寸能小于逻辑尺寸，
所有「贴底/贴右」的 UI 都会跑出可视区，而它看起来像「元素重叠」而不是「被裁」——
因为上层元素正好盖住了下面的内容。竖屏项目上桌面必须锁逻辑尺寸。

## 追加：M72 挪位文案 + 字号整体 +2

### 挪位（用户问「怎么感觉是定死的」）
逻辑本来就是动态的：`move_options()` 按 `move_action.move=[min,max]` × 前后两个方向
现算落点（`crusader [1,1]` 只给相邻，`highwayman [2,2]` 可跨两格）。
问题在呈现——按钮只写「移到 3 号位」，看起来像两个写死的选项。

- 文案改成 `前移 1 格 → 2 号位（与强盗换位）`，方向/格数/交换对象都算出来。
- 战场上加高亮：挪位模式下，可落点的队友脚下套一圈金色地环（`is_move_spot`），
  不用读「3 号位」再回头数人。

### 字号整体 +2（`dd_theme.gd`）
`FONT_TAG 9→11 / SM 10→12 / MD 11→13 / BD 13→15 / LG 15→17 / H1 16→18 / HERO 20→22`。

原因：750 宽是按手机 2x 密度设计的，9~13 在手机上等于 4.5~6.5 逻辑点；
桌面窗口按 1334 高等比缩到 0.74 之后，9px 只剩 6.7 物理像素。

**连带修的四处**（都是「字变大就溢出」）：
1. 地图屏队伍卡：`压力 0` 单独一行会压到卡片底边 → 去掉文字，只留条形 + 中点刻度。
2. 地图格子「你在这里」：阈值 78 → 88 高，图标中心 0.46 → 0.42。
3. 城镇名册条：`存活 5 · 上限 4` 顶到「全部 ›」→ 缩成 `活 5/4`。
4. 技能卡摘要：去掉「命中 +X%」「暴击 +X%」——卡片第二行只放得下 10 个字，
   而真实命中率在瞄准态直接标在目标头上。

**物理上限**：1080p 屏可用高 1032，750×1334 最多缩到 0.77。字号 +2 相当于把这行字
的等效密度提了约 20%，再大就得重排各屏行距，不是改常量能解决的。

## 追加：M73 地图房间编号 + 残骸可摧毁

### 地图编号

### 残骸（尸体）可摧毁

规则层（`combatant.gd` / `battle.gd` / `effect_resolver.gd`）：
- `corpse_hp: int = -1`，死亡时设为 `ceil(base_hp / 12)`（小怪 1~2 下）。

  按伤害字段判断会漏掉一半攻击技。
- `_strike_corpse()`：不判命中、不走伤害公式，每下扣 1 点耐久；
  归零则 `remove_at` + `_relayout()`，后面的人整体前移一格。
- `_pick_target`（AI）：优先活人，只在没有活人可打时才清残骸。
- 事件 `corpse_hit` / `corpse_destroyed`；界面写日志 + 飘字，
  并把该 uid 从 `_order_ids` 里摘掉。

界面：残骸头顶写「残骸 N」（紫色）—— 不写的话玩家不知道打一下还在、打两下才清。

**验收坑**：`--start --battle` 会 start 两次战斗（队列里一场 + `_boot_into_battle` 一场）。
`--corpse-demo` 第一版只在「第一次进玩家回合」时杀敌，杀到的是被顶掉的那一场，

## 追加：M74 房间叙事卡

用户反馈「点进房间就结束了，没有任何画面叙事」。原来 `_drain_queue` 是**瞬间批量结算**的：
点房间 → `resolve_curio()` → 日志多一行 → 人还站在原地。

做法：新状态 `S_ROOM` + 两页卡。
- **抵达页**：房间图标 + 「N 号房 · 奇物」+ 一句环境描写 + 「你看见了：<奇物名>」，
  按钮「走进去」。
- **结果页**：把结算结果摆出来，按钮「继续赶路」。

实现要点：
- 新增 `Expedition.peek_step()`：**只读**地看一眼下一步。`take_step()` 里带着
  光照消耗和走廊压力，取走再放回很脆。
- `_room_should_pause(step)`：**只拦房间里的奇物**。
  走廊步骤带 `corridor: true`，一路走一路停会把节奏拖死；
  战斗房由遭遇横幅负责。`_selftest` / `_auto` / `_skip_battles` 一律返回 false
  —— 自动化不会点按钮，停下来就是卡死。
- 结果文案**直接复用刚写进日志的那几行**（记 `_log.size()` 前后差），
  不另维护一套：日志说掉血、卡片说没事这种不一致迟早会出现。
  显示时用 `_strip_log_tag()` 去掉「【奇物】」前缀。
- 卡片底下先 `_draw_map()` 再盖 0.66 遮罩，然后 `_buttons.clear()` ——
  模态卡片只该有自己那颗按钮（不清的话地图片区的热区还活着）。
- 卡片高度按内容算（结果可能只有一行，也可能五六行）。

**没做的**：空房间（`K_EMPTY` 没有 step，压根不进 `_pending`）、
走廊陷阱/路障（不打断节奏，目前只有一行日志）。
这两块要补的话，方向是「不打断的横幅」而不是再弹一张要点的卡。

验证：`shots/m74_room.png`（抵达）、`m74_room_res.png`（结果）。
验收参数 `--room-demo` / `--room-demo=1`。规则层 1365 项全过。

## 追加：M84 战斗状态块挪到光照之后（「紫字像半透明」的真因）

用户问「为什么有些字体半透明，紫色的尤其」。查下来**跟 alpha 无关**：
`DdTheme.STAT = #9d7bd8`，alpha 一直是 1。

真因是**绘制顺序**：`_draw_unit`（含头顶状态块）画在 `_draw_lighting` **之前**，
而光照会铺一层全屏 `Color(0.012,0.011,0.013, dim)` + vignette。
敌方离我方火把远 → 那一带 dim 高 → 紫字被压掉一半亮度，看着就是半透明。

修法：把状态块从 `_draw_unit` 拆出来成 `_draw_unit_status()`，
在 `_draw_lighting()` **之后**遍历 `_slots` 再画一遍。
`_slots` 里补了 `cx/gy/top` 三个几何字段，绘制时不用重算立绘尺寸。
`_draw_unit` 里只保留「算 blk_top + 存 slot」，立绘/阴影/地环照旧。

**教训**：这类「看着像透明」的问题，先看是不是被上层画的东西压住了。
`_dci()`/光照层/遮罩都是同一类陷阱，查 alpha 只会白跑一遍。

验证：`shots/m84_battle.png`（敌方 DOT×1 紫字不再发灰）。规则层 1365 项全过。

## 追加：M92 属性文案补齐（16 种未映射）

`_buff_line()` 是饰品/怪癖共用的「一条属性 → 中文」翻译函数，末尾有兜底
`return "%s %+.0f"`。数据里 `stat_type` 共 **27 种**，只映射了 **11 种**，
剩下 16 种全落进兜底 —— 界面上直接露出英文键。

而且兜底**不乘 100**：`stun_chance` 的 amount 是 0.1，`%.0f` 写成「+0」，
看着像「零效果」，比露出英文更误导。

补齐 16 种（眩晕/流血/中毒/减益/位移/被暴击/受伤/受疗/施加压力/施加减压/
饥饿伤害/怪物奇袭/我方奇袭/决心经验/消除负面怪癖/无视潜行），
`ignore_stealth` 不带数字（它是开关）。

**教训**：这类「翻译表 + 兜底」的函数，兜底本身要为「未知键」设计得保守
（至少别把 0.1 写成 +0）。补映射时先用脚本比对「数据里出现过的键」和
「代码里 match 过的键」，比翻截图快。

验证：`shots/m92_shop.png`（六件饰品摘要全是中文且百分比正确）。规则层 1365 项全过。

## 追加：M93/M94「名册满员但战斗缺人」的表达问题

用户连问三轮才问准：**「队伍锁了之后，为什么名册不把这些人下掉？」**

查下来**逻辑没错、表达错了**：
- 名册用 `alive_ids()`（只判活着），出征用 `selectable_ids()`（还要 `busy_of() <= 0`）。
- 名册的定位是**全部雇到的人**，故意不下掉——人送去疗养院就"消失"的话，
  玩家第一反应是"我的人被吃了"。所以数据不动。
- 但**之前没有任何视觉区分**：城镇名册条上，忙的人和空闲的人长得一模一样，
  只有一个"活 5/4"。那个写法本身就在制造误会——活着 5、上限 4，
  读起来像"系统不让我带满"。

改动（都只碰表现层，规则零改动）：
- 城镇名册条：`活 5/4` → **`可出征 3/4`**（不足 4 时用 WARN 橙）；
  在建筑里的人**头像压暗 + 名字降一档**（`draw_texture_rect` 的 tint）。
- 名册页（公会式卡片）：忙的人名字 `TEXT → DIM`。
- 出发准备屏头部：`⚠ N 人在建筑里，本趟不能出征（可去马车补人）`。

**顺带纠正一个用户误解**：招新在**马车**不是酒馆
（马车：1000 金 + 4 纹章/人，每周 2 个职业候选；酒馆：减压 70/450 金；
修道院：减压 40/200 金——两档性价比，不是重复功能）。

验收参数 `--busy-demo=N`：把前 N 个活人标成「还剩 2 周」，
不造这个数据就截不到「忙 / 空闲」的视觉差异。

**方法论**：用户说"人不见了"时，先分清是**数据错**还是**表达错**。
这次三轮才钉住——第一轮我答"忙的人不能出征"（对但没回答他的疑问），
第二轮才意识到他在问"名册为什么不改"。

## 追加：M95 APK 重新打包 + release 签名

11-16 检查发现 `build/DarkestLike.apk` 停在 **11-06**，落后一周（M74~M94 全不在里面）。

配 release 签名的步骤（一次性）：
1. `android/` 建目录，用 AndroidTools 里的 JDK 生成密钥：
   `keytool -genkeypair -keystore android/darkest_release.keystore -alias darkest
    -keyalg RSA -keysize 2048 -validity 10000 -storepass <pwd> -keypass <pwd>`
2. `export_presets.cfg` 的 `[preset.0.options]` 加三行
   `keystore/release` / `keystore/release_user` / `keystore/release_password`。
3. `godot --headless --path . --export-release "Android"`。

**坑**：`--export-release` 在缺 keystore 时**会先把 APK 写坏再报错**
（`ERROR: Project export failed` 但文件已经被覆盖成半成品），
必须立刻用 `--export-debug` 重新导一次恢复。

**体积**：debug 127M / release 126M —— 几乎没差。素材占大头（7950 个资源），
脚本调试符号不是瓶颈。所以配 release 的意义主要是**性能**（无 GDScript 调试开销），
不是体积。

`export_presets.cfg` 本来就在 .gitignore 里（密码不会外泄），
但 `android/*.keystore` **没有**，已补规则 —— 密钥丢了就没法给已装的包做覆盖升级。

## 追加：M96 手机版 HUD 断层 —— EXPAND 改回 KEEP

真机截图：内容只画到屏幕 2/3 处，下面大片黑，底部按钮悬在留白里。
桌面引擎窗口正常（750×1334 比例一致，两种缩放模式看不出差别）。

**根因是两套坐标系**：
- `content_scale_aspect = EXPAND` + `content_scale_size = 750×1334`，
  在 482×1080（比例 0.446，比 0.562 瘦）的屏幕上，
  视口变成 **750×1680**（多出来的高度给界面用，这是当初选 EXPAND 的理由）。
- 但纵向布局没有跟着走：
  - 城镇画布 `_town_canvas_rect()` = `size.x * 1334 / 750` → 恒定 1334；
  - 地图屏用写死的 156 / 716 等 y 坐标 → 也停在 1334 附近；
  - 底部按钮用 `size.y - 44 - 204` → 8 跑到 1432。
- 中间空出 346 逻辑像素（≈222 屏幕像素）→ 看起来就是「断成两截」。

**修法**：`KEEP`。内容按 750×1334 完整显示并居中，比例不符的机型上下留边
——边比断层好。真正的「铺满无黑边」需要把所有纵向布局都改成跟 `size.y` 走
（画布、建筑槽位、地图网格、每个面板的 y），是一次大改，这次先不做。

**教训**：`content_scale_aspect` 换一个值，等于换了一整套坐标假设。
选 EXPAND 之前得先确认「所有写死的 y 都已经是自适应的」。
当时只考虑了「高度能多用一点是好事」，没检查布局有没有能力用。

## 追加：M99 桌面「手机显示模式」`--phone=WxH`

用户痛点是「每次都要导 APK 到手机才发现布局问题」。

Godot **没有** Unity 那种设备模拟器。原生只有：
- `display/window/size/window_width_override`（编辑器试跑窗口尺寸）
- Debug → Customize Run Instances

但这两样**管不到 `content_scale`**，而本项目的布局问题全是 content_scale 引起的
（M96 就是 EXPAND 把视口撑成 750×1680 造成的断层）。只改窗口大小复现不了。

做法：加 `--phone=482x1080`（省略尺寸时默认 482×1080 = 20:9），
走 `_apply_mobile_scale(win_size)` —— **和 Android 分支共用同一个函数**。
模拟必须和真机走同一段代码，否则桌面上看着好、手机上照样错。

```
godot --path . -- --phone=482x1080           # 20:9
godot --path . -- --phone=540x1168           # 19.5:9（iPhone 系）
godot --path . -- --phone=540x960            # 16:9
```

**注意**：`--shot` 截的是 viewport（750×1334），不含窗口黑边。
所以「留边多少」只能用眼睛看窗口，「布局对不对」才看截图。
想看含黑边的画面得走 `DisplayServer.screen_get_image()`，没做。

## 追加：M101「打完又来一组」的真相 + 战斗场次

用户反馈：一组怪打完马上又来一组，分不清是「同一场补位」还是「新的一场」。

查下来**两种都可能发生，且都不违背规则**：

1. **敌方召唤**（M12）。`battle.gd` 的三道闸：
   - `DEFAULT_SUMMON_LIMIT = 2`：同种怪同时最多 2 个；
   - `MAX_SUMMONED_PER_BATTLE = 4`：一场最多召 4 个（语义是「最多补一整支队伍」）；
   - 阵型 4 格兜底。
   所以「打死一个又补一个」最多补 4 次，不是无限增殖。
2. **连续两场遭遇**。地图是节点式的：走廊战斗 → 进房间又是战斗，
   两场之间没有走路过程，看起来就是「无缝接了一场」。
   `data/monsters.json` 里的 `wave_spawning` 是**原版空字段，代码从来没读过**
   —— 不存在「一波一波放」的机制。

**问题在表达，不在规则**：标题只写「第 N 轮」，召唤只在底部日志和飘字出现
（战斗中没人看底部）。玩家自然分不清。

修法：战斗标题加场次 —— `"第 %d 场 · 第 %d 轮 · 光照 ..."`
（`_battle_no`，进远征时清零，每次 `start_battle` +1）。
这样「第 1 场 → 第 2 场」是明确的；同一场里数量变化只能是召唤。

**没做**：召唤物在状态块上加「召」角标。`_battle.summoned` 里有 uid 集合，
接上去很简单，等用户确认要不要。

## 追加：M114 切后台丢配置（Android 生命周期）

2. 没有任何 `_notification` 处理 —— 切后台时 Godot 发

- `_notification()`：`APPLICATION_PAUSED` / `WM_CLOSE_REQUEST` / `WM_GO_BACK_REQUEST`

- 队伍屏进来先初始化名单。

**顺带修掉一个反复出现的坑**：`_activate` 和 `_activate_id` 是两套并行分发，
`--click=` 只走前者。新 id 只挂后者时「手点有效、脚本验收无效」——
这已经是第三次（M104 作弊、M114 名单）。给 `_activate` 末尾加了兜底转发。

第一次 `--click=dock:party,party_toggle:vestal`，读存档确认

- `_ready()` 末尾**自动**调用恢复，不再需要点按钮。

**验收参数的处理很关键**：`--shot` / `--click` / `--bld` / `--auto` 一律
**不自动恢复**，否则所有城镇截图都会变成地图。另外加了 `--resume-demo`
专门验收这条路径（否则自动恢复这条路根本截不到图）。

## 追加：战斗为什么不存（要回答的话术）

不是不能，是**当时判断成本高**，但这个判断值得推翻：

`Battle` 要存的东西：`party`/`enemies` 每个 `Combatant` 的
hp / stress / rank / dead / deaths_door / corpse_hp / stun_turns /
buffs / dots / cooldown，加上 `round_index`、行动序、`awaiting_input`、RNG。

**可行的降级方案**：只存「回合边界」——每回合结束时快照一次，
恢复从那个回合开头重打。最多丢一个回合的操作，而
`awaiting_input` 这类瞬时状态根本不用序列化。

比全量战斗序列化简单得多，也比「整场重打」体验好得多。

**教训**：上一轮我用「收益远小于复杂度」把这件事挡掉了。
但一场战斗 2~5 分钟，玩家正在关键时刻切出去回消息是常态——
这个判断站不住。用户一追问就露馅了。

## 追加：M118 战斗存档（回合边界）

做法：**不序列化 Battle 对象，而是记住「这一场是怎么开起来的」**
（`_active_step`），恢复时重走一遍 `exp.start_battle(step)` ——
开关、环境、受压倍率、技能/饰品装配全部自动完成，一段都不用抄。

存的只有单位的**可变状态**：hp / stress / dead / corpse_hp / at_deaths_door /
stun_turns / buffs / dots / statuses / affliction / virtue / rank。
基础值（攻击、闪避、抗性）不存 —— 由数据表重建，存了反而会脱节。

**存盘时机 = 每回合开头**（`_begin_player_turn()`）。这一条很关键：
只在回合边界存，「快照 = 这一回合开头」才成立，恢复后血量/buff 与快照一致，
不会出现「血恢复了但技能已经放掉」这种鬼状态。

**验收**：`--start --battle` → 存档里 `ui_state=2`、`round=1`、`units=8`
（4 英雄 + 4 敌人）→ `--resume-demo` 直接进战斗屏，双方血条、行动序、
技能面板、回合数全部正确。

## 追加：M119 Spine 2.1 自写运行时（试验成功）

**背景**：DD1 用 Spine **2.1.27**，Godot 生态的 spine 插件都是 3.8/4.x，
打不开。社区有 `brachna/SpineConverter2.1.27`（Python）能把 `.skel` 转 JSON，
**已跑通**。`.skel` 没加密，只是旧版二进制头看起来像乱码（字节里有 `2.1.27`）。

**数据实况**（十字军）：`idle` 49 骨骼 / 31 槽位 / 1.07 秒，
`tunic01~15` 十五段布料各有独立相位。`combat` 是**静态站姿**（战斗中不呼吸，
省性能）——所以「动作只有一帧」的错觉来自取帧方式，不是没动画。

**自写运行时**：`src/view/spine_mini.gd`，约 280 行。支持 region 附件 +
rotate/translate 时间轴（stepped / 线性）。不支持 mesh/IK/skin 切换。

**两个关键坑**：
1. **`rotate: true` 的图集切片**：atlas 里的 `size` 已经是旋转后的尺寸，
   源矩形照原样取，绘制时转 -90° 且显示宽高对调。早期版本交换了源矩形宽高 → 图撕裂。
2. **Y 轴翻转必须在绘制入口做一次**，不能逐骨骼翻 ——
   逐骨骼翻等于把父子链里所有旋转方向都反了，表现是「人形能拼出来但整体拧成一团」。
   正确做法：`_bone_world` 全程用 Spine 坐标（y 向上），
   出口处 `pos.y` 取负、角度取负、`scale.y` 取负（等价于套一层 `scale(1,-1)`）。

**试验结果**（`--spine-demo`）：
- 画面：完整十字军（头盔羽饰/面甲/胸甲白十字/肩甲/护腿/影子全对位）✓
- 动画：0.35s 与 0.9s 两帧确实不同（呼吸 + 布料）✓
- 性能：桌面 8 个单位同屏 **FPS 60** ✓（手机未测，GDScript 开销估计 ×3~5）

**成本**：每职业 14 个动作，每套 json 60KB + png 200KB。
15 职业全量约 55MB（比现在 203 张单帧 PNG 大）。

## 追加：M120 补贝塞尔 / 缩放 / mesh —— 主体成了，武器没成，性能掉了

**补上的**：
- **三次贝塞尔插值**（`_bezier_y`，牛顿迭代反解 t）。idle 里 45 个关键帧用它，
  丢掉就是「匀速平移」，看起来像木偶抽搐。
- `scale` 时间轴（4 条，呼吸时胸腔起伏）。
- **mesh 附件**（`_draw_mesh`，剑/披风那种变形网格）。

**结果分两半**：
- ✅ **人物主体完整**：头盔羽饰、面甲、肩甲、胸甲白十字、裙甲、护腿、靴子、
  影子全部对位，呼吸和布料摆动正常。
- ❌ **武器（剑）画错**：一块灰蓝色大平面横在腰上。剑在图集里是 160×450 的
  竖图，而 mesh 顶点范围是 238×145 的横条 —— 说明顶点已经沿骨骼 x 轴
  （剑长方向）排布，UV 的映射方向和我想的不一样。**没修好，别当已完成。**

**性能倒退**：mesh 支持前 8 单位 60 FPS，加了之后 **52 FPS**（桌面）。
`draw_polygon` 每帧 8 三角形 × 8 单位 = 64 次调用，GDScript 侧开销明显。
按手机 ×3~5 折算，真机大概 20~35 帧 —— **这条路的技术风险比预估大**。

要救有几条路：`RenderingServer` 直接提交（绕开 CanvasItem）、
把 mesh 烘成 Mesh 资源缓存复用、或者只在「待机呼吸」用 Spine
（1 个 mesh、开销小），攻击仍用静态图。

## 追加：M121 离线烘焙管线跑通（30/32 帧坏了 1 块）

用 **Godot 自己烘焙**（`--bake-spine`），不引 Java/libGDX：
逐帧 `queue_redraw` → `await RenderingServer.frame_post_draw` →
`get_viewport().get_texture().get_image().get_region()` → `save_png`。
32 帧 460×620 全部生成，管线**通了**。

**踩的坑**：`--bake-spine` 一开始完全没反应。原因是 **M47 主菜单**：
`_ready()` 在 `if not _skip_menu: ... return` 处就返回了，
后面所有初始化（包括烘焙、M117 自动恢复）都不执行。
**必须带 `--save=user://xxx.json` 跳过菜单** —— 和 MEMORY 里
「主菜单之后 `--shot=` 单独用截到的是菜单」是同一个坑。

**还没成的**：烘焙图里**腰上横着一块灰蓝色大平面** —— 就是那个 render 错的
mesh（剑）。`sword` region 在图集里是 160×450 竖图，而 mesh 顶点范围是
238×145 横条，说明顶点所在的坐标系和我的理解不一致（可能已含 attachment 的
旋转/缩放，或者 world 级联里 `spine` 父骨骼的旋转没生效）。
**这一块没修好，别当已完成。**

## 结论：Spine 这条路**已放弃**（M122，用户判定）

最终状态：**回到了原本的静态图 + 姿势切换**，试验代码已全部清理。

链条上每一环都试过，卡在最后一环：

| 环节 | 结果 |
|---|---|
| 找 `.skel` 解密/转换工具 | ✅ `brachna/SpineConverter2.1.27`（Python）能转 json |
| 解析骨骼 + 时间轴 | ✅ 贝塞尔/缩放/布料全对，人形能拼出来 |
| mesh 附件（剑/披风） | ❌ 顶点坐标系没吃透，剑变成腰上一块横布 |
| 性能 | ❌ 8 单位 52 FPS（桌面），手机 ×3~5 折算不够 |
| 离线烘焙 | ⚠️ 管线跑通，但把 mesh 的错误一起烘进去了 |

**判定依据**：造型已经扭曲，不是「差一点调优」的程度。硬撑下去的每一轮都在赌，
而收益只是「站着呼吸更顺滑」，不值。

**如果将来还想碰**，记住三条：
1. 别自写运行时。要么用正版 Spine 编辑器把 2.1 升到 4.x 再配 `spine-godot`
   插件（要钱、要转换验证），要么就别做。
2. **别在手机上实时算骨骼**。GDScript 扛不住，`draw_polygon` 尤其贵
   （8 单位 64 次/帧就从 60 掉到 52）。
3. 想改善「打起来硬」，最小成本是**补间**（攻击前冲 20px、命中后仰），
   30 行左右，不碰任何美术资源。

## 追加：M126 每技能等级（原版机制落地）

## 追加：M133 真机崩溃排查（内存侧）

   每次拼路径 + 查表。桌面看不出来，手机上（res:// 走 PCK）会叠在每帧上。

**验证**：VRAM 压缩后截图对比，**肉眼无明显损失**。

## 追加：M134 真正的元凶 —— `quit_on_go_back` 默认 true

用户猜「是不是切后台那个逻辑自己跳出去了」，方向对，但真凶不在那段逻辑里，
而在**从来没设过的一个引擎默认值**：

```gdscript
SceneTree.quit_on_go_back   # 默认 true
```

我们从没关过它。安卓上按返回键（含**全面屏的边缘滑动手势**）→
引擎发 `NOTIFICATION_WM_GO_BACK_REQUEST` → `_notification` 里只做了存档、
**没有阻止退出** → 引擎直接 quit → 玩家看到的是「它自己跳回桌面」。

**完全对得上用户的描述**：点边上的按钮时高概率触发（手势从边缘滑入），
不是崩溃、不是 OOM，是**应用被自己退掉了**。

**修法**：
1. `_ready()` 里 `get_tree().quit_on_go_back = false`
2. 自己接管 `_on_back_pressed()`：关浮层 → 子屏回城镇 → 城镇再按才退出
3. 地图/战斗里按返回只给提示（「撤退请走界面按钮」），**绝不直接退** ——
   一按就退的话，打了五分钟的仗说没就没

**教训**：这类「引擎默认值 + 平台特有输入」的问题，看代码根本看不出来，
因为代码里**什么都没写**。手机端上线前应该专门过一遍
`SceneTree` / `DisplayServer` 的平台相关默认值。

## 追加：M135 真正的崩溃 —— `_activate` 兜底写在 match 外面

用户截图是**桌面窗口**（不是手机）点「出发」直接崩，所以本地就能复现。
一跑就出来：

```
_activate_id (4153) ↔ _activate (3531)   ← 循环 1000+ 层
SCRIPT ERROR: Stack overflow
```

**根因**：`_activate(id)` 里的 `match id:` **每条分支都没有 `return`**，
而 M114 加的兜底 `_activate_id(id)` 写在 **match 外面**：

```gdscript
	match id:
		"prep_go": _launch_with_pack()    # 执行完**继续往下走**
		...
	_activate_id(id)                      # ← 兜底，谁都会撞进来
```

而 `_activate_id` 的 `else` 又回调 `_activate` → 无限递归。

**为什么「只有某些按钮崩」**：取决于那个 id 在哪一边有分支——
`_activate_id` 里有分支的（`cheat_res` / `dock:*`）走到兜底会被处理掉；
**只在 `_activate` 里有的**（`prep_go`）就会 `_activate` → `_activate_id`(else) →
`_activate` → … 栈爆。

**修法**：把兜底改成 `match` 的 `_:` 默认分支。匹配了就执行完拉倒，
没匹配才走兜底。

**注释里原来写着「上面每条分支都 return 了」——那句话是错的**，
当初就是这么以为才敢把兜底放外面。以后写兜底一律用 `match` 的 `_`。

验证：`prep_go` / `dock:party` / `bld:guild` / `cheat_res` / `roster_page` / `dock:gate`
六个入口全部 0 次栈溢出，出发能正常进地图。

## 追加：M137 刷奖励漏洞 —— `settle()` 从没清过 `expedition_run`

## 待确认：走廊遭遇战的流程

用户描述「进战斗房间前遇到遭遇战，表现像连续打了两次，希望打完回原房间休整再选路」。
`travel()` 的实现是：走廊事件先入 `_pending`，然后**立刻** `current_room = room_id`，
接着把房间的 step 也入队 —— 所以走廊战和房间战是连着跑完的。

**改法有歧义，先没动**：
- 方案 A：走廊战打完 → 人停在**目标房间门口**（`current_room` 已改），
  房间 step 等玩家点「进入」再触发
- 方案 B：走廊战打完 → **退回起点**（`current_room` 不变），当作「路上遇袭、原地休整」

用户原话是「回到原来的启示房间」，听起来像 B，但 DD1 原版是 A
（打完继续前进，到房间门口）。**需要确认再改**，否则返工。

「已打过的遭遇战不重复」这条**已经满足**：`travel` 里 `first_time` 判断
依据边的 `walked` 标记，重复走同一段走廊不会再触发事件。

## 追加：M144 走廊战与房间内容拆开（方案 A）

用户确认走**方案 A**：走廊遭遇战打完，人停在目标房间门口，
房间里的战斗/奇物等玩家**点脚下这一格**才触发。

**改 `expedition.travel()`**：
- 房间的 step **不再直接塞进 `_pending`**，先存进新字段 `room_pending_step`
- `visited` 也**不再提前标**（空房间除外 —— 空房间没内容可触发，直接算进去过）
- 新增 `has_pending_room()` / `enter_room()`：后者把 step 入队 + 标 visited + 计数

**改界面**：
- `_travel_to(room)`：如果 `room == current_room` 且有 `has_pending_room()` →
  调 `enter_room()` + `_drain_queue()`（而不是再走一次 `travel`，那会「走不到」）
- 地图底部提示：门口有内容时从「点地图上的绿框走过去」改成
  「**点脚下这一格 · 进去看看**」（金色 → 红色强调）

**存档**：`room_pending_step` 加进 `to_save_dict` / `from_save_dict`。

**效果**：走廊战 → 回地图（人站在门口、脚下这格有印章）→ 玩家可以点火把/休整
→ 点脚下进房间。两场战斗不再连成一串。

**教训**：`travel()` 把「走路」和「进门」两件事挤在一个函数里 ——
`current_room` 改完立刻把房间事件入队。要拆开就得先想清楚
「谁是玩家可见的最小决策单位」，否则改出来的流程会奇怪。

## 追加：M167 全技能分类验证（结论：没有错）

新增 `tests/test_skills.gd`，走 **`Battle.submit_choice()`** ——
界面点技能、点目标之后调的就是它（不是内部 `_apply_choice`），
所以验的是「玩家按下这个按钮，游戏会发生什么」。

**结果：1150 项断言全过。用户怀疑的「治疗被做成伤害」不成立。**
- 标了治疗的技能（`levels[].heal` 是数组 `[2,3]`）→ 提交后确实出 `heal` 事件
- 没标治疗的 → 不会出 `heal` 事件

**写这个测试踩了四个坑，全是同一个毛病——不看真实数据结构就写代码：**

1. **`a or b` 返回 bool**：`(lv or [{}])[0]` → `(bool)[0]`，
   报 「Invalid access to property or key '0' on a base object of type 'bool'」。
   正确写法是显式 `if ... else`。
2. ** лечения 字段是数组不是数字**：`heal: [2, 3]`。

3. **必须给 `decision_provider`**：`step_turn` 里
   `if actor.is_hero and decision_provider.is_valid() and not awaiting_input`

   105 个技能全被跳过。
4. **别猜目标**：`targets[0]` 可能是**尸体**（前面的英雄先打死了），
   提交后只出 `corpse_hit`，看起来像「技能没生效」；`miss` 也一样是正常没打中。
   要用引擎给的合法目标，再从中挑 `not dead` 的。

**另外**：轮到**别的英雄**时不能直接 `step_turn()` 跳过他 ——
他的回合会被当成 pass 空过，行动序一轮只走一遍，于是永远轮不到目标角色。
要替他提交一个合法技能，把这一轮推过去。

## 追加：M178 「装了 4 个、战斗只出 2 张卡」的真正原因

**不是技能丢了，是卡片放不下，被 `break` 静默丢掉。**

```gdscript
var avail_h = r.size.y - 66 - 12      // 战斗底部面板 ~180 高 → avail_h ≈ 102
var bh = clampf((avail_h - gap) * 0.5, 80.0, 132.0)   // ← 下限 80
...
if br.position.y + br.size.y > r.end.y - 12.0:
    break                              // ← 两行 80+10+80 = 170 > 102，第二行整行消失
```

M164 把技能卡从 4 列改成 2 列时，**只改了列数、没算行数够不够**。
4 个技能要 2 行，而面板只放得下 1 行 —— 于是永远只显示 2 张，**且不报错**。

**修**：`bh` 下限 80 → **44**，卡内文字基线跟着压（名字 30→24、摘要 54→44），
图标 `minf(46, bh - 8)` 别撑破卡面。

**教训**：改布局的「列数」时，要回到调用方确认**行数在可用高度里放得下**。
`break` 这种防御性写法会把「放不下」变成「静默少显示」，比报错更难发现。

**顺带**：「战地医术 治疗 1-1」不是 bug —— `battlefield_medicine` 的
`levels[0].heal` 就是 `[1, 1]`，等级 0 的数值本来就低。
（我之前看到 `[2,3]` 的是 `crusader/battle_heal`，不同技能不同等级。）

## 追加：M180 补给面板「透出地图」

**看起来像面板半透明，其实是画序压反了。**

- `_map_layer` 是 `add_child` 出来的**子节点** —— 子节点**永远画在父节点之上**
- 补给面板是在 **self 上** `draw_rect` 的（`_draw_supply_panel`）
- 于是面板的实心底色 `#161920` 画完后，`_map_layer` 的房间图标和走廊金线**又盖上来**

**修**：和 `S_ROOM` 同一套做法 —— 面板打开时 `_map_layer.hide()`。

```gdscript
if _state == S_MAP:
    if _supply_open:
        _map_layer.hide()
    else:
        _map_layer.show()
```

**记这条的原因**：这个工程的 `_map_layer` 是子节点，凡是「要盖住地图」的新面板
（对话、确认框、结算）都得走这条隐藏逻辑，不能只靠「背景不透明」。
源码里 M80 的注释已经写过「子节点的层级是固定的（永远在 self 之上）」，
但补给面板是后来加的，没接这条规则。

## 追加：M188 「随手吃口粮」把「休整」架空了

用户发现两个机制对不上：休整耗 2 份口粮、每趟只能 1 次；
但补给面板里 1 份口粮就能 +12%，**可以一直点**。

**数值对比**：
| 动作 | 代价 | 效果 | 风险 | 次数 |
|---|---|---|---|---|
| 休整 | 2 口粮 | +30~35% + 压力-40 + 光+60 + 救死门 | **33% 被偷袭** | 每趟 1 次 |
| 随手吃 | 1 口粮 | +12% | **无** | **无限** |

「随手吃」是 M154 加补给面板时顺手做的便利功能，**和原版不一样**：
DD1 的口粮只能在营地吃。

**后果**：玩家只要一直点吃口粮，就能无风险把血补满，休整彻底没意义；
而休整那个「33% 偷袭」的风险设计也跟着作废。

**修**：`exp.food_room_uses` 计数，**每间房只能吃一次**，换房间重置（`enter_room`）。
超了提示「这间房已经吃过一次了 —— 还想补就用「休整」」。

**存档往返**：`to_save_dict` / `from_save_dict` 两边都加了 ——
新字段只存不读，读档后会变成「这间房还能吃」（其实已经吃过了）。

**踩坑**：第一次把 `food_room_uses` 插进了 `supply_pack()`，
那是「出发带什么」的快照，不是存档 —— 名字看着像，位置差很远。
