## M15 饰品（完成）

**定性**：M13 最后一块「只计数不落地」。`loot_trinkets += agg["trinkets"].size()`
——件数进了结算屏，东西没进游戏。这期把它接成「仓库 + 每人 2 格 + 战斗生效」。

**数据闭合度**：490 件 / 1964 条 buff 引用 / 943 个不同 buff / **缺失 0 / 未知规则 0**。
可掉落 196 件（10 档稀有度），294 件 kickstarter 从不被任何表引用（保留这个筛选，
别让赞助者礼品从普通宝箱开出来）。

**必须先记住的四件事**

1. **抽卡表只写稀有度**（`{"type":"trinket","data":{"rarity":"very_common"}}`），
   不写 id。解析必须用**派生 rng**（`LootTables._derive_seed`，只读 `draw_count`
   当盐）——主序列多抽一次，M13 量到的全部掉落基线作废。验证：M14 与 M15 默认
   基线逐位一致，连 4903.125 这个金币小数都没动。

2. **仓库与装备是两个容器，不能合成一个列表**。两个理由同时成立：
   ① 装备中的件不占仓库格，合成后「仓库满了但人身上还能戴」表达不出来；
   ② `limit`（同名上限）要按总量判，只看仓库会让「仓库两件+身上两件」绕过 limit=3。
   为此有 `owned_trinket_ids()`。

3. **limit 分布**：1 → 330 件、0 → 159 件、3 → 1 件（`dd_trinket`）。
   我起先以为「稀有件应该唯一」，测试写完才发现 `swift_cloak` 的 limit 是 0。
   两派都大量存在，别凭印象定。

4. **饰品没有显示名数据**。`trinkets.json` 字段只有 buffs / hero_class_requirements /
   id / limit / origin_dungeon / price / rarity，`_raw/all_records.json` 里也没有
   localization。原游戏的饰品名没被抽出来。做法：按 id 词根拼
   （216 个词根，可掉落 196 件覆盖 100%），认不出的整件回退英文，
   不做半中半英。`DdTheme.trinket_name_coverage()` 供断言。

**重构**：规则判定抽成 `src/core/buff_rules.gd`，`QuirkLib.rule_active` 改为转发。
饰品多 6 种规则：`in_rank`(197) / `at_deaths_door`(56) / `attacking_monster_type`(22) /
`actorStatus`(22) / `skill`(3) / `monsterSize`(1)。
`in_rank` 的 `rule_data.float` 只有 0 和 3 两种值，buff id 自带 `_FRONT`/`_BACKRANK`
后缀 → 确认是 0 基站位号，不是掩码。猜错 197 条会全错位且不报错。
重构后 713 项旧断言一条没变，这是抽对了的唯一证据。

**Combatant 第三条通道**：`_trinket_active`，与 `_quirk_active` 并列而非合并
（卸饰品不该刷掉怪癖，反之亦然）。注入顺序写死：`hp = base_hp` → `set_quirks`
→ `set_trinkets`（两者都可能乘 base_hp，顺序换了血量舍入会漂）。
`filter_active` 加 `skip_max_hp` 参数，注入时一次性乘并同比例缩放血量。

**落地率 82.7%**（1625/1964）。312 条无承载（hp_heal_percent / resolve_check_percent /
stun_chance / damage_received_percent / activity_side_effect_chance 等），
27 条规则不可判（in_camp 38 条为主）。

**对照实验（40 趟 short/Lv3）——这期最干净的一组**
| 组 | 完成 | 压迫 | 死亡 | 末血 | 末压 |

| 完全不戴 | 0.875 | 0.698 | 0.72 | 0.603 | 76.2 |
| 戴了但关掉 | 0.875 | 0.698 | 0.72 | 0.603 | 76.2 |
| 戴了且生效 | 0.950 | 0.492 | 0.42 | 0.653 | 63.3 |

第二行与第一行**逐位相同**，证明注入路径本身不改任何东西，差异全来自 buff。
比「和上一期比」更硬。

**一个反直觉结果要记住**：「我拍的『好』件」组（0.900）不如随机组（0.950）。
原因是判据只认速度/暴击/命中/伤害倍率，漏了随机池里一批「减受压」的件
（它们贡献了 13 点末压差）。**我拍的好坏 ≠ 数据里的强弱**。
所以那张表只能说明方向能分开，不能说明最优配置。可信的是开关 A/B。

**界面**：城镇右下「饰品仓库 N/16」→ 独立状态 S_TRINKET，
左 4×4 仓库格 + 右四人各 2 槽，点仓库件选中（金框）再点空槽装上。
交互只做 `_toggle_slot()` 一个入口（装/卸/换走同一段），两套代码分叉是
「装得上卸不下来」的常见来源。结算屏报「饰品 ×N」，进不去仓库时报
「另有 N 件没能带走」——只报掉了 2 件而实际一件没进，玩家会以为存档坏了。

**留了个不好看的事实**：`trinkets.base.starting` 是空数组，**开局一件都没有**；
自然掉落中图 1.12 件/趟（200 趟模拟）、短图约 0.6 件/趟。打两趟才见一件。
和 M14 怪癖一样：机制完整，出现率是内容决策，不是代码问题。

**验证**：791 项断言全绿（+78）。三档 SELFTEST PASS（中图实掉 accuracy_stone）。
bench 新增 `--no-trinket` / `--trinkets=N` / `--trinket-pick=mix|best|worst`。
文档 M15_TRINKETS.md 十节。未 commit、未 push。

## M16 城镇经济（完成）

**定性**：M15 的两个洞——金币只有升级一个出口；`trinkets.json` 的 `price`、
`inventory.json` 的 `purchase_gold_value` / `sell_gold_value` 三组数据读进来却没用。
这期把它们接成「出发前买补给 + 城镇商店买饰品 + 卖仓库里的件」。

**价格来源（一个都不许拍）**
- 补给买/卖/上限：全部来自 inventory.json。10 条定义、8 种可交易
  （firewood / dog_treats 买卖价都是 0，不是商品）+ 食物 = 9 种在售。
- 饰品买价：trinkets.json 的 `price`，按稀有度规整成 5000/7500/10000/15000/25000/50000。
  15 件 `price ≤ 1` 是占位价（trophy/crow/darkest_dungeon），`can_stock()` 挡掉。
- 饰品卖价：**数据里没有**。取买价的 10%（跟随补给的比例），常量 `Shop.SELL_RATIO`。

**顺手修掉的口径分裂（M13 遗留，真 bug）**
火把同时存在于 `supplies["torch"]`（1 支）和 `torch` 字段（4 支）：
点灯读字段、奇物交互读字典 → 同一个数字两个值。口粮反过来：
奇物给的食物进 `supplies["food"]`，饥饿检测读 `food` 字段 → **给的食物吃不到**。
修法：`supply_count/add_supply/take_supply` 三入口统一，torch/food/shovel 走独立
字段；`DEFAULT_SUPPLY_PACK` 去掉 torch。改完默认携带仍 14 件、baseline 逐位一致。

**设计选择：补给不进元层仓库**。DD1 的补给是「这趟带下去的」，回城不结余。
做成库存会多出一堆边界，换不来决策——真决策是「这趟带几根火把」，发生在出发前。
**保底包**（= M13 之前的硬编码默认）免费，钱不够也能出发，否则第一趟就卡死。
代价：前几趟白嫖补给。

**对照实验（40 趟 short/Lv3）—— 补给的真实价值**
| 补给 | 完成 | 压迫 | 死亡 | 末血 | 饥饿未喂 |
|---|---|---|---|---|---|
| 默认 4/4 | 0.875 | 0.698 | 0.72 | 0.603 | 0.23 |
| **无口粮** | **0.775** | **1.270** | **1.35** | **0.241** | **1.57** |
| 无火把 | 0.850 | 0.745 | 0.80 | 0.596 | 0.23 |
| 全精简 | 0.800 | 1.163 | 1.30 | 0.347 | 0.90 |
| 带满 8/8 | 0.875 | 0.698 | 0.72 | 0.656 | 0.00 |

**三条要记住的结论**
1. 口粮是绝对主力（死亡 +88%）；火把是小头（短图上末光照 57.6，离阈值 50 不远）。
2. **带满与默认逐位相同**（完成/压迫/死亡/轮），唯一差别是末血 +0.053 = 那 0.23 次未喂。
   **补给是保险不是增益**：补齐到默认有回报，超过默认没有。
3. 带满成本 7300 金 = 一趟 short/Lv1 收入（3498）的 209%，买不起一趟
   → 补给和饰品抢同一笔钱，这是有意的。

**界面**：点难度卡不再直接出发，改成进「出发准备」（左补给清单 －数量＋、
右难度合计余额）；城镇右下并排「饰品 N/16」「商店」两个入口。
商店：上排 6 格货架（点买），下排仓库（点卖）。**买走的格子留空不往前挤**
——货架是格子不是列表，挤上去玩家会看到自己没买的件换位置。

**买入顺序写死：先判容量再扣钱**。反过来会出「钱扣了但仓库满了」，玩家只会觉得坏了。

**验证**：863 项断言全绿（+72）。三档 SELFTEST PASS。baseline 与 M15 逐位一致
（0.875/0.698/0.72/32.775/0.603/76.2443/4903.125）。
bench 新增 `--pack=base|lean|rich|nofood|notorch`。文档 M16_TOWN_ECONOMY.md 九节。
未 commit、未 push。

**未做**：补给不能卖（买多就浪费）；`reroll_shop()` 有实现但界面没接（换货本来就免费）；
`origin_dungeon` 没接（会让商店按地牢出货，但会改 M13 的掉落梯度）；传家宝不能买饰品。

## M17 内容密度（完成）

**定性**：三期文档都在写「机制完整但看不见」。这期只改一个数字，
但先把「这数字到底是什么」查清楚了——M13 已经误解过一次。

**语义确认：`hallway_curio` 是百分比，不是数量**
证据：值 9/14/19 只随 size 变，与房间数（7-19）、走廊数（8-20）都不对应；
short 有 8 条走廊却写 9，若当数量会超过走廊数。原始 `.darkest`
（`scripts/map_generator.darkest`）里同组 `hallway_battle [2,4]` 是数量区间，
而 curio 是单值——它是「走廊有奇物的概率」。

**实测（改前）**：走廊奇物 short 0.57 / medium 1.30 / long 2.53 个/图，
填充率 11%/15%/21%（与 9%/14%/19% 吻合，代码没错，数字本身就这么小）。
加房间守卫宝箱（0.6/1.6/2.6）= 一趟短图只有 1.17 个互动点。

**上限被 M7 结构锁死**：四类内容先按 `cap = 走廊×0.55` 分配，奇物只填空走廊。
空走廊 short 5 / medium 8.9 / long 12 —— 100% 填充也只有这么多。
提高上限必须改「一条走廊一件事」，会重排 M7 全部基线，本期不动。

**实现：`max(数据值, 配置下限)`，不是硬覆盖**
硬覆盖的问题：数据将来调高会被按回配置值，且**没人会发现**。
配置放 `expedition.json` **顶层**（不是 preset）——出现率不是难度旋钮，
放 preset 会让「换难度顺手改了内容密度」，两个变量再也分不开。
`DdDb._read_curio_rate()` 只从 res://data 读，**不走 balance 包**
（和 loot/curios 同类，是规则数据不是平衡旋钮）。

**实测（改后）**：走廊奇物 3.07 / 5.67 / 7.87（×5.4 / ×4.4 / ×3.1），
短图合计 3.67 个互动点。

**但只解决一半 —— 这期最重要的发现**
真实远征（地图模式+真实战斗，medium Lv3，10 趟）：
奇物 1.40 个/趟、步数 5.5、金币 2977、饰品 1.00 件/趟。
**图上 6.67 个奇物，玩家只遇到 1.40 个（命中率 21%）**，因为只走 5.5 步
（图有 14 房间 19 走廊 = 33 个节点）。有样本只走 2 步。
→ 密度从「几乎没有」变成「每趟一次多一点」，是改善不是解决。
要真解决得让玩家走更远，那是难度/撤退策略问题。

**饰品掉落不动**：实测 1.00 件/趟，接近原版（0.5-1），商店已有货架，
再提会让商店失去意义。A 表 T 权重 8/174 保持。

**顺手修两个自检误判（都是判据错，不是游戏错）**
1. `loot_ok = gold>0 or end_reason=="wipe"` → 「撤退且零收入」被误判。
   改成 `battles>0` 又不成立：17 只怪的 loot 就是 NONE，赢了也不掉钱。
   最终：**这一项不判 PASS，只报数**（收入由遭遇决定，同位移/召唤）。
2. `while guard < 600` 预算不够：奇物占轮次 + 战斗变长 → 停在 S_BATTLE
   （表现像「没走到结算屏」）。提到 1200，medium 连跑 12 次全 PASS。

**新增自检栏**：`SELFTEST 内容 奇物=N 陷阱=N 障碍=N 饥饿=N 房间=N 步数=N`
——「图上有多少」vs「这趟遇到多少」是两个数，之前没有这一栏无法区分。

**验证**：872 项断言全绿（+9）。三档 SELFTEST PASS。
bench 基线逐位一致（线性路线没有走廊概念，作用域干净）。
配置 `expedition.json` 加 `curio_rate.hallway_pct_min = 60`。
文档 M17_CONTENT_DENSITY.md 十节。未 commit、未 push。

## M18 远征节奏（完成）

**定性**：上一期建议「查清为什么只走 5.5 步」。查下来第一个发现是我自己量错了。

**方法论修正：自检 ≠ 玩家**
`_selftest_move()` 只走「离出口更近」的邻居（BFS 最短路径）。medium 图 33 个节点，
最短路只有 3-5 步 → 「5.5 步」是这个策略的结果，M17 把它当玩家行为是错的。
加了 `--explore`（优先走没去过且不后退的邻居）后：步数 4.88→5.25（+7.6%）、
奇物 1.38→1.62（+17%）。**几乎没有可绕的**——地图是几个大环+一堆死胡同触须，
不是可规划的支线网络。这是 M7 的地图生成决定的。

**真问题：队伍活不下来**
自检 medium Lv3 八趟全部 wipe，5 趟只打 1-2 场。而 bench 同难度完成率 0.600。
唯一差异是队伍：bench 用 crusader，campaign 名册用 man_at_arms（M10 换的）。

**根因：M10 换人的债从没校准**
bench 30 趟只换队伍：crusader 0.600 / man_at_arms **0.367**，死亡 1.83→2.73。
数值：man_at_arms 伤害 [5,9] vs crusader [6,12]（均值低 22%）、hp 31 vs 33，
换来只有 +2 速度。M10 的「守护/反击要能演示」成立，但代价只记了一句「−0.216」，
从没回调难度。

**解法：演示需求和强度需求分开**
名册扩到 5 人、出战仍 4 人由玩家选。顺序有意排成
`crusader, highwayman, vestal, plague_doctor, man_at_arms` —— 前 4 个正好等于
bench 默认队伍（历史基线可比），man_at_arms 排第五随时换上场。
准备屏加「出战 N/4」卡片：点一下切换、至少留 1 人、满员时挤掉最后加入的。
`_start_expedition` **硬夹 4 人**（战斗层 rank 只有 0-3，第 5 人会被目标掩码漏掉）。

效果：complete 从 0/8 到 1/6，平均金币 1334→1981（+48%），步数上限 10→11。

**顺带查出一个真 bug：228 回合的死斗**
`Battle.MAX_ROUNDS = 40` 只用在同步驱动 `run_until_over()` 的循环上限，
**逐步驱动（界面/自检走的这条）完全没有上限**。`is_over()` 只看一方死光，
双方互相打不死时 `begin_round()` 无限加轮。
M18 自检撞上过 `战斗轮=228`（诊断行打出来的）。
修：`begin_round` 判 `round_index >= MAX_ROUNDS` → `stalemate=true`，
`is_over` 含它、`winner()` 返回 "none"；结算按脱离接触处理（无掉落 + 全队加压 20）。
不加惩罚的话可以故意拖回合白跑。修完 medium 连跑 10 次全 PASS。

**新增诊断**：自检 FAIL 时打印 `循环用了 X/1200 轮 state=? 战斗轮=? 待输入=? 待结算=?`
——预算用完 vs 卡在不推进的状态是两种病，不加这个只能猜。

**测试**：test_campaign 的「开局 4 人」改成按配置读（M13 硬编码 100 金同款教训）；
test_battle 加 `run_stalemate`（推到上限、不误判、僵持后不再推进）。

**验证**：884 项断言全绿（+11）。三档 SELFTEST PASS。bench 基线逐位一致。
文档 M18_EXPEDITION_PACE.md 七节。M17 §6 加了修正注记。未 commit、未 push。

**未解决**：medium Lv3 对 0 阶队伍仍偏难（6 趟 5 团灭，有趟 2 场仗全灭）。
符合「先打短图攒装备」的设计，但「2 场打死 4 人」值得单开一期查 Lv3 遭遇池。

## M18 补记：名册 ≠ 队伍（体验反馈）

主人上手十分钟报障：「队伍 5 个人，战斗里只有 1 个人。原版是 4 人队，你改成 5 个不对。」

**诊断：战斗层没坏。** `PARTY_MAX = 4`、rank 0–3，从 M0 起没动过。
5 是**名册**（roster）人数，可以 5 选 4 上场，跟原版「名册远大于队伍」一致。

真实原因两条叠在一起：
1. 城镇画 5 张英雄卡，看起来就是 5 人队（`campaign.hero_ids()` 包含死者，全画）。
2. 那份存档连打 10 趟、5 人**全部阵亡**（`alive=false`，deaths 4/4/4/4/1），
   只剩刚免费征召的 1 个新兵，而**准备屏允许 1 人出发** → 1v4 必死。

**修复（全在表现层，规则层零改动）**
- 城镇名册区加「名册 N 人 · 存活 N · 每次出战最多 4 人」；全灭时红字引导去免费征召
- 城镇难度卡「队伍 5 人」→「可出战 min(存活,4) 人」
- 准备屏出战卡加 `✓` / `＋` 前缀（光靠 2px 边框分不清选中态）
- 准备屏出发按钮：不满 4 人禁用；**能招人时禁止降门槛**，只有真招不到才允许少人出发

**踩的坑：门槛写反了。** 第一版写 `need = min(4, 名册活人)`，本意防死锁，
结果把「1 人队出发」这条死路**合法化**了（自检也不报错，因为它合法）。
正确做法：能招就必须先招满，降门槛只留给「真的一个人都招不到」。

**新增工具**：`--prep` 启动参数（直接停在准备屏），配 `--shot` 可截图验证。

## M19 技能组（7 选 4）

**起点**：`heroes.json` 的 `skill_selection`（每人最多 4 个，憎恶 7 个）
从 M0 就抽好了，`grep -r skill_selection src/` 的结果是 **无匹配**。
十九期以来英雄 7 个技能全开，原版最核心的 build 取舍根本不存在。

**改了三层**
- 新增 `src/core/skill_loadout.gd`（`class_name SkillLoadout`）：`default_for` / `sanitize` /
  `max_slots`。抽共用件的理由同 M15 的 BuffRules——元层和 bench 两个调用方。
- 三层默认值全部留「空 = 全装」的退路（Combatant.selected / Battle.loadout_by_id /
  Expedition.hero_loadout），所以 **bench 不加参数时逐位不变**，`--skills=loadout` 才切新路径。
- 城镇加公会入口（`S_GUILD`）+ 技能选择屏；新增 `--guild` 启动参数可截图。

**默认组是本项目补的**：原版没有「默认装哪 4 个」的表（硬编码在逻辑里，抽不出来）。
`campaign.json` 的 `default_skills` 写明这点，并配了 5 个职业的合理组合。

**对照（30 趟，同路线只切开关）**
| 规格 | all(7) | loadout(4) |
|---|---|---|
| short Lv1 | 0.967 | 0.900 |
| medium Lv3 | 0.600 | 0.400 |

第一版默认组只有 0.333，差在**没带减压**（压迫 2.407）；把 crusader 的 bulwark 换成
`inspiring_cry`、vestal 带 `gods_illumination` 后到 0.400。

**关键结论：bench 的 AI 不会组合技能。** 它逐动作挑当前分最高的，没有「攒控场、
先奶再打」的概念。技能池 7→4 对它是「少 3 个选项」，对玩家是「必须取舍」。
所以 0.400 是 AI 的下限，不是玩家的上限——以后拿 bench 数字代表玩家体验前，
得先做这种 AI。

**踩坑**：`launch`/`target` 在 JSON 里是 **int 或 null**，`target` 还带 `@`（己方）、
`~`（全体）前缀。第一版 `str()` 后逐字符拆，`null` 变成 `<null>`，界面显示
「打 `<、11、1、1、> 位`」。另外「鼓舞呐喊」有 heal[1,1] 被标成「治疗」，
实际是减压——先认 effect 里的 `stress` 再认 heal。

**验证**：909 项断言全绿（+25）；三档 SELFTEST PASS；`shots/m19_guild.png`。

## M20 区域与首领

**起点**：`expedition_scene.gd:26` 写死 `_dungeon = "weald"`，另外三个区域的遭遇表、

撤退是主动放弃，这个是「到了地方没打下来」）。

**数据**：海湾 medium Lv1 首领任务 10 趟——打到 0.900、击杀 0.400、团灭 0.500。

## M21 可读性：名字与出发情报

**踩坑**：`pretty()` 在场景里有 26 处，长得几乎一样但参数类型不同

**测试抓出的漏网**：全量扫描 encounter 表发现 3 个怪没名字——`shambler` /

## M22 城镇建筑

## M23 周次循环

**起点**：`settle` 里早就写着「DD1 的商店是按周刷新的，这里按趟」——
「趟」被当成了时间单位。只有「打完一趟回城」时够用，一旦有了建筑就不够了：
建筑的核心语义是「占用人」，没有时间轴这个代价无法表达。

**一趟 = 一周**：新增 `Campaign.week`，`settle` 末尾调 `advance_week()`
（周次 +1、忙的人少忙一周、按配置做压力衰减、刷商店）。

**建筑占周（核心）**：疗养院/修道院/酒馆成功后写 `busy = 1`——
效果立即生效，代价是这一周不能出征。自然产生了原版那个「一周只能办一件事」
的限制（M22 时能一口气治完病再减压再清怪癖）。
`selectable_ids()` 收窄成「活着且不忙」，所以备战屏根本列不出忙人。

**存档兼容**：`week` 旧档按 `expeditions + 1` 补（不从 1 重来——
打了 10 趟的档显示「第 1 周」是错的，不只是缺的）；`busy` 缺省 0。

**压力衰减是旋钮，默认关**：`weekly_stress_relief` 缺省 0。M16 量过
「无口粮死亡 0.72→1.35」，续航全靠回城那 40 点撑着，动它要重跑整条基线。

**踩坑**：新机制一上线 M22 的测试立刻红三条（治完病不能再清怪癖）。
不是测试写错，是行为真的变了——改测试为「推进一周再清」，
顺手把新机制钉成断言（忙人不在 selectable、busy 递减、周次随档走）。

**验证**：967 项断言全绿（+9）；两区域 SELFTEST PASS；
截图 `shots/m23_town.png`（城镇 · 第 7 周、卡片「忙 1 周」）、
`m23_sanitarium.png`（右上角「这周还有事（剩 1 周）」、按钮变灰）。
文档 `M23_WEEKS.md` 九节；M22 文档加了补记。未 commit、未 push。

## M24 主动过一周

**起点**：M23 的 `advance_week()` 只在 `settle` 里被调用——时间只能「打完一趟顺便过」。
于是「建筑占人」只成立一半：派去疗养院的人不打仗就永远不结束。
更荒唐的是「想减压就得再打一趟，而那趟又加压」。

**两个必须先解决的问题**
1. **压力不恢复 = 休整纯亏**。M23 把 `weekly_stress_relief` 默认 0（怕动续航基线）。
   这期开成 **10 点/周**（约为回城 40 的四分之一），八条路线形成梯度：
   打一趟 −40（有风险）/ 酒馆 −70（450 金）/ 修道院 −40（200 金）/ **休整 −10（50 金，不占人）**。
   **bench 不受影响**：bench_expedition 走 Expedition 不走 Campaign，批量数字逐位不变。
2. **不收钱 = 免费刷商店**。`advance_week` 会 refresh_shop，白嫖就能无限刷货架。
   原版靠「不出发难度上升」堵，我们没有那条，只能用钱堵：**50 金/周**。

**实现**：`Campaign.idle_week()`（扣钱 → advance_week）；**商店刷新从 settle 移进
advance_week**——时间推进的副作用只有一个来源，以后加第三种推进方式不会漏。
UI：城镇「出发」行右侧加「休整一周（50 金）」，和区域选择同排（同一层的选择）；
副标题改成「远征 N 趟 · 每周自然恢复 10 压力」（不写这句玩家不知道那 50 金买到什么）。

**配置**：`campaign.json` 新增 `town_cycle` 段（`weekly_stress_relief` / `idle_cost`），
note 里写明「为什么不收钱不行」——半年后看这配置的人第一反应一定是想删掉那 50 金。

**验证**：976 项断言全绿（+9：成本>0、恢复>0、钱不够不推进时间、休整让忙人减一周、
压力按配置恢复）；两区域 SELFTEST PASS；截图 `shots/m24_town.png`。
文档 `M24_IDLE_WEEK.md` 七节。未 commit、未 push。

**下一步候选**：难度随时间上升（原版时间压力的另一半）、怪物行为情报、
建筑「下周生效」队列、休整期间的随机事件。

## M25 决心等级（主人问「原版靠什么爬难度」之后做的）

**主人的问题**：原版靠什么爬难度。查证后答案是**不是时间膨胀**，而是三件事：
① 只有三档离散台阶（1/3/5），同档内数值固定；② **双向等级锁**——英雄比任务
高 2 级或以上拒绝参战，低 N 级可进但进本 +20N 压力、受压 +25%N；
③ 任务板按名册等级加权随机，但永远保底一张学徒本。周数本身不加难度。

**核心洞察**：我们缺的不是「难度」，是「人」这根轴。
`grep resolve src/core/` 在 M25 前零匹配——装备阶是硬上限，有钱就能顶满然后
拿 4 阶打一辈子短途。「有装备这根轴，但装备不会拒绝去打低难度」。

**实现**：`Campaign` 加 `resolve`(1-6) + `xp`；`RESOLVE_XP=[0,0,5,6,8,8,11]`
（增量式，index=目标等级）；`QUEST_XP` 按 难度×尺寸（学徒 2/3/4/4、精英 2/4/6/8、
冠军 4/8/12/16，乘性关系）；`can_join` / `entry_stress` / `gear_cap(=resolve-1)`；
`recruit()` 重置等级与装备（**但不清怪癖**——只有 5 个固定 ID，清空会造出
「故意送死洗负面」的漏洞）；旧档无 resolve 时按 `gear+1` 反推（不从 1 重来）。
`Expedition.join_stress` 必须在 **setup 之前**赋值（state 在 setup 里建）。

**对照（bench 新增 `--resolve=N`，种子固定只切这一个开关）**：
medium Lv3 不模拟 0.350/0.650/2.480，`--resolve=3` **逐位相同**（等价性检验），
`--resolve=1`（+40 压力）掉到 0.250/0.750/2.985；short Lv1 不模拟与 `--resolve=1`
两组均 0.900/0.100/0.600。

**踩坑**：`gear_gate_reason` 两个数都写成 `gear+2`（界面出现「要 4 级才能穿 4 阶」，
人在 2 阶）；结算屏加两行后溢出卡片（行距 31→26、卡片 424→470、按钮 586→634）；
升级行 4 个名字约 430px 撑破 420px 栏宽（改「最多两个 + 等 N 人」）。

**验证**：1027 项断言全绿（+48）；三档 SELFTEST PASS；截图 `shots/m25_town.png`、
`m25_prep.png`（Lv5 老兵标「高出 2 级，不能带」）、`m25_smith.png`、`m25_result*.png`。
文档 `M25_RESOLVE.md` 八节。未 commit、未 push。

**下一步**：任务板按名册加权（补「向上推」的另一半，现在的锁只负责不让你往下走）、
受压 +25%/级（要单独一期带基线对照）、名册扩容（原版双线的前提）。

## M26 任务板

**起点**：M25 的锁只做到「不让你往下走」，但城镇那四张难度卡的等级是
`expedition_scene.gd` 里写死的常量（M0 起就没变过），玩家永远能挑低的那张。

**不能照抄原版的原因**：原版敢写死「永远保底一张学徒本」，是因为马车每周能补
1 级新人。我们只有 5 个固定 ID，全员 5 级时硬塞学徒本会得到 **4 张卡里 3 张
「够格 0 人 · 全都超级了」**。所以做了三处有意偏离（都写进代码注释和文档 §2）：
① 保底改成「名册最弱的人免罚打得动的最高档」；② 池子按「至少一人能进」筛而不是
纯加权随机；③ 尺寸固定绑在槽位上。

**规则**：`board_ceiling = 名册最高等级 + 1`（+1 是留「略微超纲」的选项，
高 1 级只吃 20 压力不是拒绝）；`board_level_pool` 只放有人能进的档；
`board_floor_level` = 最弱者的免罚档；`roll_board` **先定保底槽（位置随机），
再从「能凑够 4 人」的档里抽剩下三格**。

**关键教训**：第一版是「按权重抽 4 张 → 事后检查有没有学徒本 → 没有就改第一张」，
混编名册废卡率 **43%**。改成「先定保底槽再抽其余」后降到 **25%**（正好一张），
差别在于废卡有了身份：它不再是抽坏的，是留给新人的那个位置。

**数据（每档 300 周 × 4 张）**：全员 1/2/3/5 级 → 板子分别 100% L1 / 59·41 L1L3 /
100% L3 / 100% L5，废卡 0%；4×L5+1×L1 → 25/0/75，废卡 25%；2×L5+3×L3 → 0/25/75，
废卡 25%。

**踩坑**：① 上述「事后检查」写法；② `board_ceiling` 一开始没 +1，导致全员 Lv2
的池子只有 `[1]`，练到 2 级看不到任何新东西。

**验证**：1047 项断言全绿（+20：池子随名册变化、保底档抬升、混编三档齐全、
40 次重抽都有保底档、3 级名册不出 5 级本、废卡≤1、advance_week 会重抽、
存档逐槽保留、旧档自动补板子）；截图 `shots/m26_town_top.png`（全员 Lv5 四张全 5 级）、
`shots/m26_town_mix.png`（混编：三张 5 级 + 一张 1 级留给新人）。

## M27 名册扩容

**起点**：`_order` 从 M0 起只在 `setup_from_cfg` 里从配置抄一次，之后再没人往里加人。
`alive_ids` / `hero_ids` / `graveyard` / `_alive_count` 全走它，所以「名册」架构上
就等于「配置里那 5 个职业」。M25 的等级断层、M26 的废卡率都是这个死结的下游。

**实现**：`_order` 语义改为「已入册的职业，按加入先后」；新增 `known_heroes`
（场景从 `hero_ids()` 灌）同时兼任名册上限和野 id 过滤；`hireable_pool` /
`roll_recruit_candidates`（每周 2 个）/ `can_hire` / `hire`；`advance_week` 和
`new_game` 各调一次 roll；`to_dict/from_dict` 存取 `order` 和 `recruit_candidates`。

**最大的坑**：老 `from_dict` 是「以配置里的 5 人重建 roster」，名册超过 5 个时
**静默丢人**（存 8 个读回 5 个，丢的正好是花钱招来的）。新读法三步：
存档 order → 配置补齐 → 兜底循环（用 known_heroes 校验）。测试专门钉了
「招到 8 人存档读回、人数和顺序都一致」。

**语义**：`hire`（招新职业）和 `recruit`（复活死人）并存——原版死人不复活，
但我们的名册从 5 人起步，删掉复活会让老档里的死人永远消失。招新只收
1000 金币不收传家宝（传家宝稀缺，会让人不敢换阵容）。

**三处 UI 重排**：城镇名册 8 列×2 行（112 高，砍掉生命/护甲/闪避）、
准备屏 6 列×3 行（52 高，砍掉出征次数）、建筑屏名册 2 列×8 行（42 高，
第二行只留「病/负/忙」）。默认出战名单 `_party_for` 改成按「等级→装备」降序
取前 4，且准备屏列表用**同一个排序**（不一致会看到「勾全在最后一行」）。

**坑**：① 建筑屏 15×78=1170px 直接画出屏幕；② `draw_string` 的 `width`
是从 pos.x 向右量的，右对齐要把起点左移一个框宽，否则数字画到卡片外面。

**验证**：1071 项断言全绿（+24）；两区域 SELFTEST PASS；截图 `shots/m27_town.png`、
`m27_prep.png`、`m27_coach.png`、`m27_bld.png`。文档 `M27_ROSTER.md` 九节。
未 commit、未 push。

**下一步**：解雇（只能加不能减，满了就僵住）、受压 +25%/级、马车候选按阵容短板加权。

## M28 解雇

**起点**：M27 只做了 `hire`，没有 `dismiss`。名册满了之后新面孔永远招不进来，
练废的人也只能一直占位置。

**规则**：免费，等级和装备一起归零（原版语义：这个 ID 是「名册上的一个位置」，
不是某个具体英雄）。三条限制：**至少留 1 个活人**（防锁死——名册空 + 钱不够招人
= 存档走不动）、**忙人不能删**（他这周还在疗养院，钱怎么算）、死人可以删
（= 从墓园移除记录）。busy 检查放在 `can_dismiss` 而不是 `dismiss`，
让按钮直接灰掉——可点但报错玩家会以为是 bug。

**顺带修的 bug**：`roster_full()` 原来是 `_order.size() >= 15`，而 `_order` 含死人，
团灭过两轮的档会「名册 15、能出征 3 个、还招不进人」。改成按活人数算。

**UI**：马车分上下两半（上半招人 / 下半名册管理）；解雇**点两次**（自绘 UI 没弹窗，
第一次只上膛，换选别人会取消）；给 `_add_button` 加 `danger` 参数（警示色 2px 边 +
警示色文字）——第一版只改文字，截图一看和普通按钮没区别，而玩家连点两下时不会读字。
`_draw_buildings` 左栏改成「马车列全部人（含死人）、其他建筑只列活人」。

**新调试参数**：`--pending-fire`（截图确认态）、`--bld-hero=<hid>`（指定选中的人，
否则死人的那半屏永远截不到）。第二个是必要的：`_boot_building` 固定选 `alive_ids()[0]`。

**坑**：① `--bld-hero` 传了但被 `if not who.has(_building_hero): _building_hero = alive[0]`
重置掉，我一开始以为参数没生效；② 危险态按钮第一版只有文字变化。

**验证**：1091 项断言全绿（+20）；两区域 SELFTEST PASS；截图 `shots/m28_fire.png`、
`m28_confirm.png`、`m28_dead.png`。文档 `M28_DISMISS.md` 九节。未 commit、未 push。

**下一步**：受压 +25%/级（唯一还躺着的原版核心机制缺口）、马车候选按阵容短板加权、
同职业多人（key 要改成 id#序号，牵动四处）。

## M29 受压 +25%/级

**起点**：M25 的等级惩罚只做了一半——`entry_stress` 是**一次性**的（进门 +40，
撑过前两场就回本）。原版同时给两笔：进本 +20/级 **且** 每次受压 +25%/级。

**关键设计**：`Combatant.join_stress_mult` 必须是**独立字段**，不能乘进
`stress_in_mult`——后者每场战斗都被 `Battle.set_environment` 整个覆盖（光照驱动），
塞进去的话走进明亮区域那一刻等级惩罚就被洗掉了。测试钉了三条：
三层叠乘 10×1.3×1.5=19.5 / 换光照后倍率仍是 1.5 / 光照归零后 10×1.5=15。

**数据（bench 新增 `--resolve-mult`，20 趟同种子）**：
base 0.350/0.650/2.480；`--resolve=1` 0.250/0.750/2.985；
`--resolve=1 --resolve-mult` **0.150/0.850/3.785**；`--resolve=3 --resolve-mult` **逐位等于 base**。
结论：两条惩罚的难度贡献几乎相等（各 -10 个百分点），只做一半等于砍半；
压迫指数 2.480→3.785（+53%）是「全程更疼」的直接体现。

**UI**：准备屏队伍摘要加一句「N 人低于任务等级：最多进本 +X 压力、受压 ×Y」
（卡片太小写不下，且那笔罚是整队的事）；不够格的人的 Lv 行转警告色。

**顺手修的真 bug**：行程区选中态 `sel` 只比 size+quest 不比 level，M26 之后
会出现「标题写中程 3 级、高亮的是中程 1 级」。加了 `_prep_level == row[1]`。
（只在截图时暴露：我用 `--prep --level=3` 指定，而板子上那格恰好是 1 级。）

**验证**：1099 项断言全绿（+8）；两区域 SELFTEST PASS；截图 `shots/m29_prep.png`。
文档 `M29_STRESS_PENALTY.md` 七节。未 commit、未 push。

**下一步**：cleanse/gather/activate 三类任务（数据早在但没接，同 M13/M19/M20 的路子）、
每区域一块任务板、同职业多人。

## M30 修正：八座建筑只有公会能进（主人上手发现）

**症状**：城镇底部八座建筑，只有「公会」点进去有二级界面，其余七座点了没反应。

**真因**：`_activate()` 的 `bld:` 分支里，非公会那条只赋了 `_building` / `_building_hero`，
**漏了 `_state = S_BUILDING`**。点击确实被处理了（有 hover、变量也写了），画面却没切，
表现 = 无响应。公会走的是 `_state = S_GUILD`，所以只有它活着。

**为什么两期没发现**：`--bld=<id>` 截图参数是直接赋状态进建筑的，**绕过点击分发**；
规则层单测覆盖不到界面状态机。同 M20 的 `el\tif`：规则全绿、接线断了。

**修法**：补 `_state = S_BUILDING`（顺带清 `_fire_pending`）；
新增 `--click=<按钮id>` 启动参数，走真正 `_activate()` 再截图（和 `--bld=` 互补：
前者测接线，后者测画面）；商队/墓园副标题去掉「左侧点人」；商队空仓库改文案。

**验证**：七座建筑 `--click` 逐个打印 `S_TOWN(0) → S_BUILDING(8)`，公会 `→ S_GUILD(7)`；
1099 项断言全绿；两区域 SELFTEST PASS；
截图 `shots/m30_{coach,smith,sanitarium,abbey,tavern,wagon,graveyard}.png`。
M22 文档加 §11 补记。未 commit、未 push。

**教训（写进约定也值得）**：凡是「截图参数直接赋状态」的调试入口，
都会掩盖点击分发断线——新增界面屏时，必须留一条走真实分发的验证路径。
（2026-11-04 18:59 主人实测：八座建筑逐个点过，均正常进入二级界面。）
