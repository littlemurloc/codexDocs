## 11:50 · 验证图 09/10：能不能做成游戏画面

出 2 张（各 5-10 积分）：`shots/concept/09_west_battle.png`（4v3 战斗）、`10_west_descent.png`（竖井下行）。

**三个可用的结论：**
1. **4v3 站位天然可读**：左四人背影 / 右三只怪物 / 中间一支火把 = 天然的阵营分界线。UI 布局直接照这个来：下方技能栏，两侧各 4/3 个血条位，火把位置就是光照系统的可视化锚点。
2. **光照系统的视觉本质 = 「一盏灯画一个圈」**。M3 的 darkness 五档可以等价于光圈半径，不需要另做雾效。10 号图已经把这个说清楚了。

**一个必须警惕的偏差：**
氛围图会**自动补全暗部细节**——画面上四周虽然暗，但石雕、柱子、拱廊全都看得见。DD 实际的战斗画面是**真的黑**，只有角色身上有光。所以这两张只能当「资产设定参考」，不能当「画面目标」。若照它做，玩家不会觉得恐怖。游戏里该做的是**把光圈外的内容真的删掉**，而不是加一层暗色滤镜。
另：模型会把怪物摆得「好看」（错落、远近），但战斗需要三只怪在同一水平线上——美术必须为玩法让位，这是具体的一处冲突。

## 12:14 · M11 怪物位移：三层断点，不是数据没有

**先纠正 M9 的错**：M9 文档写「没有任何怪物技能带 push/pull」——**是错的**。
552 个怪物技能里 46 个带位移（push 37 / pull 21 / shuffletarget 14 / shuffleparty 6），
分属 41 只怪。

「怪物不会推人」有三层原因，单独修任何一层都不够：

1. **`move_resist` 解析了没人读**（和 M10 的 `ignore_guard` 同一形状）。
   英雄 0.2~0.4、怪物 0~0.95（原始 3.0/10.0 被 clamp）。
   关键坑：`res > 0` 必须短路，否则抗性 0 的单位也白消耗一次 rng → 序列错位 → 基线莫名变化。
2. **`shuffletarget` / `shuffleparty` 是死代码**（第三批），落兜底分支返回 `{}`。
   洗位只洗活人槽位（尸体不动）；`Shuffle Self` 不吃自己的抗性。
   消费顺序坑：洗位结果没有 `move` 字段，会被 `if delta == 0: continue` 静默吞掉。
3. **真正的原因：`_score` 不认识位移**。带位移的技能永远输给同伤害带压力的技能。
   `cultist_incantation` 7.20 分里有 5.6 分来自 +20 压力，push 只有 5.13。

### 交付
- `effect_resolver`：push/pull 过抗性、新增 shuffle 解析
- `Battle`：`shuffle_unit` / `shuffle_team` / `_alive_slots`、两个对照开关
- `_score`：位移按**实际能挪几格**估值（推到边界不记分）× 推得动概率
- `MOVE_VALUE_PER_RANK=1.0` / `SHUFFLE_VALUE=1.5` —— **唯一不来自数据的参数**，必须明说
- `bench_battle`：`forced_move_per_fight` / `shuffle_per_fight` / `move_resist_per_fight`
  + `move_probe` 三组专项遭遇（不进 summary）
- 界面：三种 move 分开写日志（主动/推拉/洗位）+「站稳了（位移被抵抗）」
- 自检只报数不判 PASS（玩家控制不了怪物推不推人）
- `tests/test_move.gd`（25 项）、`M11_MONSTER_MOVE.md`

### 数据（关键结论）
- **默认基线逐位不变**（4.0962 / 0.9410 / 0.8052），纯增量 —— 默认遭遇没有怪会用位移，
  英雄也一个位移技能都没有
- **单场有效**：crabby 场景 0.830（关估值）→ **0.580**（开），9.82 vs 11.51 轮
- **抗性挡掉 42% 位移但没救回血量**（2.06/0.580 vs 3.42/0.601）→ 位移边际递减
- **洗位完全无效**：13.25 次/场，血量 0.958 与抗性开关无关
- **远征反直觉**：120 趟，完成率 +0.033/+0.033/+0.017/0，压迫 −0.197(standard)
  → **怪物学会推人，玩家反而更轻松**。原因是副作用：估值把 AI 从 DOT 拉到直伤，
  而 DOT/压力是累积的。`witch_no_push` 三组完全一致证明不外溢。

### 踩的坑
1. `effect` 单值时是字符串，Python 遍历会按字符拆（`['B','l','e','e','d']`）
2. **数组下标≠单位身份**（M10 同款）：先记 `b.party[3].rank` 再读 `b.party[3]` = 两个人
3. 测试里拨了 `move_value_enabled` 忘了还回去 → `4.693 > 4.693`
4. 自检出手次数 12/58/27 不稳定，**不能用来对比改动**

### 验证
421 项断言全绿（新增 25）；短/中/长三档自检 PASS，中图真的出现「推拉=1 抵抗=1」、
长图「推拉=4 抵抗=1」。

### 遗留
英雄一个位移技能都没有（推怪做不到）；怪物不会主动调整站位；洗位无效果；
位移估值与 DOT 估值耦合（同一行代码绑了两件事）；召唤仍未实现。

## 13:20 · 画风转向：暗黑地牢式版画（用户反馈"写实太油腻"）

试 4 张对照：`25_dd_p1_six_kin` / `26_dd_c1_winchford` / `27_dd_stoneborn` / `28_dd_d2_winchworks`。**结论：场景全改用版画风，无一张输给写实版。**

### 换风格的本质（写进 WORLD_INSERTS §8.1）
写实厚涂 = **氛围性**（让人沉浸，像电影院）；版画 = **图解性**（让人看懂，像书籍插图）。
**用户要的是"小说插页"，而版画是插页的母语。** 版画的每根线都在承担说明义务，没有一根在烘托气氛。
附实用优势：**版画画错不像事故，像风格** —— 迭代成本低一个量级。

### 提示词骨架（已验证）
`Darkest Dungeon style woodcut illustration, heavy black ink, dense cross-hatching, harsh bold black outlines, flat colour over aged yellowed paper, palette sepia/bone/iron grey/ink black. NO gradients, NO soft lighting, NO oil painting, NO 3D.` + 结尾 `The whole image should read as an engraving: hatch density as the only shading.`
**关键：`hatch density as the only shading` 是在规定渲染算法，比写十遍 "woodcut" 都有效。**

### 逐张
- `28_dd_d2_winchworks` **最好**：地下压埋矿镇，苍白的悬空人形意外极准
- `26_dd_c1_winchford` **极好**，"越靠内越破"第一次是读出来的
- `27_dd_stoneborn` 单人立绘满血，"宽"方案成立
- `25_dd_p1_six_kin` 群像仍坍缩，石生画成巨人（身高第 4 次反向）

### 两个修法

2. 石生 4 头身像食人魔 → 加 `six heads tall, human proportions, only the WIDTH is abnormal`

### 最重要的发现：石生要不要"矮"（待用户拍板）

### 版画风特有的两个便利（写实做不到）
1. **空蚀用"缺影子"**：版画里影子=排线，全屋都有影子只有他那块是干净空白 —— 这是"语法错误"，眼睛自动去找。写实要靠"光穿过手"。
2. **盐骨层用"留白"**：版画背景就是纸，"灯照外什么都没有"= 什么都不画。写实反而画成雪原。
→ 推广：**版画分辨率是"画了/没画"，写实是"多亮"。前者更适合表达"不存在"。**

### 修正旧结论：克隆脸不是人多的错
写实版 16 里十几人共用一张脸，我原结论是"人多会坍缩"。**错。**
真因：写实要求脸"真"，真脸收敛到同一平均值。版画画的是**符号**（没牙/光头/拐/孩子/胖），符号天然互斥。
→ 新规则：**要一群不一样的人，别用写实，用符号**，给每人一个唯一标识。

## 13:32 · M12 召唤：数据缺失才暴露的第三个层次

上一期收了尾，「下一步做什么」我给了两个选择：召唤（战斗层，59 条数据）vs 奇物（949 条，但缺道具系统）。主人选了召唤。

### 数据全貌
59 个 `summon_monsters` 效果、**35 只怪**，从 M0 就在库里，一直落到 `unsupported = "summon"`。所以收藏家、死灵法师、溺亡船长这些「以叫人为核心威胁」的怪，等于一群只会平砍的普通怪。

### 三个必须先搞对的数据形态
1. **`summon_monsters` 单值时是字符串**（不是数组）——M11 踩过同类坑，解析层统一摊平。
2. **`summon_limits` / `summon_ranks` / `summon_chances` 是与候选并行的数组**。
   「第二个候选拿第一个候选的上限」不会报错，只会悄悄变成另一个东西 → `_aligned()` 强制对齐。
3. **`summon_ranks` 是位掩码，不是槽位号。** 第一版按 1 基槽位实现（值域像 1~4），
   但 `brigand_sapper` 写 **12**——槽位号无解。按位掩码：`12 = 0b1100` = 3、4 号位；
   `[1, 4]` 对应 `[割喉贼, 火枪手]` = 近战前 / 火枪后，语义自洽。**这是决定性证据。**

### 又一次「解析通了不等于实现」
接通第一天，六只召唤怪的召唤技分数：`cannon_summon` **0.00**、`collect_call` **0.00**、
`beholder_summon` 1.00、`summon_slime` 0.85。实跑 12 场，召唤 **0 次**。
原因：`atk=0, dmg=[0,0]`，`_score` 里没有一条给它们加分。**和 M11 一模一样的剧本。**

估值口径：`1.5 + hp/4`（血量代理「要多打的血 + 每回合多一次攻击」）。
**召唤不乘命中率**——59 条全是 `on_hit/on_miss` 双 true。加在 `bonus *= hit` 之后。

### 数据缺失才暴露的第三个层次
59 条里只有 22 条带 `summon_limits`。`ectoplasm_A` 召的是**它自己**，于是：

| 实现 | 轮数 |
|---|---|
| 无任何上限 | 22.1 |
| 每施法者 4 次 | 16.3 |
| 同种上限 2 | **23.7（更糟）** |
| 同种 2 + 阵营总量 4 | **9.73** |

第三行是关键：只限「同种在场 2 个」会让数量卡在 2 上下**震荡**——打死一个，剩下那个立刻补回来，阵型不增长但总血量无限延伸。所以需要两条闸：`DEFAULT_SUMMON_LIMIT=2`（防占满阵型）+ `MAX_SUMMONED_PER_BATTLE=4`（防死一个补一个）。**这是补充规则，不是数据**，数据优先。

### 顺手修的健壮性 bug
`effect_resolver.apply` 里的 `bool(e.get("on_miss"))`：数据里 `on_miss` 有 **3 条是列表**，
`bool(null)` 会抛 `Nonexistent 'bool' constructor`，`Array == bool` 是非法运算。
之前没炸只因为走到那条路径的技能恰好都写了 true/false。统一走 `_flag(v)`。
