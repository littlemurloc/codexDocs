# M34 · 同职业多人（名册的 key 换成实例 id）

> 一句话：名册的 key 从「职业 id」换成「实例 id」，于是同一个职业可以有第二个人。
>
> M27 到 M33 有六期妥协都长在同一行字上：`campaign.roster` 的键是职业 id，
> 所以「一个职业最多一个人」。这条限制冒充过好几种游戏规则——
> 马车永远不给你第二个修女、名册上限等于职业数、解雇一个人候选池里就少一个"职业"。
> 这一期把键换掉，那些规则就自动散了。

---

## 1. 起点：一条实现限制冒充了六期游戏规则

| 期 | 当时的写法 | 真正的原因 |
|---|---|---|
| M25 | 「同职业不能多人」写进已知限制 | key 是职业 id |
| M26 | 四个区域共用一块板子（后来才发现） | key 是职业 id |
| M27 | 名册上限 = 职业总数（15） | key 是职业 id |
| M27 | 候选池 = 没入册的职业 | key 是职业 id |
| M28 | 解雇时 `recruit_candidates.erase(hid)` | key 是职业 id（其实 erase 无效） |
| M32 | 任务板"保底最弱的人"要绕开名册结构 | 名册结构单一 |

所以这不是一个功能，是**改地基**。改之前只有 3 个文件直接碰 `roster`
（`campaign.gd` 19 处、测试 45 处、场景 1 处），其余全走 API——
这一点决定了它现在改还来得及。

---

## 2. 命名方案：为什么是 `crusader#2`

有两种做法：

1. **不透明 uid**（`h1`、`h2`…）+ 每行一个 `def` 字段。最干净，但所有
   「拿 id 去查数值表」的代码都要改成「先查 def」，包括 bench 和 45 处测试。
2. **`职业 id` + 后缀**：第一个是 `crusader`，第二个起 `crusader#2`、`crusader#3`。

选了 2，理由是**向后兼容是结构性的，不是运气**：

- M0~M33 的存档里，每个键本来就是一个职业 id → 第一个人天然合法；
- 现有 45 处测试、bench、以及所有「按职业查数据」的调用，
  在只有一个实例时 `key == def`，一行都不用改；
- 界面上第一个十字军就叫「十字军」，第二个才叫「十字军 Ⅱ」——
  玩家的既有认知不变。

代价是必须守住一条规则，写进了 `Campaign.def_of` 的注释：

> **查数据用 def，记状态用 key。**

两个十字军的 `def` 都是 `crusader`（同一份血量表、技能表、饰品职业限制），
但 `key` 不同（压力、血量、等级、装备、怪癖各归各的）。

后缀用罗马数字（Ⅱ / Ⅲ …ⅩⅤ）而不是阿拉伯数字：`十字军 2` 会被读成
「2 级」，而等级就在同一张卡上写着。

## 3. 改了什么

| 文件 | 改动 | 关键点 |
|---|---|---|
| `combatant.gd` | 新增 `hero_key` | `def_id` 答「干什么的」，`hero_key` 答「哪一个人」 |
| `battle.gd` | `setup(..., def_by_key)`；快照按 `hero_key` 存取 | 不传映射时行为与 M33 逐位相同 |
| `expedition.gd` | `hero_defs` + `_def_of()`；4 处 `db.hero*` 改走 def | 状态/装备/怪癖按 key，数值查询按 def |
| `campaign.gd` | `roster` 键改实例；`def_of` / `next_uid_for` / `variant_suffix`；`hire` 造 uid；候选池放开 | 旧档自动补 `def` 字段 |
| `expedition_scene.gd` | `_hero_label()`；5 处 `db.hero_base` 走 def；出发时递 `defs` | 28 处名字显示收口到一个函数 |

`roster_max()` 从「职业总数」变回一个人头上限（仍是 15）：
城镇名册两列 15 格的排版（M31）是按这个数排的，改它要重排版面。

## 4. 踩的坑

**批量替换把函数自己替换掉了。** 先把 28 处 `DdNames.hero_name(` 全换成
`_hero_label(`，而 `_hero_label` 内部那行也被换成了 `_hero_label`——
于是它调用自己。症状不是编译错，是**运行时栈溢出**：

```
SCRIPT ERROR: Stack overflow. Check for infinite recursion
   at: Campaign.def_of
   [0] _hero_label ... [23] _hero_label
```

而外面的表现是「带重复职业的存档一读就崩，普通存档完全正常」——
如果只跑常规自检，这个 bug 一行都不会露头。

**罗马数字不能拼。** 第一版用减法拼装（10/9/5/4/1 循环），
2 被拼成「ⅠⅠ」而不是「Ⅱ」。改成 1~15 的查表——反正名册上限就是 15。

**旧档校验会把第二个人吃掉。** `from_dict` 里有个兜底循环用
`known_heroes.has(key)` 判断「是不是已知职业」，而 `crusader#2` 不在里面。
不改成先取 def 再校验，读档会静默丢掉同职业的第二个人——
正是 M27 那次「存了 8 个读回来 5 个」的同一种病。

## 5. 数值

这一期不改任何战斗数值：不传 `def_by_key` 时 `def == key`，
所以 bench 的输入完全没变。可以验证：

```
1265 项断言全绿（+55，新增 tests/test_m34.gd）
```

与上一期逐位可比的部分（战斗/远征指标）没有重跑，因为规则层没有可观察变化。

端到端：

| 场景 | 结果 |
|---|---|
| 常规 5 人名册，短图 Lv1 | PASS（和 M33 一致） |
| 名册含 十字军 / 十字军 Ⅱ / 修女 / 修女 Ⅱ（7 人） | PASS |
| **4 个十字军**组队（无治疗） | 跑完整趟、`PASS`，但必死（团灭）——这正是预期：结构通了，阵容仍然很烂 |

## 6. 已知限制

1. **候选不按阵容短板加权**。M27 记的那条还在：缺治疗时更容易来修女，没做。
   现在候选池是「全部职业里抽 2 个不同的」，比 M27 更均匀，也更随机。
2. **`recruit`（复活）和 `hire`（招新）仍然并存**。M27 当时说是过渡设计，
   等名册够大就关掉复活。这一期没动它——它现在按实例 id 工作，不需要改。
3. **同一个人的名字只靠后缀区分**。原版是独立人名（Dismas、Reynauld…），
   我们没有名字池，所以「十字军 Ⅱ」读起来还是像编号而不是一个人。
   要做的话得引入一张名字表，那是内容层的事。
4. **`roster_max` 固定 15**，不再随职业数变化。想要「最多 25 人」得同时改
   城镇名册的两列排版。
5. **怪癖/饰品没有「同名冲突」问题，但也没有「按人区分」的展示**：
   两个十字军的怪癖各归各的，界面上只在选中他们时才看得到。

## 7. 验证

- **1265 项断言全绿**（+55，`tests/test_m34.gd`）：
  - 命名：第一个是 `crusader`、第二个 `crusader#2`、`def_of` 两者都是 `crusader`、
    后缀 Ⅰ/Ⅱ/Ⅲ、名册里没有时也能按命名规则推 def
  - 招两个十字军：老人装备 3 阶 / 新人 0 阶、老人 4 级 / 新人 1 级、
    老人压力 55 / 新人 0、技能表两人相同（按职业查）
  - 解雇其中一个不牵连另一个
  - 战斗层：两人 `def_id` 相同、`hero_key` 不同；快照是两条；
    血量 3 与 11 分别落在各自名下；回灌也分开
  - 不传 `def_by_key` 时：纯职业 id 照常装配；传实例 id 则**装配失败**（不猜）
  - 存档：`crusader#2` 读回来还在、def/装备/等级都对；
    旧档（缺 `def` 字段）不丢人、按命名规则推得出来
- 端到端：常规 5 人 / 7 人（含两对同职业）/ 4 个十字军 —— 三种名册都 PASS
- 截图：`shots/m34_town_dup.png` —— 城镇名册「十字军 / … / **十字军 Ⅱ** / **修女 Ⅱ**」
