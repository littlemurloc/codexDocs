# M46 · 补上的两个规则缺口

> 任务完成给报酬、战役有终点。这两件事之前都不存在。

## 1. 任务完成报酬（quest_rewards）

### 之前的状态

`quests.json` 里一直躺着完整的报酬表，全项目**零引用**。任务完成只发远征途中捡到的东西，
交差不给钱——所以「跑完一趟」和「半路撤退」在经济上几乎没区别，只差一点经验。

### 表的结构

```
quest.generation.generation.rewards
├─ item_table[难度行][长度列]              → 金币（如 [1][1] = 3000）
├─ heirloom_amount_table[type].amounts[][]  → 各传家宝件数
├─ resolve_xp_table[][]                     → 决心经验（本项目已有等价实现 QUEST_XP，未接）
└─ trinket_chance_table[]                   → 饰品掉落概率（未接）
```

- 行 = 难度：**1 / 3 / 5**（数据里 0/2/4/6 行是空的，用 `_xp_tier()` 归一后正好落在这三行）
- 列 = 长度：0 是空列，**1=short 2=medium 3=long**
- 首领任务的 `size` 名义上是 `medium`，所以落在第 2 列

### 实测数值

| 难度 | 短途 | 中途 | 长途 |
|---|---|---|---|
| 学徒（Lv1） | 3000 | 4500 | 7500 |
| 老手（Lv3） | 4500 | 6750 | 11250 |
| 冠军（Lv5） | 6000 | 9000 | 15000 |

传家宝（Lv1 短途）：`bust 2 / portrait 2 / deed 3 / crest 3`（共 10 件）

### 这个数没有打崩经济——先量了才敢用

直觉上「一趟给 3000」很夸张，因为本作的招募只要 1000 金。但 `campaign.json` 的 `loot.note`
自己写着：`complete_gold: 45` 是**旧基线常数**，真实抽卡表一趟短途 Lv1 约 3498 金。

实测三趟（`--dev` 打印）：

```
[econ] 结束=complete  战利品 1658 + 任务奖励 3000 = 4658 金
[econ] 结束=complete  战利品  442 + 任务奖励 3000 = 3442 金
[econ] 结束=complete  战利品 5105 + 任务奖励 3000 = 8105 金
```

战利品在 **442–5105** 之间波动（11 倍），任务奖励 3000 落在中位附近。
它不是「凭空多一笔」，而是**把运气差的一趟托起来**——固定收入让经济不再完全依赖掉落随机。

判据和 `xp_for` 一致：**只有 `complete` 发**。`incomplete` / `retreat` / `wipe` 一律不发，
否则「进去打两间房、撤退重来」又能刷钱，和刷经验是同一个漏洞。

### 没接的两块

- `resolve_xp_table`：本作已有 `QUEST_XP` 常量实现（`campaign.gd:52`），数值口径不同但功能等价。
  接过来只会让同一个数字有两个来源。
- `trinket_chance_table`：按稀有度给完成任务的饰品概率。要接就得在结算里掷骰，
  而结算目前不消耗 rng。**这是下次要做时唯一需要小心的地方**（M15 那条铁律）。

## 2. 战役终局

### 为什么不做「第四个区域」

原版的终局是 4 个 DD 副本。但 `dungeons.json` 里 **`darkestdungeon` 一张地图都没有**
（maps 只有 weald/crypts/warrens/cove 各 11 张），只有遭遇表。

要真做就得自己生成一套 DD 地图，那是「内容」不是「收尾」。

所以改用：**讨伐四个区域的首领 = 战役结束**。

- `campaign.boss_cleared: {region: true}`
- 结算时判定 `end_reason == "complete" and quest_type == "kill_boss"` → 记下该区域
- 四个区域全清 → `victory_pending = true` → 下一屏是胜利屏

零新数据，规则上也说得通（四个首领都在，只是分散在四个区域）。

### 判定为什么放在规则层、切界面为什么放在 view

`settle()` 只负责「记下这件事发生了」（`victory_pending`），
界面读它、显示完再清掉。让规则层去决定「该显示哪个屏」会把 UI 知识写进 core。

### 胜利屏

一张卡、五行数字、两个按钮。**刻意没写剧情文本**——本作没有剧情系统，
写两句煽情的话只会显得假。

两个出口：
- **继续经营这座城镇**：不锁档。本作没有多周目，锁档等于把玩家攒的东西全扔了
- **开新的一档**：真的清档重来（会盖掉当前槽）

### 玩家怎么知道要打首领

城镇屏底部那行原来只讲战利品，现在补一句：

> 战利品只在远征里拿：赢一场就有，走完全程另有结算奖励。**讨伐四个区域的首领即战役结束（2 / 4）。**

不写的话，这件事只有读过文档的人知道，玩家会一直以为这是个无限循环。

## 3. 顺带修的两个真 bug

### 3.1 右对齐的文字画到了屏幕外

`draw_string(font, pos, text, align, width, ...)` 里 **`pos.x` 是文本框左边界**，不是右边界。
所以 `HORIZONTAL_ALIGNMENT_RIGHT` 必须写成 `pos.x = 右边界 - width`。

查下来三处是错的：

| 位置 | 原来写的 | 后果 |
|---|---|---|
| 地图屏「侦察 %」 | `size.x - 24`, w=200 | 整行画在屏幕外 **176px**，**从来没显示过** |
| 英雄卡「忙 N 周」 | `r.x + r.w - 10`, w=64 | 画到卡片外 54px |
| 城镇资源行右端 | `size.x - 28`, w=380 | 同上 |

「侦察概率」这条最要命：它是光照的第三个作用（光照 ≥50 才有侦察加成），
玩家一直在为一个**看不见的收益**做决策。

### 3.2 主菜单的 `--w=1080` 测了个假的

`_want_w` 的应用原来在 `_boot_campaign` 之后，而主菜单分支在那之前就 `return` 了。
于是「1080 宽下看主菜单」截出来还是 1280。

这和 M41 踩过的是同一个坑（`--resolution` 不改变视口 → 测了个假的）。
修法是把窗口尺寸的应用提到菜单分支之前。

## 5. 新增参数

| 参数 | 用途 |
|---|---|
| `--bosses=N` | 把前 N 个区域标成已讨伐。没有它，想看「首领 3/4 的城镇」得真打三场首领 |
| `--victory` | 直接进胜利屏（同时把四个区域标成已清，否则画面上会写着「战役完成」而「首领 0/4」） |
