## 一、先回答"能不能办到"

**能，而且核心部分我已经做出来了。**

- 这个游戏的"游戏性"其实只有一台 **11 条指令的虚拟机 + 一个程序编辑器 + 一组关卡数据**。这部分是纯逻辑，Godot 里一天能写出来——原型里已经实现并通过 64 项自动检查。
- 真正的成本不在技术，在 **内容与皮**：50 关左右的关卡设计（输入流/输出流/开放指令/双指标目标值/旁白）、角色动画、办公室场景、音乐。
- **有一条红线**：玩法机制不受版权保护（可以合法做"同类"），但原版的美术、音乐、字体、文案、具体关卡数值属于表达，不能扒来用。下面给了可执行的替代路线。

## 二、这份工程里到底有什么（实测数据）

### 2.1 文件构成

| 文件 | 大小 | 说明 |
|---|---|---|
| `Human Resource Machine.exe` | 120,869,376 B | **整个游戏就这一个 exe**，零散资源文件一个都没有 |
| `steam_api.dll` | 191 KB | Steam 接口 |
| `readme.html` | 3.6 KB | 操作说明 + 存档路径 |
| `soundtrack/*.mp3` | 18 首 | 原声碟（单独卖的，不是游戏运行必需） |

没有 Unity 的 `*_Data`、没有 GameMaker 的 `data.win`、没有 `.pak`/`.assets`。**Tomorrow Corporation 自研引擎**（World of Goo / Little Inferno 同款技术栈），C++ 静态链接。

### 2.2 引擎与资源系统

PE 节表：

```
.text   0x83d85    .rdata 0x1b4da    .data 0xee65a0    .rsrc 0x728fde0   ← 119.8MB
```

`.rsrc` 里只塞了一项大资源：`RCDATA type=20480 id=1, size=119,798,208`。**所有资源集中在一个包里**，格式是自研的：

```
header : u32 version(=1) | u32 count(=1643)
index  : 1643 × 16B  =  (u32 keyHash, u32 flag, u32 offset, u32 chunkSize)
chunk  : flag=1 → (u32 compSize, u32 rawSize, zlib/deflate 数据)
         flag=0 → (32B 头, 裸 PCM；头里能看到 0xAC44 = 44100Hz)
对齐   : 每个 chunk 起始 64 字节对齐，空隙用 "PAD" 填充
```

- **文件名不存**，只有 32 位 hash——典型的"只读资源包"设计，加载时按 hash 查表。
- 实测：**1482 个 zlib 块 + 161 个裸 PCM 块 = 1643**。
- 解包后的每个资源是自研"节点"格式：`u32 type | u32 headerSize | 类型专属字段…`

  已确认的类型：

  | type | 数量 | 内容 |
  |---|---|---|
  | 1 | 696 | 纹理。**未压缩 RGBA8**（如 936×936 = 3,504,404 B，正好 936²×4+20） |
  | 2 / 3 / 4 / 5 | 76/24/9/20 | 场景对象、变换矩阵（能看到 42.2f / 11.1f 之类的浮点） |
  | 6 / 7 | 47 / 122 | 容器。其中 `0001` 是 **5.6MB 的位图字体**——字形用 ASCII 字符画存（`!!!!!!!!!` 拼出来的像素） |
  | 8 | 165 | 音频节点（32B 头 + PCM，44100Hz） |
  | 10 / 11 | 43 / 35 | 大块二进制帧（1~3MB / 3 个 15.8MB 同尺寸） |
  | 19 | 2 | 语言索引表 |
  | — | 43 | **DXBC 编译着色器**（D3D 管线，说明是自研渲染层） |

解析脚本：`_hrm_analysis/extract_pak.py`（可复现，一条命令拆完整个包）。

### 2.3 文本与本地化

有一个 548KB 的语言表节点，**19 种语言**：`bp cht cs da de en es fr hu it jp ko nl no pl ru sv tr zh`。

字符串按 hash 键存、每种语言一格，所以文本能完整读出来，包括：

- 全部 UI 文案（`INBOX` / `OUTBOX` / `JUMP` / `COMMENT` 等指令名、"如果 INBOX 是…OUTBOX 应该是…" 的任务描述模板）
- 全部关卡名，例如（实抓）：`Mail Room`、`Busy Mail Room`、`Copy Floor`、`Scrambler Handler`、`Zero Exterminator`、`Tripler Room`、`Zero Preservation Initiative`、`Octoplier Suite`、`Sub Hallway`、`Equalization Room`、`Maximization Room`、`Employee Morale Insertion`、`Absolute Positivity`、`Exclusive Lounge`、`Sabbatical Beach Paradise`、`Rainy Summer`、`Midnight Petroleum`、`Fibonacci Visitor`、`Digit Exploder`、`Vowel Incinerator`、`Alphabetizer`、`The Littlest Number`、`Multiplication Workshop`、`Inventory Report`、`Sorting Floor`、`String Storage Floor`、`Duplicate Removal`、`Three Sort`、`Prime Factory`、`Re-Coordinator`、`Tetracontiplier`、`Cumulative Countdown`、`Scavenger Chain`…
- 老板/员工的邮件式旁白（法语文案里能看到"用户投诉机器过热/数字太复杂"那类原文）

**这是最值钱的一份素材**：它把整款游戏的**叙事结构和关卡顺序**白送了，只是文案本身不能直接抄。

### 2.4 存档

`%APPDATA%\Human Resource Machine\profiles.bin`，**14,990,216 B**，首 4 字节 `4B23E5A6` 后面全是高熵数据——**加密/混淆过**，不能直接读。

顺带说明一个设计点：一个纯逻辑游戏的存档能到 15MB，基本可以断定它**把每关的解法程序和每次运行的周期记录都存下来了**（年鉴/统计页要展示"你的历史最优"）。这一点对重构有参考价值——存档别只存"是否通关"。

### 2.5 没拿到的东西

- **关卡的数值数据（输入流、期望输出流、开放指令集、SIZE/SPEED 目标）没有明文**，编译进了自研节点二进制，需要继续逆向才能逐关提取。
- 音乐/音效是**裸 PCM + 压缩块**，理论上能还原，但——见第四章版权部分。

## 三、游戏拆解：真正需要重写的是什么

### 3.1 核心：一台只有 11 条指令的虚拟机

整个游戏跑在一台极简机器上：**一只手（寄存器）+ 一排地板格（内存）+ 收件箱/发件箱（输入输出队列）+ 跳转标签 a~d**。

| 指令 | 前置条件 | 语义 | 周期 |
|---|---|---|---|
| `INBOX` | 手必须空 | 从收件箱取一个到手 | 1 |
| `OUTBOX` | 手必须有值 | 把手里的值送进发件箱，手清空 | 1 |
| `COPYFROM n` | 手必须空 | 地板[n] → 手 | 1 |
| `COPYTO n` | 手必须有值 | 手 → 地板[n]，手清空 | 1 |
| `ADD n` | 手必须有值 | 手 += 地板[n] | 1 |
| `SUB n` | 手必须有值 | 手 -= 地板[n] | 1 |
| `BUMPUP n` | 手必须空 | 地板[n] += 1，结果同时进手 | 1 |
| `BUMPDN n` | 手必须空 | 地板[n] -= 1，结果同时进手 | 1 |
| `JUMP l` | — | 跳到标签 l | 1 |
| `JUMPZ l` | 手必须有值 | 手的值 == 0 才跳 | 1 |
| `JUMPN l` | 手必须有值 | 手的值 < 0 才跳 | 1 |
| `COMMENT` | — | 纯注释，不计 SIZE、不计周期 | 0 |

**这套约束里藏着一个设计精髓**：你**无法"丢弃"**手里的值。想扔掉一个 0，必须 `COPYTO` 到一个地板格上。"丢不掉"这条限制，直接制造了《零清除者》《零保护计划》这类关卡的难度（我写原型时就被它绊了两次，见 5.2）。

两个指标：
- **SIZE** = 非注释指令条数（代码能多短）
- **SPEED** = 总周期 ÷ 物品数（跑得多快）

双指标互相拉扯，是这游戏能让人反复重刷 50 关的唯一原因。

### 3.2 关卡 = 纯数据

一关只需要 7 个字段：

```json
{ "inbox": [1,2,3,4], "outbox": [1,2,3,4],
  "allowed": ["INBOX","OUTBOX"], "mem_size": 2,
  "size_target": 8, "speed_target": 2.0,
  "story": "…老板的邮件…" }
```

加一条"参考解"就能自动算出双指标目标值（原型就是这么做的，改关卡不用手填数字）。

### 3.3 三层循环

1. **编辑**：从指令面板把指令拖进程序区（拖拽是核心手感，不是点缀）
2. **运行**：单步/连续，员工抱着值在收件箱→地板→发件箱之间跑，每一步都能看见
3. **优化**：过关后看到 SIZE/SPEED 两行，没达标就想再删两条指令——**这才是留存引擎**

### 3.4 表现层（原版真正的成本）

- 办公室实景：升降梯、同事、老板、咖啡机、盆栽、逐年变化的装修
- 员工动画：抱箱子走、放地板、发呆、加班变憔悴
- 叙事：邮件/对话式叙事贯穿 7 年，最后"机器取代人类"的结局
- 音乐：18 首原声

这部分**占原版 80% 的制作量**，但在重构里可以先降级——原型就用了纯色卡片 + 数字块，机制完全成立。

功能点：
- **20 关**，覆盖全部 11 条指令的教学顺序：INBOX/OUTBOX → JUMP → COPY → ADD → JUMPZ/JUMPN → BUMPUP/BUMPDN → 哨兵值/累加/比较三分支

- 标签 a~d 一键循环切换，`JUMP/JUMPZ/JUMPN` 用下拉选目标

- **办公室舞台**：墙面/灯/挂钟/公告栏 + 地板格实时显示内存值 + 员工抱箱走动（走到收件箱、走到某个地板格、走到发件箱），指令执行时对应格子高亮

顺手记一个有意思的坑：我最初按记忆写的三倍房解是 `COPYTO 0; ADD 0; ADD 0`——**跑不通**，因为 `COPYTO` 会把手清空。正确解必须 `COPYFROM 0` 把值捡回来。虚拟机把这个错误精确报了出来，说明语义判定是硬的，不是"看起来差不多"。

## 八、第三版：换成「数羊」主题（逐项可行性评估）

「程序员搬箱子」是原版的设定，既然要自研就得换掉。下面是把每个机制往「睡眠中数羊」这个念头上套的完整评估——**先说明哪些套得上，哪些套不上，再谈美术能不能做**。

### 8.1 逐项映射与表达力评级

| 机制 | 数羊主题里的对应物 | 表达力 | 说明 |
|---|---|---|---|
| `INBOX` | 从左边羊圈牵一只羊出来 | **强** | 羊圈、围栏、挤着的羊，天然成立 |
| `OUTBOX` | 把羊推过栅栏，它跳过去 = 数过一只 | **极强** | 这就是数羊这个动作本身，是整个主题的锚点 |
| 手（有值） | 怀里抱着的那只羊，编号浮在头顶 | **强** | 手空 / 手满 = 怀里有没有羊，一看就懂 |
| 地板格 `mem[i]` | 草地里插着的木牌，牌子上写数字 | **中强** | 必须放弃"石子堆"（数到 20 就没法画），改用写字木牌才可读 |
| `COPYFROM i` | 从 i 号木牌上把数字捡起来 | **中** | 概念是"记账"，能自洽但要玩家接受一次转译 |
| `COPYTO i` | 把数字记到 i 号木牌上 | **中** | 同上；顺带把"COPYTO 会清空手"讲成"记完就腾出手了"，反而更好懂 |
| `ADD` / `SUB` | 木牌上的数字变大 / 变小 | **中** | 抽象，但配上数字跳动就够用 |
| `BUMPUP` / `BUMPDN` | 木牌上的数字 +1 / −1，同时拿到手里 | **中强** | 语义本来就是"增减一格"，很贴 |
| `JUMP` / `JUMPZ` / `JUMPN` | —— | **弱（无实体）** | 控制流没有物理对应物。原版也没表现它，玩家接受度没问题 |
| 程序出错 | 羊被栅栏绊倒，四脚朝天，头顶冒星星 | **极强** | 比"报错弹窗"生动得多，是这版最大的收益 |
| 全部输出正确 | 羊全跳过去，头顶飘 `z z z`，月亮变亮 | **强** | 「终于睡着了」是天然的胜利画面 |
| `SIZE` / `SPEED` 双指标 | 无主题对应 | **弱** | 保持技术面板形态，不做拟物化——玩家需要精确数字 |

**结论：11 条指令里 10 条能落到具体物件上，只有控制流（跳转/条件）无实体。** 这不是缺陷——数羊这件事本来就没有"跳回第三只羊"的物理动作，玩家读程序行时也不需要看它。真正要接受的转译成本只有一个：**"地板格"变成"木牌"**。

### 8.2 三处真实的设计张力（先说清楚，别等做到一半才发现）

1. **"数羊"天生是顺序计数，而游戏在做乘除比较。**
   解法不是硬掰，而是把它写进设定：**你已经数到半梦半醒，羊的编号开始自己翻倍了**。这一句话同时解释了所有算术关卡，也让「三种手势」这种怪关有了安放之处。荒诞感在这里是资产，不是负债。

2. **"助眠"的情绪和"解谜"的情绪是相反的。**
   数羊让人放松，调试程序让人紧张。所以这版**不追求"真的让人困"**，而是"失眠者脑子里的荒诞牧场"——用幽默化解，色调保持深夜但不做催眠式的柔和。

3. **木牌和角色会抢同一条地平线。**
   这是实际做的时候撞到的第一个硬问题：角色和小人都立在 `floor_y` 上，木牌如果也立着，必然互相遮挡。**解法是把木牌平铺到前景草地上（`floor_y` 以下）**，角色站在木牌后方——一次坐标分层就解决了，但这只能在画出来之后才发现。

### 8.3 美术资源：我能做到哪一步

四条路线，按成本排：

| 路线 | 我能做到 | 代价 | 适合 |
|---|---|---|---|
| **A. 纯代码绘制**（当前实现） | 已经做完，羊/木牌/栅栏/夜晚全部 `_draw` 现画 | 0 资源、改色改比例即时生效 | 原型、内部验证、快速迭代 |
| **B. 程序化像素风** | 能做，用 `_draw` 按格子画 | 需要写一遍像素级绘制，改起来比 A 慢 | 想要"复古像素"标签 |
| **C. AI 生成贴图** | **能生成**（图生图 + 透明背景），但需要人工挑图、切帧、对齐锚点 | 每张图消耗额度；风格一致性要反复调；透明边缘常需手动修 | 静态元素（月亮、木牌、装饰）优先 |
| **D. 找美术画** | 我做不到，只能出需求单和资源规格 | 真金白银 | 要上架卖 |

**A 的实际上限**：几何扁平风可以做到"干净、可读、有生命感"（当前截图就是这个上限），但到不了手绘的细节密度和材质感。
**C 的现实风险**：单张图好看 ≠ 能用。游戏内元素需要严格一致的尺寸、锚点、朝向、帧序；AI 出图在这四点上都不稳定，通常要做一轮"生成 → 抠图 → 对齐 → 挑帧"的人工工序。所以我的建议是：**先 A 把玩法定型，等关卡和手感都稳了，再用 C 只替换最值得替换的几件（羊、角色、月亮），别整体重做。**

### 8.4 这一版已经落地的内容

- 舞台整块换成夜晚牧场：渐变夜空、星、月（通关后变亮）、远山、云、草地、萤火虫
- 羊圈（待数）、木牌（内存）、栅栏 + 计数挂牌（输出）、栅栏右侧"已数过的羊群"
- 牧羊人（睡衣小人）、怀里抱羊、头顶编号牌
- **跳跃弧线**：`OUTBOX` 时羊从怀里沿抛物线越过栅栏，落到另一侧
- **绊倒动画**：出错时羊翻倒在栅栏边，四脚朝天 + 头顶星星 + "绊倒了"红牌
- 报错文案全部改成牧场语境（`"怀里还抱着一只羊，腾不出手去羊圈牵（INBOX 要求手空）"`）
- 20 关全部改名（Mail Room → 第一只羊 / Tripler Room → 三只一堆）

## 九、第四版：拖拽手感 + 羊圈可读性

这一版只解两个"玩起来别扭"的问题，但两个都是根因级的。

### 9.1 拖拽为什么"必须对准"——以及为什么不修补内建 DnD

内建 DnD 的命中规则是：**找鼠标正下方那个控件，只问它 `can_drop_data`**，不往下问，也不往上问。于是有几处天然死区：

| 死区 | 原因 |
|---|---|
| 行与行之间 4px 的缝 | 缝隙不属于任何行，落上去没有任何控件接 |
| 行内的按钮 / SpinBox / 下拉框 | 它们是更深的控件，事件被它们接走，行收不到 |
| 上下半的分割线附近 | 半行判定，手一抖就插错位置 |
| 列表下方的大片空白 | 不属于任何行，直接丢弃 |

所以不是"阈值没调好"，是**判定模型本身只有一条线**。这版改成自己算：

- `_input()` 比 GUI 更早拿到所有鼠标事件，拖拽期间由它统一接管（并 `set_input_as_handled()`，避免抬键误触行内的 `×` 删除按钮）
- 命中判定变成**整块编辑器面板**：面板矩形放宽 40px 内任意位置都算投放区，按纵向位置换算成"插到第几行"；列表下方空白直接等于"插到末尾"
- 判定用的是**还原掉空隙后的行坐标**，所以空隙长高、行往下挤的过程中判定点不会跟着跳，手感才不抖
- 插到上下边缘时列表自动滚动，长程序能一路拖到底；`Esc` 或拖出面板= 取消

### 9.2 让位置"自己挪出来"

只画一条插入细线，玩家还是得对准那条线。这版把**插入位做成一个真实节点**（`scripts/drag_gap.gd`），插进 `VBoxContainer` 里，高度从 0 长到一行高——长高的过程就是把下面的行真的挤下去，同时显示虚线框 + "放这里"。

好处是"位置"这件事从**抽象的线**变成**占了空间的格子**：玩家只要把鼠标放到大概位置，格子自己张开，松手就落进去。

顺带一个坑：拖拽会吞掉抬键事件，`BaseButton` 的 `press_attempt` 因此不会复位，指令面板按钮会留下一个"按下去"的假象。处理办法是把这些按钮的 `pressed` 样式改成与 `normal` 一致——按下的即时反馈由随鼠标走的幽灵卡片提供，不需要按钮自己再给。

### 9.3 羊圈：栏杆让位给编号

原设计里羊圈前面的木栏是**前景**，正好横在羊身上，把编号全挡了。这版：

- **栏杆整个去掉**，只留一块踩实的土地做圈地暗示（前景不跟信息抢位置）
- 编号**直接刷在羊毛中央**，深棕字 + 一圈浅描边（`draw_string_outline`），压在毛边或影子上也不糊；2 位 / 3 位数自动缩字号
- 间距从 39px 放到 58px：后一只羊的头不再挡住前一只的编号；总数超过 3 只时右上角显示 `+N`
- 牧羊人取羊的站位后移，不再压住最后一只羊
- 怀里抱的羊、跳过去的羊，身上同样带编号——"哪只羊过去了"看得见

### 9.4 验证方式

界面测试加到 **57 项**，其中新增的真·鼠标链路（按下指令面板按钮 → 拖到两行之间 → 松手；按住首行拖到末尾）用 `Viewport.push_input` 模拟真实事件：

```
$ godot --path hrm_godot --script tests/test_ui.gd      # 带窗口，57 项
$ godot --headless --path hrm_godot --script tests/test_ui.gd   # 49 项，跳过鼠标链路
```

headless 没有窗口，`gui_get_hovered_control()` 恒为 null，GUI 命中测试跑不起来——所以这部分必须带窗口跑，headless 只跑逻辑与数据断言。

## 十、第五版：把「隐性概念」搬到牌面上

### 10.1 问题不是玩家看不懂，是游戏没写

达叔在第 6 关（第一次给 JUMPZ）卡住的原话是：「在哪里比较的手上的数字是不是 0？我在指令面板里根本就没找到类似比较的功能函数牌。」

这句话不是误解，是**指认了设计缺口**：HRM 家族的规则里根本没有 `CMP` 指令——比较是**融合在条件跳转里**的（`JUMPZ` 就是「手上的数是不是 0」，`JUMPN` 是「是不是负数」；比大小则要靠 `SUB` 减完看符号）。这条元规则整个游戏里没有任何一句话说过，而面板上只印了 `JUMPZ` 六个字母，玩家唯一能做出的推断就是「这里缺了一块」。

更糟的是三级提示的第三级**直接填入参考解**——玩家拿到一份「看得见但读不懂」的程序，比没有提示更挫败。

结论：**约定俗成的隐性知识不能靠玩家自己悟**，要在界面上就地解释。

### 10.2 四处改动

| 位置 | 之前 | 现在 |
|---|---|---|
| 指令面板 | 一排按钮，只有英文缩写 | **指令牌**：上行指令名，下行一行白话（`JUMPZ` / `是 0 就跳（比较）`） |
| 程序行右侧 | 空白（只有弹性空隙） | 每行一句极短白话（`取一只` / `是0就跳` / `送出` / `写木牌` / `跳`） |
| 指令面板底部 | 无 | **解释条**：默认写「没有单独的『比较』牌：JUMPZ / JUMPN 就是比较」；鼠标停到任意指令牌或程序行上，换成那条指令的完整说明 |
| 第 6 关提示 | 「JUMPZ 不会把值弄丢」 | 第一级就点明「比较长在 JUMPZ 身上」，第二级给出骨架并说明「JUMPZ 不吃掉值，所以 0 要自己扔」 |

### 10.3 两条文案原则

1. **白话挂在指令名下面，而不是塞进 tooltip**。tooltip 要悬停才出现，而玩家看不懂的时候恰恰不知道自己该悬停哪个。
2. **默认就回答最容易被问的那句**。解释条不是空白的「悬停查看说明」，而是直接写「这游戏没有比较牌」——把玩家心里那句疑问先答掉。

实现上把文案集中到 `hrm_vm.gd` 的两张表（`OP_SHORT` 牌面白话、`OP_TAG` 行内极短标签、`OP_HELP` 完整解释），UI 只负责取值，避免同一句话在三个地方各写一遍。踩到的坑：`Label.clip_text = true` 会把最小宽度压成 0，放在 `SIZE_EXPAND_FILL` 的 spacer 边上会被挤成一条看不见的线——行内标签必须用极短文案且**不能开 clip_text**。

### 10.4 验证

界面测试 57 → **58 项（headless）/ 67 项（带窗口）**，新增断言：JUMPZ 牌面含条件字样、JUMPZ/JUMPN 的完整解释必须出现「比较」二字、解释条默认文案必须提到没有比较牌、程序行右侧必须挂上白话标签。关卡测试 **64 项**仍全绿。

## 十一、第六版：指令说明书弹窗

### 11.1 悬停不够，要能「主动问」

上一版的解释条有个前提：玩家得先把鼠标**放到某张牌上**。可达叔的原话是「不然像 JUMPZ 或 JUMPN 的函数牌，没人会知道」——问题在于**不知道自己该问什么**的时候，悬停提示永远触发不了。所以要在指令面板上放一个主动入口。

做法：指令面板标题右侧一颗 `说明书` 按钮（`F1` 同效）。点开是一个遮罩弹窗，把这关**能用的每一张牌**按用途分组逐条讲完：

| 分组 | 内容 |
|---|---|
| 搬运：羊圈 ↔ 手 ↔ 栅栏 | INBOX / OUTBOX |
| 木牌：唯一能把值存下来的地方 | COPYFROM / COPYTO |
| 算术：只在手上算，结果留在手上 | ADD / SUB / BUMPUP / BUMPDN |
| 跳转 —— 比较就藏在这一类里（没有单独的「比较」牌） | JUMP / JUMPZ / JUMPN |
| 其他 | COMMENT |

每条给三样：指令名、一行白话、完整解释（手会不会空 / 值去哪了）；`JUMPZ`、`JUMPN` 额外挂一个亮底「这就是比较」徽章。只要本关有这两条，弹窗顶部就先写一句「这游戏没有单独的『比较』牌」。

### 11.2 三个设计决定

1. **按用途分组，不按指令集顺序**。玩家的念头是「我怎么把一个 0 扔掉」，不是「J 开头的那几条」。分组标题本身就是线索。
2. **只列本关 allowed 的牌**。说明书不预告后面的关卡内容——既避免剧透，也让「这关能用什么」变成一次确认。
3. **列表可滚动，卡片不做分页**。卡片高度稳定，滚动比翻页少一次决策；同时把弹窗做宽（700px）让解释尽量两三行内说完。

### 11.3 关闭与打断

`Esc`、点遮罩空白处、右上「关闭 ×」、切换关卡（`load_level` 里调 `_close_doc()`）都会收掉弹窗。弹窗开着时 `_input` 只认 `Esc`、`_unhandled_input` 直接 return——否则空格/方向键会在背后驱动游戏（空格是「运行」，最容易误触）。

### 11.4 验证

界面测试 58 → **72 项（headless）/ 81 项（带窗口）**。新增断言：说明书按钮存在、`pressed` 能开出弹窗、**本关每一条 allowed 都必须出现在说明书里**（数量相等 + 逐条包含）、JUMPZ 的完整解释文本必须在弹窗里、「这就是比较」徽章必须存在、标题必须标出当前关卡、关闭后节点销毁、切关自动关闭。

截图模式新增 `--doc`（打开弹窗后截图）与既有的 `--op=JUMPZ`（定格解释条），都可以无头以外的带窗口方式跑。

## 十二、为什么 COPYTO 不叫 PASTE

### 12.1 直觉是对的，但落点差了一格

达叔问：「为什么我感觉 COPYTO 更应该叫 PASTE？」这个直觉抓到了真问题——`COPYTO` 这个名字确实**在语义上说了谎**，但谎点不在「该叫 PASTE」，而在「它根本不是 copy」。

看虚拟机里的两行实现（`hrm_vm.gd`）：

```gdscript
"COPYFROM":  hand = mem[n]        # 木牌不变  → 源不消失
"COPYTO":    mem[n] = hand; hand_full = false   # 手清空  → 源消失
```

| 指令 | 源 | 源是否保留 | 本质 |
|---|---|---|---|
| `COPYFROM n` | 木牌 n | 保留 | **复制** |
| `COPYTO n` | 手 | 消失 | **搬运 / 存入** |

所以 `COPYTO` 是**搬进去**，`COPYFROM` 才是**复制**。两个名字一个骗人、一个诚实，正好卡在「镜像词形」最容易被当成对称两件事的位置上。

### 12.2 PASTE 会引入三个更糟的预期

1. **粘贴不会清空剪贴板**。真用 PASTE 命名，玩家会理所当然地「粘两次」，而这里粘完手上就没了，下一次 `COPYFROM` 才能再拿——这是最容易撞的墙。
2. **粘贴暗示「刚才复制过什么」的历史**。这里没有剪贴板历史，源永远只有一个、且永远是明写的「手上的值」，PASTE 不增加任何信息。
3. **PASTE 找不到配对的词形**。若改成 `PASTE` / `COPYFROM`，一眼看不出这两个是一对；而 `COPYFROM` / `COPYTO` 的 FROM/TO 是同一介词的两端，配对关系自明。

### 12.3 真正的精确命名是 STORE / LOAD

按 CPU 的惯例，这一对应该叫 `STORE [n], reg` / `LOAD reg, [n]`——语义完全准确，也确实比两个 COPY 好。但这一版**不改名**，理由是词汇的兼容性价值高于术语纯度：玩家查原版攻略、对照其他 HRM 资料时，`COPYFROM/COPYTO` 是通用词；改了名，说明书和攻略就对不上了。

> **补记**：这条结论后来被推翻了——用 `MOVETO` 而不是 `STORE` 就同时满足了「准确」和「好懂」。见第十三章。

原则定下来：**词形沿用原版，含义补在界面上**。具体落两处：

- `COPYTO` 的完整解释加一句「注意它不是『粘贴』：粘贴完剪贴板里还留一份，这里写完手上就空了——是搬进去，不是复制一份」；
- `COPYFROM` 的完整解释加一句「木牌里那份抄完还在——这一步才是真正的『复制』」；
- 木牌分组的标题加后缀「（FROM = 从木牌拿，TO = 搬进木牌）」，让介词方向在分组层就自明。

### 12.4 这条经验可以复用到别处

凡是「玩家会用日常软件的心智模型来套」的地方，都要在界面上显式否定。当前已经处理的三处：

| 玩家默认以为 | 实际 | 界面在哪说 |
|---|---|---|
| 一定有条「比较」指令 | 比较长在 JUMPZ / JUMPN 上 | 指令面板底部解释条 + 说明书 |
| 粘贴不会清空剪贴板 | COPYTO 写完手就空 | COPYTO 的牌面白话「手变空」+ 说明书 |
| 跳转条件是「跳到第 n 行」 | 跳的是**标签**，行首那个按钮给行起名 | 第 6 关提示 + JUMP 的解释 |

## 十三、定名：COPYTO → MOVETO

### 13.1 上一章的「不改名」被自己推翻了

第十二章我判断「沿用原版词汇优先」。达叔接着抛了一个词：`MOVETO`。这个词同时解决了两件事——它**不再冒用 copy**，而且比 `STORE` 好懂（不需要先知道 CPU 是什么）。

所以最终命名是**一个不对称的词对**：

| 新名 | 旧名 | 语义 |
|---|---|---|
| `COPYFROM n` | 不变 | 从木牌抄到手上，木牌那份**还在** |
| `MOVETO n` | `COPYTO` | 把手上的搬进木牌，**手空了** |

不对称不是妥协，是**信息**：`copy` 与 `move` 的区别正是源还在不在——这在 Unix 里就是 `cp` 与 `mv`。所以词形本身就在教规则，不需要额外记。说明书里那句分组标题也顺势改成「copy 的源还在，move 的源没了 —— 和 cp / mv 一样」。

顺带把牌面白话从「写木牌」改成「搬进木牌」：`写` 是中性的，`搬` 自带「搬完这边就没了」的暗示。

### 13.2 改名的真实代价在存档上

改名不是 sed 一遍的事。玩家存档里 `saved_programs` 存的是 `{"op": "COPYTO", ...}` 这种**字符串快照**，直接改名会让老玩家的程序在执行侧匹配不到分支、在 UI 侧查不到白话（`op_tag("COPYTO")` 返回空串，行右侧一片空白）。

做法是在**入口收敛**，而不是在执行逻辑里到处兼容：

- `hrm_vm.gd` 加 `OP_ALIAS = {"COPYTO": "MOVETO"}` 与 `canon_op()`；
- 三个入口统一过一遍：`parse_program()`（关卡数据）、`make_ins()`（新建指令）、`step()` 里取 op 的那一行（兜底，任何来源的老字典都能跑）；
- `main._program_from_save()` 加载存档时也过一次，否则 UI 仍会显示旧名。

原则：**别名只在边界出现一次，内部永远只有一个名字**。这样测试与调试看到的永远是新词，不会出现「一半 COPYTO 一半 MOVETO」的中间态。

### 13.3 验证

界面测试 75 → **79 项（headless）/ 88 项（带窗口）**，其中 4 条专测迁移：`canon_op("COPYTO") == "MOVETO"`、`make_ins` 会收敛、`parse_program` 会收敛、**手工塞一条旧存档进去再 `_program_from_save` 必须变成 MOVETO**。

关卡 20 关的 `ref` 全部改用 `MOVETO`，**64 项仍全绿**——说明改名没有动到任何一条参考解的语义。

## 十四、控制栏消失：一次「最小高度预算」溢出

### 14.1 症状与误判

达叔截图问：「怎么开始运行什么的类似这些按钮不见了？」画面上 `▶ 运行 / 单步 / 重置 / 清空程序` 整排消失，只留下舞台和一行「已数 0 / 3」。

第一反应会以为是窗口太小被裁掉，但**窗口没那么小**——真正的原因是**页面最小高度超过了画布**：

```
画布 1280×800，上下页边距各 12 → 可用 776
第 10 关时 root VBox 的最小高度 = 842
```

`VBoxContainer` 不会把子项压到最小高度以下。四个子项（顶栏 / 三栏主体 / 舞台 / 控制栏）里前三个都已经顶到最小，多出来的 66px 只能由**最后一项**溢出——正好是控制栏。它不是被隐藏，是被画到了画布外面。

### 14.2 为什么是这一版炸的

三处改动叠加，把右侧栏的最小高度从 341 顶到 497：

| 改动 | 增加的最小高度 |
|---|---|
| 指令牌从 1 行英文变 2 行（32 → 46） | 关卡 7 张牌 = 4 排 → +56 |
| 新增底部解释条（46） | +46 |
| 关卡越靠后可用指令越多 | 第 1 关 2 张、第 10 关 7 张、第 20 关 11 张 → 线性膨胀 |

关键在于第三行：**面板内容量由关卡数据决定**，这是典型的「今天够用、明天加两关就炸」的结构。所以不能只调数值。

### 14.3 三条改法（按重要性排序）

1. **让指令牌能滚动**（根因修复）。把 GridContainer 包进 `ScrollContainer`，最小高度锁 144px（正好三排），第四排起滚动。从此「本关有几张牌」不再影响页面高度——这是把「随内容增长」改成「固定预算」。
2. **舞台改成可伸缩**（让位顺序）。原来 `custom_minimum_size = 252` 是硬值；改成最小 190 + `EXPAND_FILL`，空间富余时它自己变高，吃紧时**先缩舞台而不是缩掉控制栏**。顺序原则：控制栏是玩家唯一必须一直看得见的东西，它排最后。
3. **压缩留白**（余量）。解释条 46→40、牌高 46→44。

改完：最挤的第 5 关 737 / 776，**留白 39px**。

### 14.4 护栏：把「最小高度」写进测试

这次的问题截图看不出来（1280×800 截图里一切正常，只有玩家的窗口才露馅），所以必须用断言锁死：

```gdscript
for lv in range(main.levels.size()):
    main.load_level(lv)
    await process_frame
    var need: float = main.root_box.get_combined_minimum_size().y
    _check(need <= 776.0, "第 %d 关最小高度 %.0f 超过可用 %.0f" % [lv + 1, need, 776.0])
```

再补三条：控制栏必须是根 VBox 的**最后一段**、第一个按钮文案含「运行」、底边在画布内。界面测试 79 → **83 项（headless）/ 92 项（带窗口）**。

**经验**：凡是「布局节点数量/文字长度会随数据变化」的界面，都要有一条「整页最小高度 ≤ 可用高度」的断言。截图只能证明某一关好看，证明不了每一关都装得下。

### 14.5 排查手法

别盯着截图猜。写一个一次性探针脚本加载主场景，打印根 VBox 和每个子段的 `get_combined_minimum_size()` 与 `size`，一眼就能看出是谁把页面顶高的：

```
$ godot --headless --path hrm_godot --script tests/_probe.gd
root vbox min = (1002.0, 842.0)  size = (1252.0, 842.0)
  HBoxContainer min=(342.0, 29.0)   ← 顶栏
  HBoxContainer min=(1002.0, 497.0) ← 三栏主体：就是它
  PanelContainer min=(2.0, 252.0)   ← 舞台
  HBoxContainer min=(848.0, 34.0)   ← 控制栏（被挤出画布）
```

探针用完即删，不进仓库。

## 十五、关卡盘点：哪些是复刻、哪些是自造

达叔问得直接：这 20 关是照抄 Human Resource Machine，还是自己 DIY 的？诚实的答案是**一半一半，而且重合的那一半不是巧合**。下面逐关摊开。

### 15.1 逐关对照

| # | 我们的关 | 对应的原版关（对照第二章抓到的关卡名） | 关系 |
|---|---|---|---|
| 1 | First Sheep | Mail Room | 直接对应：原样搬运 |
| 2 | All Night Long | Busy Mail Room | 直接对应：加 JUMP 成环 |
| 3 | Copy That | Copy Floor | 直接对应：把常量重复输出 |
| 4 | Swap Around | Scrambler Handler | 直接对应：成对交换 |
| 5 | Triple Flock | Tripler Room | 直接对应：×3 |
| 6 | Shoo the Zero | Zero Exterminator | 直接对应：丢掉 0 |
| 7 | Keep the Zero | Zero Preservation Initiative | 直接对应：只留 0 |
| 8 | Eight at Once | Octoplier Suite | 直接对应：×8 |
| 9 | Take Away | Sub Hallway | 直接对应：成对相减 |
| 10 | The Bigger One | Maximization Room | 直接对应：成对取大 |
| 11 | Never Negative | Absolute Positivity | 直接对应：绝对值 |
| 12 | One More | 无 | **自造**：把 BUMPUP 拆出来单独成关做教学 |
| 13 | One Less | 无 | **自造**：BUMPDN 对偶关 |
| 14 | Rainy Night | Rainy Summer | 直接对应：成对求和 |
| 15 | Running Total | Cumulative Countdown 一系 | **改规则**：改成前缀和，不用倒数 |
| 16 | The Smaller One | The Littlest Number 一系 | 直接对应：成对取小 |
| 17 | Three Signs | Three Sort 一系 | **自造**：三路分支返回 −1 / 0 / 1，还预置了常量木牌 |
| 18 | Same Sheep | Equalization Room | **改规则**：原版是相等才输出，这里反过来——不等就两个都输出 |
| 19 | Count Till Sleep | 无（0 当终止符是 Year 2 的题型） | **自造**：读到 0 收尾并输出总和 |
| 20 | Sum to N | 无（1+2+…+n 属于 Year 2 的复合题） | **自造**：还额外要求每轮把累加器清零 |

统计：**直接对应 13 关 / 改规则 2 关 / 自造 5 关。**

### 15.2 数值是自定的，题型不是

必须分清两件事：

- **数值序列（inbox / outbox / mem_size / allowed 组合 / 目标 SIZE·SPEED）全部自定。** 原版的这些数据编译在自研节点二进制里，第二章逆向时就确认了不可读——所以不存在"抄数值"这件事，是从机制反推出来的。
- **题型与教学顺序明显沿着 Year 1。** 先搬运 → 再成环 → 再存常量 → 交换 → ×3 → 过滤 → 只留 → ×8 → 相减 → 取大 → 绝对值……这条顺序本身就是原版最值钱的设计资产（第二章说它"白送了叙事结构与关卡顺序"），我照着走了。

也就是说：**抄的是教学曲线，不是数据。** 这也解释了为什么玩起来"感觉一样"——数值不同（我们 ×3 用的是 1/2/3，原版是另一组），但解题思路一模一样。

### 15.3 为什么重合躲不掉

这套机制里，能出的题型其实非常少。11 条指令 + 无间接寻址 + 无计算跳转（第二章 3.1 已论证），可玩的只有：

> 搬运 / 成环 / 存常量 / 成对交换 / 常数乘 / 过滤某一类 / 比较取大取小 / 求符号 / 累加 / 用哨兵收尾

只要做同机制游戏，都会收敛到这批题型上——这不是"抄"，是**题型的空间只有这么大**。真正的差异只能来自：换皮、增加机制（禁招、双指标对抗、预置内存、模式切换）、以及难度曲线编排。

### 15.4 三条路线，供拍板

| 路线 | 做法 | 代价 | 适合 |
|---|---|---|---|
| **A 骨架保留** | 13 关对应关作为教学骨架保留，对外话术改成"参考同类教学曲线"，不进 40 关正式版 | 最低 | 现在这版原型 |
| **B 换掉一半** | 用已验证的 5 个自有方向（禁招关 / 双指标对抗 / mem_init 预置 / 模式切换 / 流形状）替换掉 6~8 关复刻关 | 中：要重新设计并验证参考解 | 准备对外发布 |
| **C 只留最小教学集** | 复刻关压到 5 关以内，其余全靠自有机制 | 高：新手留存风险 | 想做"有辨识度"的作品 |

我的建议是 **B**：前 6 关必须保留（那是这套机制的最低教学集，任何同类游戏都得有），第 7 关以后逐步换成自有机制。`tests/test_ideas.gd` 里已经验证过 5 个方向的参考解可跑通，随时能落地成关卡数据。

## 十六、第七版：把「软件感」从界面上剥掉

达叔的原话是「总感觉太软件化了，没有作为游戏的美感」。这句话很准，但它指向的不是"不够花哨"，而是**层级没有建立**——界面像一张填满控件的表单，而不是一个摆着道具的场景。

### 16.1 先诊断：软件感的五个来源

拿《UI 设计军规》逐条对，能对出五条病根：

| # | 症状 | 对应军规 | 直觉解释 |
|---|---|---|---|
| 1 | 三层侧栏 + 中间工作台 + 底部舞台，**全是同一档深棕底 + 同一圈 1px 边** | 规则 19：别急着画 1px 灰线，先用色差/留白/阴影分区 | 所有东西一样重，眼睛不知道该看哪 |
| 2 | 全屏找不到一处亮面，亮度全挤在 10%–25% 之间 | 规则 03：层级靠对比，不靠字号 | 一起发闷，像隔着一层灰玻璃 |
| 3 | 主操作（运行）和次要操作（重置）长得一模一样 | 规则 14/15：一屏只能有一个主操作 | 没有"下一步该点哪"的引导 |
| 4 | 下拉框、数字框、滚动条是引擎默认长相 | 规则 06：原生控件会立刻出卖"这是软件" | 材质不统一，木牌里嵌了塑料件 |
| 5 | 按钮按下去没有位移、悬停没有抬升，行不出来回自动让位 | 规则 25：反馈要短、要吝啬、但必须有 | 像点一张图片 |

前四条在第五、六版已经修掉了大半（`ui_kit.gd` 统一材质、按钮三态厚度、纸条代替表格行、自建拖拽）。这一版解决的是**第二条和最后一条**，顺手把整套语言收口成一个可复述的基调。

### 16.2 基调卡

> **深夜牧场 · 木牌与牛皮纸**
>
> 场景是一张深夜的木桌：四周是钉在桌上的木牌（关卡 / 任务 / 指令面板 / 控制栏），
> 中间摊着几张牛皮纸纸条（程序行），远处是正在发生的牧场（舞台）。
>
> - 木牌 = 容器：暖褐底、2px 木边、向下 8px 投影（离开桌面的唯一证据）
> - 纸条 = 内容：浅牛皮纸、左侧 3px 色带表示状态、薄影
> - 墨 = 纸上的字：不用纯黑，用三个深棕档（`INK_1/2/3`）分主次
> - 暖黄（`AMBER`）= 可以拿起/已经选中；绿 = 正在执行；赭红 = 出错
> - 唯一的动效：正在执行那一行的色带呼吸 + 舞台上的萤火虫

有了这张卡，之后任何一个新控件该长什么样都不用再问——**它是木牌、还是纸条？**

### 16.3 明暗反转：为什么把唯一的亮面给程序区

改版前：深木底 + 深棕程序行（`#3b2f22`）。改版后：深木底 + **浅牛皮纸程序行**（`#c4b394`）。

理由不是"浅色好看"，而是**焦点应该落在玩家真正动手的地方**：

- 玩家 90% 的时间在拼程序，视线必须第一个落在这里；
- 全场只有这一块亮面，它自己就成了焦点，不需要加任何边框、发光、箭头；
- 纸张是浅的，字就必须是深墨——顺便解决了"暖白字在暗棕底上发灰"的可读性问题（正文对比度从约 4.8:1 提到约 6.4:1）。

代价是纸上所有内嵌控件都要重做一遍皮肤。这里踩了一个坑：**纸上不能描 1px 灰边**，一描就变回网页表单。最终用的是「比纸深一档的实色块 + 顶边一道更深的线」——光从上方来，凹槽的顶沿一定最暗，那道线就是"凹进去"的证据。

### 16.4 命中条目一览

| 军规条目 | 这次怎么落地的 |
|---|---|
| 02 相邻元素要成组 | 面板内 padding 统一 10、组间距 10、行间距 4，三档间距只保留三档 |
| 03 层级靠对比 | 亮纸 vs 暗木（明度差），而不是靠字号大小 |
| 06 别用原生控件长相 | 下拉/数字框/滚动条全部换皮：纸面凹槽 + 墨色箭头 + 暖色滚动条 |
| 14 浅底深字更耐看 | 纸上用 `INK_1/2/3` 三档墨色代替单色 |
| 15 一屏一个主操作 | 「运行」用实心暖黄，其余按钮是木片 |
| 16 用强调色做焦点 | 区块标题 = 3px 暖黄竖条 + 文字 |
| 19 用影分区，别画线 | 所有木牌靠投影分层；纸条也加了薄影（没有影，纸就只是"填了色的格子"） |
| 25 动效要稀缺 | 只有"正在执行"那一行呼吸，且改成呼吸**明度**（纸不透明，呼吸透明度看不出来） |

### 16.5 舞台补光：最该亮的地方原来最暗

舞台是唯一的"游戏"，但改版前它是整屏最暗的一块（草地 `#1e3527`、牧羊人 20px 高）。三处改动：

1. **月亮光晕**：从"一个半透明圆"改成 9 圈递减同心圆。单个半透明圆像贴了个光盘，递减才像光在空气里散开。
2. **光池**：月亮在草地上打一块冷光斑（固定），牧羊人脚下有一圈暖光（跟着人走）。舞台暗不要紧，但必须有"光落在哪里"的证据。
3. **纵深与小路**：草地分 7 段往下压暗（脚边亮、镜头前暗）；加一条踩出来的土路——羊每天从羊圈被抱到栅栏，路是走出来的（顺带把中间的空草填掉）。

羊圈里的羊也从 1.55 倍放大到 1.72 倍，编号在羊毛上更清楚。

### 16.6 为什么单独抽一层 `ui_kit.gd`

改版前颜色常量散在 `main.gd` 里 96 处，改一次配色要动 96 个地方，且「木牌的边」和「按钮的边」没有共同定义，越改越散。

抽出 `ui_kit.gd` 之后，UI 代码只说**角色**，不说颜色：

```gdscript
Kit.board(bg, radius, pad, border, 2, 8)   # 这里是一块木牌
Kit.strip(bg, bar, 3, 4, 3)                 # 这里是一张纸条
Kit.button_boxes(bg, 5)                     # 这里是一个能按的东西
Kit.well_paper()                            # 这里是纸上挖的一个槽
```

好处不是"少写几个字"，而是**下次换基调只改这一个文件**。基调卡（16.2）能成立，靠的就是这个边界。

### 16.7 自检与回归

- `tests/test_levels.gd`：64 项（20 关参考解 + 4 个负向用例）——全绿
- `tests/test_ui.gd`：92 项（布局护栏 + 说明书断言 + MOVETO 迁移）——全绿
- `tests/test_ideas.gd`：5 项（自有机制方向的参考解）——全绿
- 布局余量：最挤的第 5 关 747 / 776（留白 29）。**注意投影不参与最小高度计算**，所以这一版加的所有阴影都没有吃预算。

### 16.8 一个顺手修掉的坑

截图脚本之前用 `OS.get_cmdline_args()` 读 `--shot=`，在某些启动方式下读不到参数，导致截图**静默跳过**、进程不退出（看起来像"卡死"）。Godot 4 把 `--` 之后的参数单独收在 `OS.get_cmdline_user_args()`，两个都要扫。

> 教训：命令行工具"什么都没输出"和"卡死"是两种病，先用探针把两种情况分开，再改代码。

## 十七、换向：从「深夜牧场」到「明亮卡通牧场」

### 17.1 为什么推翻了第十六章

第十六章那套「深夜牧场 · 木牌与牛皮纸」在工程上是干净的：层级清楚、对比度达标、材质统一。但它解决的是**「像不像软件」**这个问题，回答的是「怎么做得不像后台表单」。

达叔看完给的判断是更高一层的：**「风格倾向是明亮卡通休闲游戏那一挂的最好」**，并给了参考图（Township / Coin Master 一类）。这不只是配色偏好，而是把问题从「怎么不像软件」换成了「怎么像一款手机休闲游戏」。

两套语言几乎每条都相反：

| | 深夜牧场 | 明亮卡通牧场 |
|---|---|---|
| 底色 | 10%–25% 明度，压暗 | 中高明度，饱和 |
| 分区手段 | 投影 + 极窄色差 | 三层明度阶梯 + 粗描边 |
| 描边 | 尽量不画 1px 灰线 | 反过来，**2–3px 深色实边是主角** |
| 圆角 | 4–6px（稳） | 9–10px（圆润） |
| 字 | 暖白 / 浅棕墨 | 纯白 + 深蓝描边（无论底色） |
| 强调 | 一处暖黄灯笼光 | 金色 + 绿色双强调 |

结论：这是一次**重定基调**，不是微调。做的时候没有推倒结构，因为第十六章已经把材质收进了 `ui_kit.gd` —— 常量名一个没改，只换值，`main.gd` 里近百处引用一次性生效。这正是上一章抽那一层的回报。

### 17.2 新基调卡

> **明亮卡通牧场（Casual Farm）**
>
> 白天的牧场。深蓝的天压在四周，中间是几块比天更亮的中蓝面板，
> 面板里铺着更亮一档的蓝色卡片。主操作用绿，强调用金，文字一律白字加一道深蓝描边。
> 所有块状物都有 2–3px 深色描边和一道几乎不模糊的硬影 —— 它们像贴纸一样贴在屏幕上。

五条可复述的规则（也是判断「够不够味」的检查表）：

1. **粗描边** —— 外圈 2–3px 深色实边。卡通感的第一来源，不是圆角。
2. **大圆角** —— 9–10px。块头越大，圆角越大。
3. **三层明度** —— 页面底 `#05223f` → 面板 `#0e5a96` → 卡片 `#1470b4`。三级阶梯撑起层级，不靠描线。
4. **硬投影** —— 偏移 4px、模糊 2px。模糊一过 4px 就变网页卡片。
5. **白字描边** —— 白字 + 深蓝描边，压在绿/金/蓝任何底上都读得清，不用为每种底色单独挑字色。

### 17.3 这一版动了什么

- **`ui_kit.gd` 全部常量换值**（名字不动）：面板 / 卡片 / 描边 / 文字 / 强调色。
- **`board()` 与 `button_boxes()` 改硬影**：`shadow_size` 从 8 降到 3，`offset` 从 3 提到 4。
- **`card()` 新增**：整圈描边的圆角卡。和旧的 `strip()`（只画左边一条色带）分工 —— 旧版状态靠左色带，新版状态靠整圈描边。
- **程序行四态改成「只换描边颜色」**：普通=深边、选中=白边、执行中=绿边（呼吸）、出错=红边。形状不变、只变色，整列扫下来才有节奏。
- **关卡列表选中**：从「左侧暖黄书签」改成「整圈白框 + 提亮底色」，和程序行用同一套选中语言 —— 一个界面里只能有一种「被选中」的表示法。
- **`_label()` 自动加描边**：亮度 > 0.62 的字一律配深蓝描边，3–4px。省掉了上百处调用点的修改。
- **主操作换绿**：`运行` 从金色改成 `#3ebc1a`，`下一关` 改回金色。
- **舞台改成白天**：星空 → 太阳（同心圆光晕保留）、云 → 白边厚云、月光斑 → 日光斑 + 接地影、草地调亮，新增树 / 灌木 / 小花 / 蝴蝶。
- **羊的编号**：描边从 2px 降到 1px —— 2px 的浅色描边在 11–20px 字号下几乎把字吃掉，远看是一团白。

### 17.4 顺手解决的一个真 bug

一直在调的「数字框上下箭头丑」，根因不是配色，是**主题项名字写错了**：

```gdscript
# 之前（静默失效，不报错）
theme.set_stylebox("up_button", "SpinBox", ...)
theme.set_color("up_icon_modulate", "SpinBox", ...)
```

引擎里根本没有 `up_button` 这个样式块。正确名字是 `up_background` / `down_background`，图标是 `up` / `down`（用 `ThemeDB.get_default_theme().get_stylebox_list("SpinBox")` 一查就清楚）。名字不对不会报错，只会**什么都不发生** —— 所以那对箭头从第一版起就一直是引擎自带的灰色三角。

修好之后，箭头换成自绘的刻痕三角：4×4 超采样算覆盖率当 alpha，得到干净抗锯齿的实心三角，不引任何外部图。步进键的底也换成了「顶边提亮」的小木片。

> 教训：主题项、属性名这类字符串常量，写错了是**静默失败**。改不动的时候先写探针把引擎里的真名列出来，别猜。

### 17.5 回归

| 测试 | 结果 |
|---|---|
| `test_levels.gd` | 64 项，0 失败 |
| `test_ideas.gd` | 5 项，0 失败 |
| `test_ui.gd`（带窗口） | 92 项，全部通过 |
| 布局余量 | 最挤的第 5 关 744 / 776（留白 32） |

换配色不影响逻辑，三套回归全绿。布局余量比上一版还多了 3px，因为大圆角让卡片的最小高度略降。

### 17.6 还没做的（下一轮）

- **指令牌还是「长条按钮」**：参考图里的道具格是**方形图标牌 + 底部名称条**，下一步该把 `INBOX` / `MOVETO` 这类牌子做成方形格，配一个 pictogram 图标。
- **面板没有竖向渐变**：`StyleBoxFlat` 只能平涂。要做出参考图那种「上亮下暗」，得叠一层 `GradientTexture2D` 的 `TextureRect`，或者换 9-slice 贴图。
- **图标体系缺失**：粗描边能撑住形，但一个休闲游戏最终还是要靠图标（金币、羊、锁、勾）来传达含义。

### 17.7 关于买素材

调研过 LayerLab「GUI Pro - Casual Game」（$23.99，1200+ PNG，9-patch 需要自己切）、Storybook Fantasy UI（$9.95）、Emberforge（$1）等 10 套。结论：

- 风格最对味的是 **LayerLab Casual Game**，和参考图同一族。
- 但它解决的是**贴图**，不解决**结构**。我们的控件丑，根因是主题项名字写错 + 结构没按卡通语言搭，这两条自己就能修，且已经修完。
- 真正值得买的是它的 **320 个 pictogram 图标 + 90 个道具图标** —— 这部分自己画不划算。

所以建议：**结构和配色自己维护（已完成），图标将来按需买**。这样 `ui_kit.gd` 始终是唯一真源，不会被素材包的风格绑死。

## 十八、接入贴图皮肤（Crisp Kit Free）

### 18.1 为什么最后还是用了贴图

第十七章结尾判断「结构自己维护、图标将来按需买」。但控件仍然有个绕不过去的问题：**手搓 `StyleBoxFlat` 只能做平涂**，做不出素材里那种「顶部一条高光 + 底部一道厚边 + 圆角带轻微内阴影」的塑料片质感。这不是配色能补的，是贴图才能给的。

选的是 **Crisp Kit Free（Anipixels）**，免费、可商用、免署名，57 件。关键优势是给了 **SVG + `sheets.json`**，里面直接写着每个部件的九宫格边距。

> 授权口径要说准：itch 的官方 tags 含 `ai-generated` / `ai-generated-code` / `ai-generated-graphics`。作者的说法是「由 Claude 设计、用代码程序化绘制，未使用 AI 图像生成器」——两句话都对，但**对外按 AI 生成披露**。

### 18.2 第一件事不是导入，是重切

原包是给手机大控件做的：`input_normal` 是 160×48，九宫格上下边距加起来 32px；而程序行只有 30px 高，原样用会把整行顶开。

`tools/import_crisp_skin.py` 做的事：按目标高度等比缩放图片，**并把 slice 边距同比例缩放**。两者必须一起缩 —— 只缩图不缩边距，边距会比图还大，九宫格直接退化成整张拉伸，圆角糊成一团。

输出 `hrm_godot/assets/ui/crisp/*.png` + `crisp_slices.json`。

### 18.3 接入层：素材缺失必须能回退

`scripts/skin_crisp.gd` 单独一层，原则是**没有素材时游戏照跑**（回退到第十七章那套手搓样式），而不是报错或者静默少一块。`ok()` 一票决定走哪条路。

这一层里踩到两个坑，都值得记：

**坑一：SpinBox 自己根本没有 `normal` 这个主题项。**
它的可见部分是里面那个 `LineEdit`。给 SpinBox 设 `normal` 不报错、也什么都不发生。必须先 `get_line_edit()` 拿到底层控件再设。

**坑二：步进键的宽度跟着图标宽度走，不跟样式块边距走。**
给 `up_background` 调 `content_margin` 完全无效。想要「键宽一点、三角还是那么大」，只能把三角画进一张更宽的透明图里（`_tri()` 里做了这件事）。

另外步进键最后**没有用素材**：`button_flat_normal` 自带一圈薄荷绿描边，染成蓝色之后那道绿边还在，挤在白输入框右边很刺眼。改成自绘白片 + 浅灰描边，和贴图输入框的描边是同一个灰度，接在一起才像同一个控件。

### 18.4 白按钮 = 整套配色

素材里 `button_flat_normal` 是纯白的。因为 `白色 × 任何色 = 那个色`，所以一块白按钮可以染出任意配色：次操作用 `modulate_color` 染成蓝色，主操作直接用原色的绿按钮。这就是「一套素材撑起整套层级」的做法，不必为每个颜色单独找图。

`_button()` 因此多了一个 `kind` 参数：`"primary"` 走原色绿，`"secondary"` 走染色蓝，空串回退到手搓。

### 18.5 结果

| 部位 | 用了什么 |
|---|---|
| 数字框 / 输入框 | `input_normal` 九宫格 |
| 步进键 | 自绘白片 + 自绘刻痕三角（素材的绿边不可用） |
| 下拉框 | `input_normal` + 深墨 V 形箭头 |
| 滚动条 | `progress_track` / `progress_fill` |
| 主按钮（运行 / 下一关） | `button_medium_*` 原色 |
| 次按钮（单步 / 重置 / 清空 / 上一下一关 / 说明书） | `button_flat_normal` 染色 |

回归：`test_levels` 64 / `test_ideas` 5 / `test_ui` 92，全绿。布局余量仍是 744 / 776 —— 贴图边距没有吃预算。

### 18.6 还没做的

面板仍然是纯色平涂。参考图里那一挂是**白卡压深蓝底**，那才是「休闲手游」最强的特征；但要改就得把全界面文字从白翻成深色，是一次伤筋动骨的手术。留作下一轮，等确认方向再动。

## 十九、两处「玩家看不出来」的修复

第十一版之后拿到两条反馈，都不是「丑」，而是**信息没传到**：

> 参数跟底下木板编号的关联性提醒太低了；标签这块的内容也非常难注意到这里可以互动编辑。

这两条是同一个病：界面把东西画出来了，但没告诉玩家「它和谁有关系」「它能被点」。

### 19.1 参数 ↔ 木牌编号：把对应关系写死

改之前的状态：木牌左侧飘着一枚 9px 灰字当编号，几乎全是「值」在抢注意力；被选中的行引用某块牌时，舞台只在那块牌头顶挂一个小三角。玩家看到的是「有块牌子抬起来了」，看不出**是因为哪个数字**。

三处一起改：

1. **编号变成牌子上的一块**，不再是飘在外面的灰字。左边一格深色底，和「值」用一条木色分隔线切开，读作「第 N 块牌」。
2. **编号格反过来做**：奶白底 + 深棕字（普通）／琥珀底 + 深棕字（被引用）。之前是深底浅字，在棕色木料上糊成一片，等于没写。
3. **被引用时加一枚「木牌 N」对照牌**，挂在牌顶，中间一个向下三角指向牌子。这一步是关键 —— 它把编辑器里那个阿拉伯数字和草地上那块牌子**直接用文字对上号**，不需要玩家自己推。
4. **表头从「参数 / 跳转目标」改成「木牌编号 / 标签」**。`参数` 是个实现词，`木牌编号` 才是这个世界里存在的东西。

联动数据流：`main._sync_stage_link()` 读当前选中行，`MEM_OPS` 之类带编号的指令 → `stage.link_slot(N)`；其余 → `-1`。在 `_select` / `_after_edit` / `_set_arg` 三处调用，所以「选中行」「改参数」「撤销重做」都会同步。

### 19.2 一层绘制顺序的坑

「木牌 N」对照牌第一版是跟木牌一起画的，结果**正中那块牌被牧羊人整个盖掉**（木牌在草地层，牧羊人站在牌子前面）。截图里看得一清二楚。

修法：提示牌单独一趟 `_draw_link_callout()`，排在 `_draw_shepherd()` 之后、`_draw_hud()` 之前。教训是通用的 —— **凡是「提示类」元素，都不该跟被提示的物体同层绘制**。

### 19.3 标签：从标点符号变成格子

改之前空标签是一枚 `55%` 透明度的「·」。那看着像句号，没有任何人知道它能点。

改成两个明确态：

| 态 | 画法 | 读作 |
|---|---|---|
| 空 | 深色凹槽 + 浅色细边 + 琥珀「+」 | 这里还空着，能往里写 |
| 填过 | 整块琥珀贴纸 + 深棕字 | 这里已经写了 |

再配 `CURSOR_POINTING_HAND` 和悬浮说明（`点一下循环 无 → a → b → c → d`）。悬停时凹槽边框转琥珀、底色提亮 —— 鼠标一上去它就活了。

配色上有个刻意的决定：**整个界面只有「标签」是暖色**。深蓝行卡上一块琥珀，不用加箭头图标也能跳出来。

### 19.4 顺手修的：数字框的步进键

参数框右边的两个上下键一直是「两块淡片 + 一撮灰毛」。查了一圈：

- 一开始以为键宽跟图标宽度走，把三角塞进 19×5 的透明图里 → 更糊；
- 改成 11×9 想让它变高 → 变成一块带缺口的小方块；
- 换成纯红色块测试 → **一样淡**，说明不是形状问题，是这么小的键里根本放不出图标细节。

最后放弃跟图标较劲：**把底做深**。`#16324a` 深蓝底 + 引擎自带的浅灰箭头，对比度天然够，形状还是引擎调好的那个。顺带把 `SpinBox` 高度从 24 降到 22 —— 24 会顶出行卡上下各 1px，白输入框在深蓝行上多出两个白角。

> 这条记进 `skin_crisp.gd` 的注释里了：**小控件别改图标，改底色。**

### 19.5 顺手加的调试参数

`--sel=N`：启动时选中第 N 行，用于截图核对联动提示。跟已有的 `--shot` / `--level` / `--run` 一套。

```bash
godot --path hrm_godot --resolution 1280x800 -- --level=17 --sel=5 --shot=<绝对路径>
```

## 二十、HUD：把「软件」改成「游戏」

> 达叔：**「控件皮肤美化效果有了，唯一不舒服的是 HUD 布局，总感觉这是一个软件，并不像一个游戏。」**

这句话把问题定位得很准：皮肤（贴图、圆角、描边、硬影）已经有游戏味了，
所以「像软件」不是材质问题，是**布局语法**问题。

### 20.1 先诊断：哪几处具体在说「我是软件」

对着截图逐条数，有五个地方在发出「软件」信号：

| 位置 | 原来的样子 | 为什么像软件 |
|---|---|---|
| 顶部 | `SHEEP COUNTER` + 弹簧 + 「上一关」「下一关」两个方块 | 这是**窗口标题栏**：产品名在左、窗口动作在右 |
| 底部右侧 | `SIZE 20/20  SPEED 0.00/11.33  0 周期 · 3 件  就绪` | 这是**IDE 状态栏**，VS Code 最底下一模一样。一个信息平铺成一句话，谁都不是主角 |
| 左栏 | `#01  First Sheep  ★ 8 · 20`（纯文字行） | 这是**文件树 / 清单** |
| 章节标题 | 一根裸竖条 + 文字 | 这是**文档小节标题** |
| 纵向比例 | 舞台占屏高 **23%** | 这是**带预览窗的软件**，不是有画面的游戏 |

### 20.2 一条总纲：游戏给每个信息一个「东西」

软件用**位置**组织信息（第 3 列、第 2 行）。游戏用**物体**组织信息（一枚徽章、一只仪表、一颗星）。

所以这一版的每处改动都是同一个动作 —— **把一行文字换成一个有体积的东西**：

| 原来 | 现在 | 为什么这样就好 |
|---|---|---|
| `#17 Three Signs` 一行字 | 一枚关号**木牌**（大号 `17` + 小字 `/ 20`） | 「第几关」有了体积。文字没有体积，牌子有 |
| 没有星级 | 三颗**★**，拿到亮、没拿到暗 | 空心/实心是最古老的进度语言，不需要解释 |
| 「上一关」「下一关」两个方块 | 两个**圆形** `‹ ›` | 圆形在界面里是一种语法：**圆 = 方向，圆角块 = 命令**。散着用会像棋子，所以全屏只允许「翻向另一关」用圆 |
| `SIZE 20/20` | 凹槽表：小字「指令」+ 大字 `20/20` | 拆成两行后，表头退成灰、数字顶上去，**余光就能扫到变化** |
| 纯文字「就绪」 | `● 就绪` | 圆点是「灯」，纯文字是一句日志 |
| `#01 First Sheep` | `[01]` 圆徽章 + 名字 | 左边一列读成**关卡节点串**，不是清单 |
| 「关卡 16 / 20 完成」 | 一行数字 + 一根会涨的**进度条** | 同一个信息，条子让人想填满，句子不能 |
| 裸竖条 + 标题 | 深底**铭牌** | 套一层底，它从「标题」变成「摆着的东西」 |

顺带两条去重：

- 抬头有关号了，工作台顶上就**不再写 `#17`**，只留关卡名。每屏说两次「你在第几关」是导航栏的做法。
- 程序区表头（`#` / `标签` / `指令` / `木牌编号`）保留但压到 10px、55% 透明 ——
  它是「表格」的最后一点残留，但**删了玩家就不知道右边那列数字是什么**。留着，不许它抢视线。

### 20.3 纵向比例：这才是「像软件」的主因

皮肤再像游戏，画面只占 23% 也还是「软件 + 预览窗」。数羊是编程游戏，编辑器必须大，
但画面不能小到像个监控画面。目标是把它拉到 **28%**。

约束是硬的：**根 VBox 最小高度 ≤ 776**（1280×800 画布），一到 777 底部的运行按钮就被挤出屏幕。

所以不能直接给舞台加高，得先**在别处把高度腾出来**：

| 动作 | 省下 |
|---|---|
| `scroll_pal` 最小高 144 → 118 | 26 |
| `lbl_op_help` 最小高 40 → 26 | 14 |
| `pv` / `right` 的 separation 各降 2 | ~6 |
| `p_stage` 最小高 180 → 186（先垫高，再由 ratio 分配） | −6 |
| **净效果** | 余量 32 → **48** |

> `144` 原来是按「一排牌 40 高」估的，实测一排 ~34、间距 6，三排只要 114。
> **一个估错的常量，白占了 26px 的整屏高度** —— 这 26px 现在是舞台的。

再给 `p_stage` 一个 `size_flags_stretch_ratio = 1.8`（原来两栏都是 EXPAND，默认 1:1）。
结果是舞台 185 → **225**，占比 23% → 28%。

顺带把地平线从 `size.y - 62` 压到 `size.y - 78`：
原来天空占舞台的 2/3、草地只有薄薄一条，羊像是走在栏杆上。舞台加高后这个比例更刺眼。

### 20.4 跟着舞台一起塌的三处坐标

改地平线是**会连累别人的**，这一版踩了两个：

**① 栅栏挂牌飞出舞台。** 挂牌挂在栅栏顶再往上 64，合计在 `fy` 之上 148px。
舞台一矮（`fy` 变小），挂牌的 y 就变成负数 —— 直接画到编辑区上面去。
修法：栅栏 84 → 66，挂牌改成**吊在栅栏顶内侧**（`top - 36`），吊线朝下接横杆。

**② 「羊圈 INBOX」标签压在羊脸上。** 标签写死在 `fy - 54`，而羊是 `fy - 24` 起、高约 52，
头顶落在 `fy - 76` —— 54 正好在脸中间。修法：抬到 `fy - 90`。

> 通用教训：**凡是写死在 `fy - N` 的坐标，都要检查 `N` 有没有超过上方可用空间。**
> 舞台高度是会变的（窗口一缩就变），这些常量不会跟着变。

### 20.5 顺手修的一个真 bug：左栏不跟人走

`_refresh_level_buttons()` 重建列表后滚动位置回到顶部。玩家点「下一关」，
抬头写着 17，左栏看得见的是 01~12 —— **两边对不上，人就不知道自己在哪儿**。

修法：重建后 `await process_frame`（刚 add_child 的按钮还没算出尺寸，这时候滚会滚错位置），
再 `ensure_control_visible(当前关)`。

### 20.6 背景加了一层远景（然后发现没用）

想法是对的：面板之间有 8~10px 的缝，缝里如果只是纯色渐变，整屏就是「几个带框的区域」；
缝里能看见山，它才是一张画。

所以加了一层 `_draw_scenery()`：月亮 + 九颗星 + 三层正弦山脊，强度压到 alpha 0.06~0.22。

**结果：几乎看不见。** 面板占了 96% 的屏幕面积，缝太窄。
这一层现在留着（没什么坏处，将来面板留缝变宽就有用），但**它不是这一版的主力**。
真正让画面变「大」的是 20.3 的纵向重分配。

## 二十一、通关反馈与一个「按钮自己吓跑自己」的 bug

### 21.1 通关原来只是「把下一关按钮显示出来」

上一版通关时发生的事：状态文字变成「● 任务完成」、底部冒出「下一关」按钮、舞台上的牧羊人开始冒 zzz。

问题在于**这三件事都不占据画面**。玩家正盯着自己刚写完的程序，根本不会注意到底部一行小字变色了。一个事件如果没有占据画面，在玩家眼里就等于没发生。

所以这一版把通关拆成两层：

| 层 | 谁来做 | 内容 | 为什么在这层 |
|---|---|---|---|
| **世界** | `stage.gd` | 彩纸、星爆、栅栏上的羊蹦跳、牧羊人睡着 | 这是「牧场里发生的事」，观众是玩家 |
| **系统** | `main.gd` | 结算卡（星级 / 指令 / 速度 / 徽章 / 去向） | 这是「一局的账」，观众是玩家本人 |

两层**刻意错开 0.85 秒**：先让彩纸飞，再弹卡。卡片立刻盖上来，玩家就只看到一张表，看不到舞台上发生了什么。

### 21.2 彩纸为什么不用粒子节点

三个决定，都是踩过或想清楚了才写的：

1. **全部 `_draw` 现算**，不用 `GPUParticles2D`。原因很实际：粒子系统有时候要等一帧才吐第一帧，截图脚本会拍到空画面。整个场景本来就全是 `_draw`，多这一层不多。
2. **随机数必须是确定性的**（`_hash01(i)`）。`_draw` 每帧都跑，用 `randf()` 每帧给新数，彩纸就会在原地乱抖 —— 看起来像信号干扰，不像纸片在飞。同一片纸必须永远走同一条抛物线。
3. **彩纸落地不消失**，趴在草地上。通关后玩家可能盯着结算卡发呆好几秒，画面应该是「庆祝正在进行」，不是「庆祝已经结束，只剩一地冷清」。

炮口只有两个（栅栏顶 + 羊圈顶），不是全屏乱喷。全屏喷是「放烟花」，两个炮口是「两个环节一起完成了」—— **把庆祝绑在场景里的物件上，别绑在屏幕上**。

星爆只在头 0.8 秒。它是「刚刚发生了什么」的惊叹号，不是背景装饰；过了那一瞬就该退场，否则一直抢彩纸的戏。

### 21.3 结算卡的三个设计约束

1. **挂在 `CanvasLayer` 上，不进根 VBox。** 根布局有 776 的高度硬预算，结算卡是「事件」不是「常驻模块」，让它浮在最上面最省，也才符合「通关是一个时刻」。
2. **星级逐颗弹出**，延迟 0.18 起、每颗间隔 0.14。拿到几颗弹几颗，**没拿到的保持暗色且绝不弹** —— 缺的那几颗必须安静，玩家才知道差在哪。一次全亮就变成装饰了。
3. **指标行居中紧凑，不是三列对齐**。奖状不是报表；左边标签右边结果那种排版会立刻把它读回数据面板。达标给绿勾，没达标给灰叉 —— 两态都有形状，玩家才知道「这一项存在且没拿到」。只在达标时显示勾、没达标就空着，看起来像这行本来就没这一栏。

徽章只挂一枚。同时刷了两项就只写「新纪录」，三行字挤一张卡没人读。

顺带修了一个边界：**最后一关通关后「下一关」什么都不做**，玩家会当成按钮坏了。现在文案改成「回到第 1 关」，行为也跟着改。

### 21.4 一个真 bug：× 按钮会被自己吓跑

达叔报的现象：鼠标移到行尾的 × 上，× 当场消失 —— 但还能点。

第一版判断：`del.modulate.a = 0`，靠整行的 `mouse_exited` 收起来；鼠标移进 × 时行收到 `mouse_exited`，于是归零。所以加个延迟判定：退出时等一帧，问「鼠标现在还在行的矩形里吗」，在就不收。

**这个修法是错的，而且错得很有教育意义。** 实测数据（`tools/probe_hover.gd` 打出来的）：

```
① 停在行中央    entered=1 exited=0
② 停在 × 上     entered=1 exited=1     ← 这里发了一次 exit
③ 停在行外      entered=1 exited=1     ← 移出行外，没有再发 exit
```

**Godot 在鼠标落进行内子控件时会给父控件发一次 `mouse_exited`（子控件接管了鼠标）；之后从子控件直接移出父控件外，不会发第二次。**

于是：
- 旧版：② 时收到 exit → × 消失；③ 时没事件 → 永远不回来。**玩家看到「想点它它跑了」。**
- 加延迟判定：② 时 `has_point` 为真 → 拦住，× 保住；③ 时同样没事件 → × **永远亮着**，再不收起。

两头都不对。根源是**用信号去表达「鼠标在不在这个矩形里」这个纯空间状态**，而这个信号在这件事上本来就不可靠。

最终改法：**鼠标位置是唯一真相来源**。`_input` 里每收到一次 `InputEventMouseMotion`，就扫一遍程序行矩形，算出「现在压着哪一行」，命中行的 × 亮、其余全收。行数几十个、矩形判断是纯算术、鼠标不动就不算，代价可以忽略。

> **通用教训：能用纯状态判断的事，别用事件。** 信号适合表达「发生了什么」，不适合表达「现在怎样」。
> 事件的采样点和状态的连续性之间必然有缝，缝里就是这类「移进来走了、移出去没回来」的 bug。

探针留在 `hrm_godot/tools/probe_hover.gd`，三态断言（行内 1 / × 上 1 / 行外 0），必须带窗口跑。

### 21.5 顺手删掉舞台底部那条 HUD

一条 16px 高的常驻横条，只有两条信息：

- 「已数 1 / 1」—— 栅栏挂牌上已经写着「已数 N」。
- 「当前指令 OUTBOX」—— 程序行的绿边呼吸已经在说同一件事。

一条两个人干同一件事的横条。删掉它，计数搬进栅栏挂牌（改成「已数 N / M」，反而多了个总数），舞台净多 16px 草皮。

### 21.6 回归

64 / 5 / 92 全绿，布局余量 728 / 776。新增探针 `tools/probe_hover.gd`（三态全 PASS）。
截图在 `hrm_godot/_shots/v14/`。

## 二十二、HUD 信息架构：哪些该常驻，哪些该收

### 22.1 一条判据

> **一个信息，如果玩家在 90% 的操作步骤里都不看它，它就不该占常驻面积。**

按这条判据，把所有模块过一遍。四层：

| 层 | 含义 | 出场规则 |
|---|---|---|
| **L0 常驻** | 每一步都在看 | 永远在 |
| **L1 状态驱动** | 有事才出现，事完就消失 | 由游戏状态决定显隐 |
| **L2 学了才需要** | 前几关必须，熟了是噪音 | 默认收起，一键展开 |
| **L3 低频查询** | 玩家主动想找才看 | 抽屉 / 弹窗 |

### 22.2 逐模块盘点

| 模块 | 现在 | 该归 | 依据 |
|---|---|---|---|
| 关号 + 三星 | 常驻 | **L0** | 「我在哪、我多好」，永远要看 |
| 程序区 | 常驻 | **L0** | 核心工作区 |
| 舞台 | 常驻 | **L0** | 游戏画面 |
| 运行 / 单步 / 重置 | 常驻 | **L0** | 操作本身 |
| 指令数 `20/20` | 常驻 | **L0** | 是这一关的硬约束，不是参考值 |
| 上一关 / 下一关圆钮 | 常驻 | **L1** | 只在通关后有意义，平时纯占位 |
| 最佳记录 | 常驻 | **L1** | 只在有成绩后有意义 |
| 状态点 `● 就绪` | 常驻 | **L1** | 已经是状态，保留 |
| 任务描述正文 | 常驻右上 | **L2** | 每关读一次；第 2 关以后就是噪音 |
| INBOX / OUTBOX 数值 | 常驻 | **L1** | 开局和卡住时看，中途不看 |

| 说明书按钮 | 常驻 | **L2** | 查过就不查了 |
| 指令面板（8 张牌） | 常驻整右栏 | **L0**（前 5 关）/ **L2**（之后） | 是打字替代，前几关必须；熟了玩家会直接拖 |
| 指令说明条（底部那句） | 常驻 | **L2** | 和悬停 tooltip 重复，**可以直接删** |
| 速度 / 周期÷件 | 常驻 | **L2** | 进阶优化指标，第一遍通关用不上 |
| **关卡列表（20 行）** | 常驻整左栏 | **L3** | 选关是「决定玩哪个」的低频动作，占 20% 屏宽 |
| 进度条 `16/20` | 常驻 | **L3** | 跟着关卡列表走 |

### 22.3 三处最该动的

**一、左栏关卡列表（占地最大，收益最高）**

20 关时长条要滚，且和顶部「17 / 20」重复计数。它是典型的 L3 —— 玩家第 1 次进来选一关，之后一小时都不会再点。

改法：收成顶部关号徽章旁边的一枚「☰ 关卡」按钮 → 点开是一张 5×4 的格子地图（比列表好看，也符合「游戏选关」）。省出的 200px 宽直接给程序区。

**二、指令说明条**

一句话，和悬停 tooltip 完全重复。悬停已经有解释条，底部这条只是「怕玩家不悬停」的保险。删。

**三、任务描述正文**

每关读一次。改成默认显示一行目标摘要（「读到 0 为止，输出合计」），点一下展开完整 INBOX/OUTBOX 数据。省出的高度给舞台。

### 22.4 不建议动的

- **指令面板不能收。** 它是「点一下就追加」的核心输入方式，收了等于让玩家打字。
- **指令数 `20/20` 不能收。** 它是这一关的约束，不是参考 —— 超了就过不了。

### 22.5 这一版只落地了一处

删了舞台底部那条 HUD（见 21.5）。其余三处都要重排布局，动之前得先确认方向 —— 尤其左栏收成格子地图，是这一版最大的一次结构改动。

## 二十三、如果做 IAA（广告变现），触发器该放哪

### 23.1 先划一条硬红线

> **任何广告都不能成为通关的必要条件。** 每一关都必须有一条免费的、完整的通关路径。

这条线一旦破，游戏就从「编程解谜」变成「付费墙」，评价体系（星级 = 写得好不好）会跟着失去意义。

### 23.2 这个游戏的「心流」是什么

```
读题 → 写程序 → 跑 → 看结果 → 改 → 再跑 …… → 通关
```

**打断心流最狠的位置，就是「写 → 跑」之间。** 那里插任何东西（插屏、Banner、弹窗），玩家都会立刻关掉游戏 —— 因为他正卡在一个思路里，思路断了就得从头想。

所以广告位只能放在**玩家自己就想停的地方**。这个游戏只有四个：

| 停顿点 | 强度 | 玩家此刻的心理 |
|---|---|---|
| 通关看结算卡 | **最强** | 满足、愿意看任何东西 |
| 卡住 60 秒点提示 | **强** | 主动求救，愿意交换 |
| 关卡之间（点下一关） | 中 | 想继续，但也可能想歇 |
| 刚启动 / 回到游戏 | 弱 | 还没进入状态 |

### 23.3 具体触发器设计

**① 提示阶梯（最合适的位）**

现在已经有三档（`hint_stage` 0→1→2→3）：

| 档 | 现在 | 建议 |
|---|---|---|
| 1 思路提示（「你需要一个循环」） | 免费 | **保持免费** |
| 2 具体指令提示（「在第 3 行放 JUMPZ」） | 免费 | **看一段激励视频** |
| 3 直接填参考解 | 免费 | **保持免费，但成绩标记为 ☆** |

为什么第 2 档收费、第 1 和第 3 档免费：第 1 档只是「提醒你该往哪想」，不替你想；第 3 档已经明确标记「看过解法」，成绩不算自己写的。**第 2 档正好卡在「帮你想了一半」的位置 —— 这是最值钱、也最该收费的那一半。**

**② 结算卡上的「回放」**

不要卖星。星级是这个游戏唯一的评价体系，卖星等于毁掉它。

可以卖的是：**看视频解锁本关的「最优解回放」** —— 逐行走一遍参考解，看它怎么做到 10 条指令。给的是信息，不是评价。

**③ 关卡间插屏**

- 触发：**主动点「下一关」**时才可能弹，不是自动切关
- 频率硬上限：**每 5 分钟最多 1 次**，且前 3 关一关都不弹（新手期绝不能弹）
- 一次会话最多 3 次

**④ 不该放的地方**

| 位置 | 为什么不行 |
|---|---|
| 主界面 Banner | 四块面板已经占满屏，Banner 只能压掉舞台或程序区，直接毁构图 |
| 「写 → 跑」之间 | 断心流，最狠的劝退位 |
| 撤销 / 重跑 | 这是基础操作能力，收费等于把游戏弄坏 |
| 买星 | 毁评价体系 |
| 体力 / 次数限制 | 这游戏没有资源系统，硬造一个只会让人烦 |
| 启动即插屏 | 玩家还没进入状态，第一印象直接负分 |

### 23.4 频率与体验的硬约束（建议写进配置）

```
前 3 关          零广告（绝对）
插屏最小间隔     300 秒
单次会话插屏上限  3 次
激励视频         只在玩家主动点击时触发，永不自动播放
广告后的状态      必须能原地恢复（不能因为看完广告丢了程序）
```

最后一条最容易被忽略：**看完广告回来，程序必须还在。** 现在程序是实时落盘的，这条天然满足 —— 但一旦将来加了「广告期间暂停」，就得保证暂停不等于重置。

### 23.5 一句话总结

**这个游戏的广告只能长在「玩家已经在求人帮忙」的地方，不能长在「玩家正在思考」的地方。**

按这个标准筛下来，真正可用的只有两个位置：**提示阶梯的第 2 档（激励视频）** 和 **通关后主动点下一关时的插屏（严格限频）**。

## 二十四、左栏：把「20 行清单」换成「20 块地」

前面第二十章讨论 HUD 时说过一条判据：**软件用位置组织信息，游戏用物体组织信息。** 当时只用在顶栏和底栏上，左栏没动 —— 但左栏才是那块「一看就知道是软件」的地方。

### 24.1 病灶：这一栏是文件浏览器

改造前的左栏长这样：

```
[01] First Sheep          ★ 34·2.0
[02] Counting Sheep       ★ 41·2.4
[03] ...
```

20 行，每行一个圆徽章 + 关名 + 成绩尾巴，塞在 `ScrollContainer` 里，要滚才能看完。

这不是游戏界面，这是**文件资源管理器**。判断标准很直白：把这 20 行换成 `main.gd`、`ui_kit.gd`、`stage.gd` 的文件名，它照样成立 —— 一个界面换了内容还不改结构，说明结构在描述「条目」，而不是在描述「地方」。

它同时还有三个实际毛病：

1. **滚**。20 关要滚，玩家永远只能看到「当前关前后几关」，脑子里建不出全局地图；
2. **关名占了 60% 的宽度，但关名不重要**。玩家的判断依据是「我打到第几关了」，不是「这关叫 First Sheep」；
3. **成绩尾巴 `★ 34·2.0` 是数据，不是东西**。它读起来像表格里的一列。

### 24.2 改法：一张自绘的牧场地图

新增 `hrm_godot/scripts/level_map.gd`，一个 `Control` 子类，自己 `_draw()` 出 20 块地砖：

```
[牧场]                    7 / 20
[▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░]
 ① ② ③ ④       ← 琥珀 = 已通关，砖底三颗星
 ⑤ ⑥ ⑦ ⑧
 ⑨ ⑩ ⑪ ⑫       ← 白框 + 琥珀光环 = 当前关
 ⑬ ⑭ ⑮ ⑯
 ⑰ ⑱ ⑲ ⑳       ← 深蓝 = 未通关
★ 15 / 60                      三星
```

4 列 × 5 行，20 关一屏铺满，**不用滚**。三态只换底色和描边，形状一律不动 —— 和程序行的四态是同一套语言：

| 状态 | 底色 | 描边 |
|---|---|---|
| 已通关 | `AMBER #ffdc30` | `EDGE` 2px |
| 当前关 | `SLIP_SEL #1c86cf` | 白 3px + 琥珀呼吸光环 |
| 未通关 | `#083a63`（比面板深一档，读作「凹下去」） | `EDGE` 2px |

砖底三颗星用**真五角星**画（`draw_colored_polygon`），缺的星只降透明度、不改形状。这一条在 v12 就定过：形状不变才数得出缺几颗。

### 24.3 为什么不用 `GridContainer + Button`

第一版想的是最省事的做法：`GridContainer(columns=4)` 里塞 20 个 `Button`。试了之后放弃，原因是**它会长成「一排按钮」**：

- 按钮框是方的、圆角是容器给的、间距是均匀的 —— 换了个排法，还是列表；
- 地砖需要「从草地上浮起来」的硬投影（offset 3、几乎不模糊）。`Button` 的 `normal` stylebox 加 shadow 会被容器的 `separation` 裁掉下半截；
- 装星点要往 `Button` 里再塞子控件，20×3 个 `Panel`，纯浪费。

自绘以后这些都在一个 `_draw()` 里按坐标画，`_boxes` 里缓存三套 `StyleBoxFlat`（按尺寸键），hover 时 `duplicate()` 只改底色。**开销比 60 个控件低，样式还完全可控。**

### 24.4 顺手修掉的一个真 bug：「几颗星」原来是错的

铺开 20 块砖以后，每块砖都要显示自己的星数 —— 这时候暴露出一个一直存在但看不见的错误：

```gdscript
# 改造前
func _stars(id: int) -> int:
    var rec = progress.get(str(id), {})
    ...
    if int(rec.get("size", 9999)) <= target_size:   # ← target_size 是「当前关」的
```

`target_size` / `target_speed` 是**成员变量**，只在 `_refresh_targets()` 里为「当前打开的这一关」赋值。原来的调用点只拿它算当前关的星，所以永远是对的；但地图要同时算 20 关，它会拿第 7 关的目标去判第 1 关的成绩。

修法是把判据挪到「按关卡下标」：

```gdscript
func _stars_of_idx(idx: int) -> int      # 按关卡下标算，target 走 _target_of(idx)
func _stars(id: int) -> int              # 老接口保留，内部找下标转调上面那个
func _target_of(idx: int) -> Dictionary  # 每关参考解的成绩，首次现算、之后缓存
```

`_refresh_targets()` 也改成从 `_target_of(li)` 取 —— **判据只有一份**，改参考解的算法不会漏掉某一处。热重载 `levels.json` 时 `level_targets.clear()`。

顺带加了 `--cleared=N` 命令行参数（`-1` 不动存档、`0` 清空、`N` 假装前 N 关通关，星数按 3/2/1 循环发），用来截图核对三种砖的样子。

### 24.5 还剩什么

`map_levels.custom_minimum_size.y` 目前写死 288（= 5 行 × 52 + 间距）。**关卡数涨到 40 时这个数不够**：10 行砖在 288 高里每块只剩 22px，数字和星点会挤在一起。到那时要么改 5 列 × 8 行、要么把地图塞回 `ScrollContainer`，没别的路。现在不加，是因为 40 关还没做。

## 二十五、程序列表：为什么它一直在跳，以及按住下滑

达叔的原话：

> 这个区域的操作太难受了，因为 list 的长度变化界面一直处于跳动的状态，且整个区域没有按住下滑的功能也难受。

两条都是体感，没有机理。所以先写探针（`hrm_godot/tools/probe_scroll.gd`），把「跳」拆成三种可能逐帧量：

| 猜的机理 | 探针结论 |
|---|---|
| A. 重建时容器塌陷，`scroll_vertical` 被夹回 0 | **不成立**。滚到 200，追加一行后仍是 200，五帧都稳定 |
| B. 行高不一致，重建后总高度变 | **成立**。同一张表里，带参数的行 44px，不带的 34px |
| C. 列表外的控件变高，把列表顶动 | **成立**。指令面板底部的解释条：文字短 26px，文字长 57px |

两条坐实，第三条是探针顺带发现的意外收获。

### 25.1 行高必须一致（B）

```
改造前   01 INBOX   34px
        02 MOVETO  44px   ← 带 SpinBox
        03 INBOX   34px
        09 OUTBOX  34px   ← 出错时整行比邻居矮一截
```

后果有两层：

1. **一列下来参差不齐**，眼睛扫行号的时候总要重新对焦；
2. **长度变化的「速度」不均匀** —— 加一条 `INBOX` 长 38px，加一条 `MOVETO` 长 48px。玩家感觉不到自己在建立一个有节奏的列表。

改法是把 `ROW_H` 从 30 改成 44，并给每一行设 `custom_minimum_size.y = ROW_H`。不画参数的行不画占位（第二十章那条铁律不变），但**格子照样占满**：空的是格子里的空白，不是格子本身。

> `ROW_H` 同时被拖拽插入空隙（`DragGap`）和边缘自动滚的步长引用，所以三处一起改，不能只改 `_make_row`。

### 25.2 会变长变短的文字，必须关进固定高的盒子（C）

解释条原来是这样建的：

```gdscript
lbl_op_help.autowrap_mode = AUTOWRAP_WORD_SMART
lbl_op_help.custom_minimum_size = Vector2(0, 26)   # ← 只是「最小」26
```

`custom_minimum_size` 是下限不是上限。文字一长，autowrap 换行，Label 变成 57px —— 上面那六张指令牌整片往上挪。**鼠标划过一排牌，面板就一跳一跳**。这种跳动最烦：它跟玩家的操作无关，纯粹是界面自己动。

改成外面套一个**固定高、能裁切**的 `Control`：

```gdscript
var help_box := Control.new()
help_box.custom_minimum_size = Vector2(0, 58)
help_box.clip_contents = true          # 关键：不裁就会画到面板外面
```

Label 铺满它（`PRESET_FULL_RECT`），并且加 `max_lines_visible = 3` + `text_overrun_behavior = TRIM_ELLIPSIS`。直接硬裁会断在半句上（「…写进」），省略号至少告诉玩家「还有，但放不下」。

代价：布局最小高度从 728 涨到 749（余量 48 → 27）。仍过 776 的线，但余量薄了一半。

### 25.3 按住下滑：位置分工，而不是手势分工

桌面端鼠标拖拽滚动不是默认能力 —— `ScrollContainer` 只认滚轮和触摸屏的 `InputEventScreenDrag`，鼠标按住拖它是不动的。

麻烦在于**同一个手势已经有主了**：按住行卡拖动 = 挪动这一行。两个动作挤在一个手势上，必然有一个不可预期。

所以按**位置**分工：

| 按在哪 | 动作 |
|---|---|
| 行卡内容上拖 | 挪动这一行（原有） |
| 行尾空档上拖 | 滚列表（新增） |
| 列表下方空白处拖 | 滚列表（新增） |

行尾那块 `spacer` 原本的注释写着「空档区域也要能按住行来拖」—— 它既不属于「读」也不属于「改」，用来做滚动最不抢戏。光标改 `CURSOR_DRAG`，鼠标扫过去就看得出来。

实现上是给 `_press_kind` 加第三个值 `"scroll"`：

```gdscript
func _start_drag() -> void:
	if _press_kind == "scroll":
		_scroll_drag = true
		_scroll_from = scroll_rows.scroll_vertical
		_scroll_y0 = _press_pos.y
		# 立刻跟上这一帧的位移：只置标志、等下一次移动才滚，会慢半拍
		scroll_rows.scroll_vertical = int(_scroll_from - (_drag_pos.y - _scroll_y0))
		return
```

**一个必须加的护栏**：行卡和列表容器都会收到同一次按下（事件往上冒）。行先认领，容器后到，容器不能抢：

```gdscript
func _begin_press(kind, op, from, gpos):
	if kind == "scroll" and _press_on and _press_kind != "scroll":
		return      # 行已经认领了这次按下
```

没有这一句，每次点行都会被当成「拖空白」，整张表就废了。

探针用真实事件链验过（`Viewport.push_input` 走完整 GUI 分发）：按在行尾空档 `(732,140)` 上拖 70px，`scroll 0 → 70`，1:1 跟手。

### 25.4 追加一行只动一行

最频繁的操作是点指令牌追加。原来它走 `_after_edit()` → `_rebuild()`：**20 行全部销毁、全部新建**。屏幕上是「闪一下」，滚到哪都跟着抖一下（`queue_free` 的旧行还在，新行已经排好，两套节点的存在时间重叠一帧）。

追加到末尾时可以只加一个节点：

```gdscript
if at == program.size() - 1 and program.size() > 1 \
		and row_nodes.size() == program.size() - 1:
	# 只 append 一个节点，不重搭整张表
```

中间插入、删行、换标签仍然走全量重建 —— 因为行内的闭包捕获了下标（`_delete_row(i)` / `_set_arg(i)`），下标一移位就全错，重建是最省心的解法。这条债记在这儿。

### 25.5 顺手修的两个小问题

1. **重建后 × 会闪**：重建的行上一帧还没排版，`_update_row_hover` 量不到矩形 → × 先消失、等鼠标再动一下才回来。改成重建时置 `_hover_dirty`，下一帧按真实鼠标位置重判一次。
2. **`String(arg)` 会炸**：JUMP 类指令的参数从存档读出来若是数字，`String(0)` 直接抛 `Invalid call 'String' constructor`，整行建不出来。改成 `str(arg)`。

## 二十六、跳转线：把「跳过去」这件事画出来

达叔的请求：

> JUMP 系列的牌放进命令区之后，能不能体现出跳转的画面标识 —— 不单单是标签字母，
> 而是有一个箭头横跨多个命令、指到对应的跳转位置，能看出代码之间的包裹性。

这是这个原型第一次有「结构可视化」的需求。前面二十几章都在处理「它像不像游戏」，
这一条处理的是「它像不像代码」。

### 26.1 病灶：`JUMPZ b` 和 `b:` 之间隔了一屏

程序列表里，跳转是这么表达的：

```
01  a  INBOX
02     JUMPZ   b     是0就跳
03     OUTBOX
04     JUMP   a      跳
05  b  MOVETO  0
06     JUMP   a      跳
```

玩家要在 02 和 05 之间、04 和 01 之间各做一次**「往下/往上找那个 b / a」**。
程序一超过一屏，这次搜索就直接失败 —— 他只能靠滚，滚完又忘了自己在找什么。

这不是「提示不够」，是**信息根本没画出来**。字母 `b` 是地址，但地址本身不表达关系。

### 26.2 做法：行卡左边留一条 14px 的空白栏

第一版把线画在行卡内部的 padding 里（`行卡左 + 4`），结果**正好压在行号上** ——
行卡的 padding 只有 11px，行号从 13px 就开始，中间根本没有画线的余地。

所以给 `box_rows` 外面套了一个 `MarginContainer`，左边留 14px：

```gdscript
row_gutter = MarginContainer.new()
row_gutter.add_theme_constant_override("margin_left", 14)
scroll_rows.add_child(row_gutter)      # 滚动列表的子节点
row_gutter.add_child(box_rows)          # 行列表
```

这条栏一留，线就从「卡片上的一道划痕」变成了「**代码块外面的括号**」——
这正是「包裹性」的字面意思。

顺带一个后遗症：行列表整体右移 14px，表头还停在原地，列名比数据左偏一格。
所以表头前面也补了一个 13px 的 spacer（13 = 行卡 border 2 + padding 11），把 `#` 压回行号左沿上。

### 26.3 一层盖在行卡上的绘制层

`jump_arcs.gd` 是一个 `Control`，和 `scroll_rows` 并排放在同一个 `row_wrap` 里：

```
row_wrap (Control, clip_contents)
├── scroll_rows (ScrollContainer)
│   └── row_gutter
│       └── box_rows (VBox)  ← 行卡
└── jump_arcs (Control)      ← 画线，mouse_filter = IGNORE
```

这个结构不是随手摆的，三条都试过：

- **塞进 `ScrollContainer`** —— 它会被当成第二个内容块，和 `row_gutter` 平分高度；
- **塞进 `box_rows`** —— `VBoxContainer` 会把它当成一行，占掉一整行高；
- **画在 `main._draw()`** —— 根节点的绘制在子控件**之前**，线会被所有行卡盖住。

所以必须有 `row_wrap` 这一层：`clip_contents` 负责把滚出去的行和线一起裁掉，
`jump_arcs` 铺满它、`IGNORE` 不吃事件、每帧 `queue_redraw()` 跟着行的位置重画。

### 26.4 线怎么画：位置分工

| 要素 | 画法 | 为什么 |
|---|---|---|
| 起点 | 小圆点（r=3） | 「这条线是从这行出发的」，和终点区分 |
| 路径 | 出 → 拐 → 竖 → 拐 → 入，直角折线 | 弧线在这种密度下会和行卡圆角混成一片 |
| 终点 | 实心三角，指回行内 | 「落点在这一行」 |
| 颜色 | 琥珀 `#ffdc30`，不选中 0.85、选中 1.0 | 和标签贴纸同色 —— 跳转靠的就是标签 |
| 位置 | **一律走左侧**，不按方向分左右 | 见下 |

**为什么不按方向分左右**（往回跳=循环画左、往前跳=分支画右）：
分左右会让同一段代码的两头各挂一串线，视觉重心散到两侧。
都走左边，一列线竖下来就是「这段被谁从外面拉着」。
上下的方向自己会说明语义：线在行**下面**收口 = 往回跳 = 循环；在上方收口 = 往前跳 = 分支。

### 26.5 分列：贪心，不是编号

第 17 关有 6 条跳转。如果按出现顺序编号分列，6 条线会占满 6 列，
可栏里只有 14px（3 列），于是糊成一片。

改法是把「分列」当成**区间排布**问题：每条线是一个 `[y_min, y_max]` 区间，
找第一条纵向不冲突的列，都冲突才新开一列（上限 3 列，超了回落到第 0 列）。

```gdscript
for span in cols[c]:
    if not (hi < span.x or lo > span.y):
        free = false
```

这样相隔很远的两个循环会共用同一列 —— 视觉上它们是「两根独立的括号」，本来就该在同一列。

### 26.6 端点滚出视口：打断口，不画断头

程序一长，跳转的另一端就在视口外。直接画会让线冲出裁剪区，玩家看到的是「线没了」，
而不是「还连着」。

所以端点越界时把线夹在边界上，并在断口画一道 5px 的短横杠：

```
断口 ═══   ← 表示「这条线还接着往上走，只是看不见」
     │
```

起点越界画断口、终点越界画断口；两端都可见才是「圆点 → 箭头」的完整表述。

### 26.7 可测的那一半

画线好不好看只能靠眼睛，但**「哪一行跳到哪一行」不能靠眼睛**。
所以把这段逻辑抽成静态纯函数：

```gdscript
static func links(program: Array) -> Array      # → [[from, to], ...]
```

`_draw()` 调它，测试也调它。四条断言：

```gdscript
_check(links.size() == 2, ...)
_check(int(links[0][0]) == 1 and int(links[0][1]) == 4, "JUMPZ b 应跳到 b 所在行")
_check(int(links[1][0]) == 3 and int(links[1][1]) == 0, "JUMP a 应跳回 a 所在行")
_check(JumpArcs.links(["JUMP zz"]).is_empty(), "目标标签不存在时不该有线")
```

补一条容易被忽略的：**同一标签写两次时取最后一次**（和 VM 的寻址行为一致）。
这种「渲染层和解释器对同一个程序的读法必须一样」的地方，错了以后表现是「线指着 A，程序跳到 B」——
比完全不画线更难查。

## 二十七、抬头重排：把「目录」和「说明书」各自归位

达叔的原话四条：

> 1. 关卡展示区域常态就隐藏不要出现了，把上面的当前关卡标签改成互动按钮，点击后才会展开关卡区域
> 2. 任务说明区域原来的位置移动到顶部的空缺位去（你自己重新做下里面的展示布局安排）
> 3. 腾出来的位置就可以只展示 函数命令区域 和 函数卡片区域，一个左侧一个右侧

第二十四章把左栏从「20 行清单」改成了「20 块地砖」，方向是对的，但**只回答了「用什么画」，没回答「该不该一直在那儿」**。
地砖比清单好看得多，可它依然常驻，依然吃掉五分之一屏宽。

### 27.1 判据：同一块屏上，什么东西有资格常驻

一条简单的问法：**玩家在做正事的九成时间里，需不需要看它？**

| 那块区域 | 内容 | 什么时候需要 | 该常驻吗 |
|---|---|---|---|
| 左栏 20 块地砖 | 关卡选择 | 想换关的时候 | **不该** —— 换关是一天几次的动作，写代码是一分钟几次的动作 |
| 右栏任务卡 | 本关目标 + 数据流 | 读一次就记住 | **不该** —— 一块只读的说明书钉在鼠标旁边，等于抽屉里塞了张 A4 |
| 中栏程序 | 自己写的东西 | 一直在看 | 该 |
| 右栏指令牌 | 能拖的东西 | 一直在拖 | 该 |

好，那两块「不该常驻」的东西去哪？**抬头本来就有大半是空的**（产品名 + 关号 + 三颗星 + 两个翻页钮，右边空着一大片）。
抬头是唯一「宽度富余、高度紧张」的地方 —— 正适合住这种「短、一次性、但要能随时瞟一眼」的信息。

### 27.2 关号徽章 = 一枚按钮

关号从「一行字」变成一枚 `Button`（62×42，木牌底 + 9 圆角）：大号 `17`，下面一行 10px 的 `/ 20 ▾`。
点它，牧场地图**以浮层形式铺开**；再点，或者点空白处、按「收起 ×」，收回去。

为什么是浮层而不是「就地展开」：

- 就地展开会让中栏跟着重排 —— 玩家点了一下导航，正在写的程序区突然变窄，这是最不该发生的一类动。
- 浮层挂在**本节点**上，不进根 VBox。根布局有 776 的硬预算（第一章那条），
  常驻模块才该受那个预算约束；浮层是「事件」，不是「模块」。`doc_layer` 早就是这么做的，这里照抄。

浮层里地砖放大到 **84px**（左栏时代 52）：大不是目的，让「关号」和「三星」在同一块砖上互不挤才是目的。
84 × 4 + 7 × 3 = 357 宽，84 × 5 + 7 × 4 = 448 高，加标题正好在 1280×800 里居中留白。

`LevelMap.tile_max` 因此从 `const` 改成 `var` —— 同一个渲染器，两种尺寸。

### 27.3 标题栏里的两个分数都得自报家门

地图上「12 / 20」旁边还有「24 / 60」，两个没标签的分数摆在一起，玩家得先猜再对。
改成 `通关 12 / 20` 和 `★ 24 / 60`。**一个数字是什么，比它准不准更早被读到。**

### 27.4 抬头：把「任务条」钉死成 56

任务说明搬进抬头以后，抬头就有了一个危险的新住客：**文字长度不受控**。
目标一行还是两行、数据流长还是短，都会把下面的编辑器整片顶走 ——
那是玩家没做任何操作、界面自己动的动，比什么都烦（第二十五章 C 那条的翻版）。

三步把它关进笼子：

1. `head.custom_minimum_size.y = 56` —— 抬头高度钉死，谁也别想撑高它。
2. 数据流从**两行**压成**一行**：`INBOX 5,3,3,5,4,4 → OUTBOX 1,-1,0`。
   原来 `"%s\n%s"` 摆两行，光数据流就吃掉 36，抬头 56 里一半是它。
   横着摆也没有更差：进和出本来就是一前一后，横着读还多一个好处 ——
   「相等」这件事变成了两段数在一条线上的对照，不用上下跳着眼睛比。
3. `lbl_goal` 允许两行（`max_lines_visible = 2` + 省略号），但 `size_flags_vertical = SHRINK_CENTER`，
   它只在自己那 32 高里待着。

回归里加了这条护栏（**116 项里的新一项**）：

```gdscript
var hud_h: float = main.root_box.get_child(0).get_combined_minimum_size().y
for lv in main.levels.size():
    main.load_level(lv)
    ...
    if absf(h - hud_h) > 0.5:
        _check(false, "第 %d 关的抬头高度 %.0f 和第 1 关的 %.0f 不一致" % [...])
```

判据是「所有 20 关的抬头高度必须一模一样」。现在实测恒为 **56**。

### 27.5 一个被掩盖的老问题：最小高度变小 ≠ 界面变高

两样东西搬走以后，`root_box` 的最小高度从 **749 掉到 582**，留白 194，看起来是好事。
结果截图一出来——**程序区只剩 4 行**，比改之前还矮。

原因是 `VBoxContainer` 分配 `EXPAND` 孩子的规则，和直觉不一样：

> **不是「按 ratio 分富余」，是「按 ratio 分扣掉固定项之后的全部高度，但谁也不许低于自己的最小高度」。**

探针实测（`tools/probe_layout.gd`）：body 和 stage 都是 `EXPAND_FILL`，ratio 1:1 时两块**各 319** ——
不是 358 / 280。638 是「776 减去抬头、控制栏和两条间距」之后的总量，319 × 2 = 638。

所以改之前那种「工作台看着够高」是假象：它的最小高度有 410，是被左栏地图（288）和右栏任务卡撑出来的，
**不是它自己挣来的**。撑它的东西一走，它就只剩 264，而富余高度按 stage 的 1.8 比例全给了舞台
（`_build_stage` 里那个 `stretch_ratio = 1.8` 是给旧布局调的，方向正好反了）。

修法是按**屏占比**反推 ratio，而不是凭手感：

```
776 - 56(抬头) - 52(控制栏) - 30(间距) = 638
舞台要 228（800 的 28.5%）→ body 410
410 : 228 ≈ 1.8 : 1
```

于是 `body.stretch_ratio = 1.8`、`p_stage.stretch_ratio = 1.0`。实测 body 410 / stage 228 ✓，
程序区从 4 行回到 7 行半。

这类问题**看截图只能看出「矮了」，看不出「矮了多少、被谁拿走了」**，
所以留下了一个探针：`tools/probe_layout.gd`，一次打出抬头/工作台/舞台/控制栏四块的矩形、最小高、ratio。
**必须带窗口跑**（headless 下窗口尺寸不对，量出来的全是假的）。

### 27.6 顺手删掉的两处死代码

- 右栏里那个 `pad`（`SIZE_EXPAND_FILL` 的空 Control，本意是「把解释条顶到底」）。
  两个 EXPAND 是平分富余的：右栏从 260 长到 410 以后，多出来的 150 有一半喂给了这块空气，
  指令牌只多拿到一排便到底了。删掉，由 `scroll_pal` 独占富余 —— 牌子列表本来就该把整只手伸到底。
  实测 `scroll_pal` 从 132 长到 270，第 17 关的 8 张牌一次全露出来。
- `bar_levels` / `bar_levels_rest`（左栏那条「通关 12/20」进度条）。地图浮层里用 `通关 12 / 20`
  这行字代替了它的位置，进度条没有第二处引用。

## 二十八、跳转线：车道缩进 + 标签上色

达叔报了两条，其实是同一个问题的两面 —— **一眼分不出哪条线是谁的**：

> 1. 这块的箭头指示线路都叠在一起了，函数命令行可否根据箭头的数量做整体适当向右缩进
> 2. 不同的标签可不可以做颜色区分，同时箭头的跳转指示也会根据其目标的标签色变成一样的颜色

### 28.1 病灶：14px 的栏里塞三列 5px 间距的线

第二十六章给跳转线留的是**固定 14px** 的空白栏，列间距 `LAYER_STEP = 5`，上限 `MAX_LAYER = 2`（三列）。
第 17 关那种程序有 4~5 条跳转，而且纵向区间大量重叠 —— 贪心分列分出 5 列，全挤在 14px 里，
每条线只隔 5px，2.5px 粗的线几乎贴在一起。

同时**所有线都是琥珀色**。5 条同色的平行线，等于让玩家「顺着一条条追」——
这和「没画线、只在脑子里搜标签」只差一点点。

### 28.2 缩进：让位跟「这段代码有几个块」走

改法是**行卡整体右移**，宽度由「需要几条车道」决定：

```gdscript
# jump_arcs.gd
func gutter_width() -> float:
	if lanes <= 0:
		return 0.0
	return LANE_PAD * 2.0 + float(lanes - 1) * LANE_STEP   # 6*2 + (n-1)*12
```

| 车道数 | 让位 | 典型程序 |
|---|---|---|
| 0 | **0** | 第 1 关那种一条跳转都没有的 |
| 1 | 12 | 单个循环 |
| 2 | 24 | 一个分支 + 一个循环 |
| 3 | 36 | 第 17 关的常见形态 |
| 5 | 60 | 参考解那种多层嵌套 |

**0 条线就让 0 宽**，这一条是特意写的：没有跳转的程序不该为不存在的线留白。
「缩进」这个词在代码里本来就意味着「结构越深，右边的空间越少」——
玩家不用读代码，看行卡左边让出多宽，就知道这段程序有几层块。**这就是包裹感的来源。**

「需要几列」只能由 `jump_arcs` 自己算（列分配要看每行的 y），所以它说了算，main 只管照做：

```gdscript
signal lanes_changed(n: int)     # jump_arcs → main
```

main 收到后改两样，缺一不可：

```gdscript
row_gutter.add_theme_constant_override("margin_left", g)
head_pad.custom_minimum_size.x = maxf(0.0, g + ROW_TEXT_INSET - COLHEAD_SEP)
```

**表头必须跟着让**，否则整排列名比数据左偏一格 —— 这是「表格」最不能忍的错位。
`- COLHEAD_SEP`（8）是因为表头这一格后面还跟着一个间距，不扣掉就一直偏右一个格距。
实测对齐精度：`表头 # 的 x = 85，期望 85`。

### 28.3 跨度大的走外圈，小的走内圈

分列顺序原来按「程序里出现的先后」，改成了**按跨度降序**：

```gdscript
items.sort_custom(func(a, b) -> bool:
	return absf(float(a[4]) - float(a[3])) > absf(float(b[4]) - float(b[3])))
```

理由：括号是层层套的 —— 贯穿整个程序的大循环该在最外圈，只包住三行的分支该贴内容。
按出现顺序分的话，第 3 行那个短跳转可能占掉最外面一列，**视觉上像是它包住了整个函数**。
这个「谁包着谁」的错觉比不画线更坏，因为它看起来很有道理。

### 28.4 上色：标签色板是唯一真源

```gdscript
# ui_kit.gd
const LBL_A := Color("ffdc30")   # 琥珀
const LBL_B := Color("4fd9a4")   # 青绿
const LBL_C := Color("ff8f6b")   # 珊瑚
const LBL_D := Color("b49bff")   # 紫
static func label_tint(lab: String) -> Color
```

两个约束：

1. **色相必须拉开**（黄 / 绿 / 珊瑚 / 紫）。四个单字母在余光里长得一模一样，
   颜色是让「这两行是不是同一个块」不用逐字读就能判断。
2. **亮度必须够当细线**。深一点的色（藏青、墨绿）做贴纸底好看，做 2.5px 的线就没了 ——
   **线的可辨识度优先于色板的和谐。**

标签贴纸和跳转线**共用这一份**。同一个标签在两处是两个颜色，等于让玩家记两套，那还不如不染。

线的颜色取「它要落到的那一行」的标签色 —— 也就是 `JUMP b` 那条线跟 `b:` 那个牌子同色：

```gdscript
static func links(program: Array) -> Array      # → [[from, to, 目标标签], ...]
```

多返回一个标签，`_draw_one` 拿它调 `Kit.label_tint`。字色统一压深蓝 `Kit.INK`，
不为每种底色单独挑字色 —— 以后加第五个颜色就不用重新挑一次，而挑错是看不见的
（字照样显示，只是糊）。

### 28.5 一个诊断过程值得记

第一次截图，我扫像素发现三条线全是琥珀色，以为是 `label_tint` 没生效。
临时打了两轮 debug 才看清：

- **第一次 debug 没带 `--shot`**，跑的是**存档里的程序**（8 行，2 条线，都是 a）
- 带 `--shot` 才是参考解（19 行，5 条线：3 条 a、1 条 b、1 条 c）

所以那三条黄线**本来就都是 a**，颜色机制一直是对的。

教训：**在这个项目里核对「画出来的东西」，CLI 参数必须和截图完全一致。**
`--shot` 会切 `demo_mode`、会把存档程序换成参考解 —— 少一个参数，看的就是另一个程序。
这类偏差不会报错，只会让人花半小时怀疑自己的代码。

为此留了个探针 `tools/probe_arcs.gd`：一次打出程序行数 / 跳转条数 / 每条线的目标标签和颜色 /
lanes / gutter / 表头对齐误差。**颜色和车道是「数」，不是感觉。**

## 二十九、四十关：预选、分页、以及难度曲线到底出了什么问题

第九章那 20 关是照着原版 Human Resource Machine 的教学顺序写的：一关引一个指令，
下一关练它。这个顺序**教得好，但难得不匀** —— 因为「引入关」天生比「练习关」轻，
而「练习关」里又有几关只是把上一关的零件重新摆一遍。

### 29.1 先说诊断：曲线不是「感觉不线性」，是真的有三处塌陷

给每关算一个可复现的分数：

```
难度分 = 参考解步数 ×1 + 可选指令数 ×1.5 + 木牌格数 ×2 + 跳转嵌套层数 ×4 + 新概念 ×6
```

「跳转嵌套层数」= 有多少条跳转区间同时开着（`jump_arcs.links()` 那套区间，取最大重叠数）。
它比「用了几个 JUMP」准：三条并列的分支和一个三层嵌套，代码行数差不多，脑子里的负担差很多。

跑出来的前 20 关（`tools/curve_plot.py` 出图）：

| 位置 | 分数 | 问题 |
|---|---|---|
| 第 10 关「谁更大」 | 45.5 | 全篇第一个真正的高点 |
| 第 11→12→13 关 | 31.5→24.5→24.5 | **连续两跳往下**，第 12/13 是一对镜像关（+1 / −1） |
| 第 14 关「雨夜的两只」 | **19.5** | **比第 3 关还低**，却排在难点之后 |
| 第 17 关「三种手势」 | 54.0 | 全篇峰值 |
| 第 18→19 关 | 41.5→**28.5** | 第 19 关掉回第 5 关的水平 |

三处塌陷的成因各不相同，而且都不是随便摆的：

1. **第 12/13 是「镜像对」**。教完 `BUMPUP` 马上教 `BUMPDN`，第二关几乎免费。
   教学上是对的（对称概念要连着教），节奏上是塌的。
2. **第 14 关是「复习关」**。它把第 4 关的「先存后读」和第 5 关的 `ADD` 拼起来，
   参考解只有 6 行 —— 它的作用是让玩家把两件事联起来，不是给新难题。
3. **第 19 关是「喘气关」**。第 17/18 连打两个三路比较，玩家需要一关能一口写完的。

**所以「不线性」不是 bug，是这个排序的依据（按指令）和难度的依据（按结构）本来就不是一回事。**
要修，只能换排序依据 —— 但那 20 关已经有人打过了（存档按 id 存），不能重排。

### 29.2 21–40：换一套组织方式，才谈得上单调

新 20 关不按指令组织，按**任务形态**组织：倒着数 / 每三只装车 / 破纪录 / 哨兵边界 /
两把尺子 / 斐波那契 / 欧几里得 / 阶乘……每一关都要同时管 2~4 个状态，参考解 14~36 行。

写完先跑分，再**按分排序**。排序前它是「引入→练习→挑战」的锯齿，排序后是 38→77 的直线：

| | 分数区间 | 形状 |
|---|---|---|
| 1–20 教学段 | 19.5 – 54.0 | 起伏（按指令组织，必然如此） |
| 21–40 进阶段 | 38.0 – 77.0 | **单调上升**（按分排序） |

排序是安全的，因为这 20 关是新的、没人打过，id 可以随便编。
唯一要照看的是「下一关是上一关的变体」这类依赖 —— 「一车里最大」必须排在「每三只一车」之后，
提示里那句「和上一关一样要装车」也得改成点名，因为排序会把它们拆开。

### 29.3 写这 20 关踩到的两件事

**（1）`JUMPZ` / `JUMPN` 不消耗手上的值。**

它只是「看一眼手，决定跳不跳」。所以每个被跳转到的标签，第一条几乎永远是
`MOVETO <废纸篓>` —— 唯一的例外是这个标签本来就以要求手空的指令开头。
20 关里有二十来处，靠人眼一定漏，所以写了个自动修复器（`tools/design_levels.py` 的 `_repair`）：
让模拟器的失败信息自己指路，在失败那一句前面插一条清手，直到跑通。
**多入口的标签它修不了**（一条路径手满、一条手空，插一行只能救一边），
这种只能把两条分支都 JUMP 到同一个汇合点，让所有入口的手都是空的。

**（2）废纸篓格会和计数器抢地方。**

「清手」= 把值写进一格没人读的木牌。但如果随手挑了 3 号格，
而 3 号格正好是层数计数器 —— 每清一次手，计数器就被写坏一次。
表现是「循环少跑两圈」，不报错，只是答案不对。所以每关的废纸篓格现在都是显式指定的（`scratch=`）。

### 29.4 地图：点一块地 = 预选，再按一下才走

原来是「点一块地就过去」。问题不在效率，在**它是个擦不掉的动作**：
换关会存盘、会把当前编辑区换掉。一个擦不掉的动作用不该由一次误触决定 ——
想看第 27 关拿了几颗星的人会顺手把自己切走。

现在的三段式：

| 动作 | 结果 |
|---|---|
| 点一块地 | **预选**：整块砖换成墨绿底 + 亮绿框（呼吸），底下的按钮改字 |
| 按「进入第 N 关 ›」 | 真的换关，浮层收起 |
| 点空白 / 收起 × / 点当前关 | 取消，什么都不变 |

预选砖的**底色也换掉**，不只是加个绿框：2px 的绿线压在 84px 的深蓝面上，
眼睛先看到的是面，绿框根本跳不出来。预选是个「马上就要走」的短暂状态，
这一瞬间玩家不需要知道「这块通没通关」—— 星点还留着，信息没丢。

「预选 = 当前关」时按钮说「第 N 关就是这儿 · 收起」，因为它此刻唯一的用处就是关掉浮层。

### 29.5 40 关必须分页

40 块砖铺进一屏是能塞的（8 列 × 5 行），但砖会瘦成 94 宽的「表格单元格」——
地砖那种「一块地」的感觉就没了。所以 4 列 × 5 行一页 20 关，两页翻。

- 翻页只用圆钮（`‹` `›`）：**圆在这套界面语言里专门表示方向**，方角块才表示命令。
- 打开地图时**自动翻到当前关所在那页** —— 常玩的人不用每次先翻。
- 页码写「2 / 2」，不写「下一页」：玩家要知道自己一共要看几屏。

这里有个顺序陷阱：`map_levels.show_page_of(li)` 必须在 `_refresh_level_buttons()`
（也就是 `set_tiles`）**之后**调。反过来时 `tiles` 还是空的，`page_count()` 算出来是 1，
「翻到当前关那页」被直接夹回第 0 页 —— 而且不报错，只是永远停在第一页。

### 29.6 结果

| | v19 | v20 |
|---|---|---|
| 关卡数 | 20 | **40** |
| 点砖 | 直接换关 | **预选 → 确认** |
| 地图 | 一页铺满 | **两页 + 自动定位** |
| 21–40 难度 | 不存在 | **38 → 77 单调上升** |
| 回归 | 64 / 5 / 128 | **124 / 5 / 142** |

布局余量仍是 582 / 776（抬头重排后没再变），地图浮层是浮层，不参与那个预算。

## 三十、任务说明从抬头搬到牧场：一块牌子 vs 一行小字

### 30.1 问题：最该先读到的一句话，是全屏最小最远的一行字

v18 把关卡地图收进徽章、把任务说明塞进抬头之后，抬头是这么写的：

```
SHEEP COUNTER 数羊 | [17 /20] ★★★ | 牧羊人今晚倒着点名：……  | 卡住了？看提示 | ‹ ›
                                     INBOX 4 → OUTBOX 4,3,2,1,10
```

看起来「密度很高、没有浪费」。但玩家的眼睛九成时间停在**牧场**上 ——
舞台占了 28% 的屏，是唯一的动态区。而「这一关到底要干什么」被压成 13px，
住在离视线中心最远的那一条上。

这不是字号问题，是**位置问题**：把最重要的一句话放在最不看的角落，
再怎么加粗也没用。抬头本身没错 —— 它错在「什么都往里塞」。

### 30.2 判据：这块地方是不是「视线中心」

| 区域 | 屏占比 | 眼睛停留 |
|---|---|---|
| 抬头 | 6% | 换关时扫一眼 |
| 编辑区 | 48% | 写字时 |
| **舞台** | **33%** | **运行、看羊、看结果 —— 一直在** |

舞台是唯一「玩家主动盯着看」的地方，那任务说明就该在那儿。

### 30.3 做法：把它做成一块牌子，而不是一段文字

游戏用**物体**组织信息，软件用**位置**组织信息。所以这次不是「把 Label 挪个地方」，
而是新画一个东西：`stage.gd::_draw_task_sign()`。

- **米色木牌**（`TAG_FACE` + 2px `C_WOOD_D` 边 + 9 圆角 + 3px 硬投影），
  两角各一枚钉子 —— 「这是一块钉上去的板子」，比任何装饰都便宜
- **17px 加粗**（`FontVariation.variation_embolden = 0.55`，项目没有粗体字重）
- 第二行才是数据流：`INBOX 5,3,3,5,4,4 → OUTBOX 1,-1,0`，数字上色、标签压灰
- **牌子宽度按内容量**：`clampf(最长行宽 + 2×20, 560, 舞台宽×0.775)`。
  写死宽度的话，短目标的牌子上会变成「一大片奶油色中间嵌着一行字」，空的地方比字还显眼

同一套判据也适用于提示：`lbl_hint`（三级提示）原来是抬头里一行 12px 灰字，
现在变成牌子下沿挂出来的一张**纸条**（浅黄底 + 「提示」小黄签 + 13px），
而且它**完全不进布局** —— 玩家自己叫出来的东西，不该把任何东西顶走。

### 30.4 四个具体的坑

1. **`FontVariation` 的 embolden 不进 advance。**
   拿加粗字体 `get_string_size()` 量出来 660，`draw_string()` 实际画出来 682 ——
   差 8%，牌子按它算就会「字贴着边」。现在折行和量宽一律用**基础字体**，
   宽度乘 `SIGN_BOLD_FUDGE = 1.09` 再画。这一类「量出来和画出来不一样」的坑，
   只能靠像素对，不能靠读文档。

2. **牌子的高度必须由折行结果唯一决定。**
   `_wrap_chars()` 抽成静态纯函数（按字符折、超 2 行加省略号），单测直接断言
   「短句 1 行 / 超长 2 行且末行带…」。牌子一抖，下面整片场景跟着抖 —— v16 那条教训。

3. **把任务搬走以后，高度分配要重算。**
   抬头 56 → **48**，但牌子占掉了舞台的 sky，`_pen._draw` 的「羊圈 INBOX」标签
   （`fy - 90`）会被牌子压住。所以 `body : stage` 从 1.8 : 1 改成 **1.45 : 1**：
   舞台 228 → 264，编辑区 410 → 382（行数 7.7 → 7.1，肉眼几乎无差）。
   **这不是「给舞台加高」，是给牌子腾出它本来该有的位置。**

4. **太阳、云、栅栏挂牌全都要跟着让。**
   牌子占了 `x 12..0.775w, y 4..66`，原来 0.70w 的太阳正好在里头。
   太阳挪到 0.80w / 0.20fy，两朵云压到牌子下面、山脊上面那道缝里。

### 30.5 结果

| | v20 | v21 |
|---|---|---|
| 目标字号 | 13px 常规，抬头最远一角 | **17px 加粗，舞台木牌正中** |
| 数据流 | RichTextLabel，抬头第二行 | 牌子第二行，数字上色 |
| 三级提示 | 抬头里 12px 灰字，会把抬头顶高 | **纸条挂在牌子下，不进布局** |
| 抬头高 | 56 | **48** |
| 舞台 | 228（28.5%） | **264（33%）** |
| 编辑区 | 410 | 382 |
| 回归 | 124 / 5 / 142 | **124 / 5 / 151** |

新增 CLI `--hint=N`（预先把提示展开到第 N 级，方便截图核对那张纸条）。

## 三十一、多语言：英文 + 繁体中文

### 31.1 三个要求，三个决定了后面一切的选择

1. **首次启动按 IP 归属定语言**：中文区 → 繁体，其余 → 英文。
2. **游戏内可切**。
3. 交付时列出「哪些区域算中文区」。

真正难的只有第 1 条背后的一个问题：这个游戏里有多少句中文？答案不是「界面上的几十个标签」，
而是 **300 条**（144 条界面 + 116 条关卡目标/提示 + 40 个关名）。299 条手写英文，等于把整个
游戏重写一遍；299 条手写繁体，等于抄一遍简中再改错一半。

所以选了三条工程路径：

| 决定 | 理由 |
|---|---|
| **原文即 key** | 源码里写的简中原文就是整张 i18n 表的键。漏翻**不崩**，只退回中文 |
| **繁体不另写一份** | 简→繁走 OpenCC 同款四趟转换，离线烘焙进 `data/i18n.json` |
| **换语言 = 整屏重建** | 逐个控件回填必然漏，而且漏了不报错 |

第一条是整个方案的地基。它把「多语言」从「一份需要同步维护的副本」变成了「一张可以自动体检的差值表」
—— 只要能在源码里枚举出所有中文字面量，就能一条条问「这条翻了没有」。
`tools/scan_strings.py --check` 干的就是这件事，当前 **脚本 144/144 · 关卡 116/116**。

### 31.2 区域判据：四个地区，其余全英文

```gdscript
# scripts/i18n.gd
const ZH_REGIONS := ["CN", "TW", "HK", "MO"]
```

中国大陆、中国台湾、中国香港、中国澳门 → 繁体中文；**其余一律英文**，包括新加坡、马来西亚
（这两个地方华人多，但系统的默认工作语言是英语，玩家看到简中会先愣一下）。

判定链按「越确定越优先」排，前一条有结论就不走后一条：

| 顺序 | 依据 | 说明 |
|---|---|---|
| 1 | `--lang=` 命令行 | 测试与截图用，钉死语言 |
| 2 | `--country=` 命令行 | 强制某国，用来核对区域表 |
| 3 | 存档里的手选语言 | **玩家自己选过就不再探 IP**，这是「手选优先于自动」的唯一实现 |
| 4 | 系统语言 | `zh*` → 繁体，否则英文。IP 三条线全不通时的兜底 |
| 5 | IP 归属（异步） | 通了再切；不通就停在 4 的结果 |

IP 探测放在 `scripts/geo_lang.gd`，四个源依次兜底：`ipwho.is` → `ipapi.co` → `api.myip.com` →
`ip-api.com`（最后一个明文 HTTP，带 UA）。超时 3 秒，返回 `XX` 或空当失败，全失败发 `""`。
**`--shot=` 时整条探测跳过** —— 截图必须确定，不能因为这台机器连的是日本节点就换一门语言。

### 31.3 简→繁：不手写字典，跟 OpenCC 逐条对齐

繁体不是「把字换成繁体字形」那么简单。四趟，顺序和 OpenCC 的 `s2twp` 一致：

```
hant_pre（词）→ hant_char（字）→ hant_post（台湾用词）→ hant_twchar（台湾字形）
```

- `hant_pre` 20 条：先处理会互相干扰的多字词（「后台」→「後台」不能先被「台」→「臺」改掉）
- `hant_char` 3881 条：单字（只→隻/只、周→週/周 这类要靠词判的走下一趟）
- `hant_post` 809 条：台湾用词（软件→軟體、视频→影片…）
- `hant_twchar` 38 条：台湾字形（裡/裏、為/爲）

字典从 OpenCC 仓库取原始文件放 `tools/opencc/`，`tools/gen_hant.py` 离线烘焙进 `data/i18n.json`。
运行时不联网、不带 OpenCC，只带一张 **126KB** 的表。

**有意的偏离用 MANUAL 表。** OpenCC 的 TWPhrases 只收 IT 词（U盘→隨身碟），不管游戏里真正会撞的
那七个：程序→程式、循环→迴圈、数据→資料、鼠标→滑鼠、设置→設定、运行→執行、重置→重設。
这七条人工定，而且**两边流水线都先过一遍 MANUAL**，否则烘焙脚本每次都会把这七条当成「差异」报出来。

体检脚本 `gen_hant.py` 同时跑两套：`runtime()`（游戏里那四趟）和 `reference()`（完整 `s2twp`），
逐条比 299 条文案的差异。当前 **需要补词 20 个 · 仍不一致 0 条**。

### 31.4 漏翻是静默失败 —— 三道兜底

漏包一个 `t()` 不会报错，只会在英文界面里混一句中文。三道网：

1. **两个汇聚点**：`_label()` / `_button()` 里统一 `I18n.t(text)`，覆盖大部分文案；
   VM 的三个出口（`op_short` / `op_tag` / `op_help`）和 21 处 `_fail()` 各自包一层。
2. **静态扫描**：`scan_strings.py --check` 枚举源码里所有中文字面量，逐条查表。
   这一条曾经骗过一版 —— 正则写的是 `[^"\\]*`，把带 `\n` 的长句整条跳过，于是「覆盖率 100%」
   是假的。改成允许反斜杠 + `unescape()` 之后才真。
3. **运行时扫控件树**：测试把语言切到英文，递归收集所有 Label/Button 文字和 tooltip，
   出现任何汉字就失败（四个语言名 `繁體中文/English/繁中/简中` 放行 —— 它们永远用自己的语言写）。

### 31.5 英文比中文占地方：四处具体的排版账

中文 1 个字 ≈ 英文 2 个字符，而英文还不能从中间断开。四处硬伤：

1. **折行必须按词。** 按字排会把 `accumulator` 切成 `accumulat / or.` —— 中文读者看不出来，
   英文读者一眼就知道这游戏没做过英文。`_wrap_chars` 改成「遇到空格才断，撇号算词内」。
2. **卡面子标题要缩。** `Jump if negative (compare)` 在 127px 的指令牌上被裁成
   `Jump if negative (compa` —— 改成 `Jump if <0 (compare)`。
3. **挂牌文案要缩。** `已数 %d / %d` 直译成 `Counted 3 / 8` 在 88px 的木牌上裁字，改成 `%d of %d`。
4. **纸条要能横着长。** 第 6 关的英文提示按 640 宽排要 5 行，第 5 行正好被截成省略号，
   截掉的还是「所以你得自己扔」这句关键做法。加到 5 行之后新的问题来了：
   纸条高度由折行决定，可用空间由**窗口高度**决定，两者没关系 —— 1280×800 上只剩 5px 缝。

最后一条值得单独说。第一版把宽度写死 700，截图上看是「贴着」，放大才知道是「差点叠上」，
而且窗口一矮就真叠上。修法不是把纸条往上挤（上面就是任务牌），而是**宽度按阶梯往上试**：

```gdscript
for cand in [minf(w * 0.56, 700.0), minf(w * 0.72, 880.0), limit_w]:
    nw = minf(cand, limit_w)
    lines = _wrap_chars(font, text, 13, nw - NOTE_TEXT_X - 16.0, NOTE_MAX_LINES)
    if _note_h(lines.size()) <= room:      # room = fy - NOTE_GAP - top
        break
```

取第一个「竖着放得下」的宽度。天空比地面富余得多 —— **「更宽」永远比「更高」便宜**。
几何抽成了静态纯函数 `Stage.hint_layout()`，测试因此能在**没有渲染帧**的情况下量它：
每一条提示 × 三门语言 × 两种舞台高度，最小间距必须 ≥ 8px（当前 1280×800 实测 17px）。

### 31.6 换语言 = 整屏重建

`_relocalize()` 把界面拆光重建，代价几十毫秒。这么做的理由不是省事，是**正确**：
逐个控件回填要维护一份「控件 ↔ 文案」的清单，清单漏一项就永远错一项，而且不报错；
重建则天然覆盖所有文案，代价只是要把程序、当前关、选中行、提示级别这些状态搬过去。

搬哪些：`program`（玩家写的程序）、`li`（当前关）、`sel`（选中行）、拖拽中的行、
`hint_stage`（提示级别）、`scroll` 位置。测试钉住前两条：切英文再切回繁体，程序行数一变就失败。

语言名两处例外：按钮上永远显示「按了会变成的那门语言」（`繁中` / `EN`），而且永远用**它自己的**
语言写 —— 英文界面里出现「繁中」不是漏翻，是必须长这样。

### 31.7 结果

| | v21 | v22 |
|---|---|---|
| 语言 | 只有简中 | **简中 / 繁中 / 英文**（简中只作原文语，不给玩家选） |
| 首次启动 | 无 | IP → 区域表 → 繁中或英文；失败退系统语言 |
| 切换入口 | 无 | 抬头右上角一枚 `繁中` / `EN` 按钮 |
| 文案条数 | 300 条硬编码 | 300 条 = **一张 126KB 的表**（`data/i18n.json`） |
| 繁体来源 | — | OpenCC 同款四趟 + 7 条人工用词，与完整 `s2twp` **0 差异** |
| 漏翻检测 | 无 | 静态扫描 260/260 · 运行时扫控件树 |
| 回归 | 124 / 5 / 151 | **124 / 5 / 184** |
| 布局余量 | 574 / 776 | 574 / 776（不变） |

新增 CLI `--lang=zh_Hans|zh_Hant|en` 和 `--country=XX`。

## 三十二、补完：声音、加速、以及四条「不新增元素」的修法

### 32.1 先报一份缺口清单

v22 交付之后的问题是「这游戏还缺哪些元素」。我先列了八条，分三档。分档依据只有一条：
**缺了这一条，已经做好的东西是不是白做了。**

| 档 | 缺口 | 后果 |
|---|---|---|
| 一 | 全程 0 处声音 | 「运行」是一个没有反馈的过程，程序对不对只能看结果 |
| 一 | 运行时节奏恒定 | 二十步和两步一样长，玩家的注意力撑不到最后一步 |
| 二 | 全三星没有收尾 | 第 40 关打完和三关打完长得一样，四十关这个故事没有结尾 |
| 二 | 前 90 秒没有引导 | 新手看到的第一屏是空白编辑区 + 一块 Instruction 面板 |
| 二 | 提示看过就回不去 | 点过一次「看提示」，想再看思路只能换关 |
| 三 | 无导入导出 | （**否掉了**，见下） |
| 三 | 出错/成功只靠红绿 | 红绿型色盲看这两个状态都是黄褐 |
| 三 | 无设置项 | 音量只能跟着系统走 |

第 6 条被当场否掉，理由是我自己也答不上来：「导入导出实际意义是为啥？」——这个游戏没有
「作品」需要带走，四十关的进度本来就存盘，玩家唯一可能想带走的是自己的程序，而它只在一关里有效。
**一条需求如果说不清它在替谁解决什么，那它就是在给自己找事。砍掉。**

第 2 条被改了需求，而且改得比原方案好：

> 「可以不给手动倍率，还是根据运行过程逐步加快播放倍率的效果。这样玩家在体验运行时不断的
> 每小步成功音效和画面提醒有种 COMBO 越来越快的刺激感」

原来是「给玩家一个 1×/2×/4× 的按钮」。改成「你跑得越顺，它自己越快」——省掉一个控件，
把加速从「一个玩家要去按的东西」变成了「一个玩家挣来的东西」。这一改定了整章的技术方向。

### 32.2 声音：零素材，六种音全部现场合成

项目里没有一张音频文件，全部用 `AudioStreamWAV` 现场合成（`scripts/sfx.gd`，163 行）。
和「舞台没有一张位图」是同一个取舍：零素材、随时可调、体积为零。

更实际的原因是**音高必须跟着 COMBO 走**。素材包里翻不出「同一个音高半音」的东西。

```gdscript
const RATE := 22050        # 音效上限 11kHz，够用；采样率减半，生成快一倍
const POOL := 8

"click": _note(680.0, 0.036, 1.0)              # 每一步，很轻，像节拍器
"wood":  _note(300.0, 0.070, 1.0, 0.42, 3.0)   # 动木牌：300 + 900 的 1:3 叠加＝空腔感
"out":   _note(523.25, 0.130, 1.0, 0.28, 2.0)  # 推一只羊过栅栏
"err":   _sweep(370.0, 196.0, 0.170)           # 绊倒：往下滑
"win":   _arp([523.25, 659.25, 783.99, 1046.5], 0.095)
"ding":  _note(1568.0, 0.280, 1.0, 0.22, 2.0)  # 刷了自己的记录
```

三个细节值得记：

1. **起音给 4ms，不给 0。** 从满幅直接开始会「啪」一声——那是爆音，不是音效。
   包络是 `min(t/0.004, 1) * pow(1 - t/dur, 2.4)`，衰减指数 2.4 比 2.0 更像敲击而不是拨弦。
2. **变调走 `pitch_scale`，不重新合成。** `pow(2.0, semitone / 12.0)`。高速时每 75ms 就要一个音，
   现场合成会卡帧；六个流合成一次总共 93ms，之后只是改一个浮点。
3. **8 路 player 池。** 一个 `AudioStreamPlayer` 播新流会掐掉上一条。间隔 75ms 时池子不够
   就会「漏拍」——那正好是 COMBO 该有的反效果。

`wood` 用 300Hz + 900Hz 的 1:3 叠加：纯正弦听起来像电子滴，加一条三次泛音才有「敲到木头上」的空腔音。
`err` 用扫频（370→196，`u*u` 曲线）而不是两个分开的音，因为绊倒是**一次**连续的下坠。

### 32.3 渐进加速：公式、边界，和三条同时在说的通道

```gdscript
const STEP_SLOW := 0.26      # 第一步
const STEP_FAST := 0.075     # 封顶
const STEP_DECAY := 0.86

func _cur_tick() -> float:
    return STEP_FAST + (STEP_SLOW - STEP_FAST) * pow(STEP_DECAY, float(combo))
```

指数收缩而不是线性：**起速感全部来自头三下**（0.26 → 0.224 → 0.192），第 20 步时已经到了 0.077。
线性会得到一个「匀速变快」的过程，玩家感觉不到自己在加速，只感觉这一关变长了。

三个边界，每一个都是被截图或手感逼出来的：

- **`combo` 只由自动运行累积，手动单步不涨。** 否则一步步点 20 次再按运行就直接全速了——
  那叫「可以预支的加速」，不叫「跟着手感长出来的加速」。单步照样给声音（这一步做对了要给确认），
  只是不给涨幅。
- **出错 / 重置 / 切关归零。** 加速是对「连续做对」的奖励，绊倒了就得重新挣。
- **`_process` 里用 `while` + guard，不用一次 `if`。** 间隔掉到 75ms 时，一帧（16ms）可能连跑好几步；
  只 `if` 一次会让实际速度卡在「一帧一步」，加速到后面就不涨了。guard 8 是防死循环的保险。

```gdscript
var guard: int = 0
while playing and acc >= tick and guard < 8:
    acc -= tick
    _step_once()
    guard += 1
```

加速由三条通道同时表达，缺一条就变成「只是变快了」：

| 通道 | 形式 |
|---|---|
| 时间 | 间隔 0.26 → 0.075（3.5 倍） |
| 耳朵 | `click` 随 combo 升调，每步升一个半音，**封顶 12 个**（一个八度） |
| 眼睛 | 执行行拖尾：起步亮一行，全速三四行一起亮＝一道往下扫的亮痕 |

`click` 封顶 12 半音是对的：再往上就进入刺耳区，而且到那时间隔已经封顶了，继续升调只会变成噪音。

**`out` 的音高跟的不是 combo，是「今天第几只」**：

```gdscript
"OUTBOX": sfx.play("out", float(mini(vm.outbox.size(), 12)))
```

一个八度分给 12 只羊。数满一关就是一段完整的上行音阶——玩家不用看「已数 3/8」的牌子，
光听就知道自己数到哪、还剩几只。这是这一章里最「游戏」的一个决定：它把一个**进度**变成了一个**旋律**。

### 32.4 节拍可视化：两次都失败了，最后落在已有的东西上

加速需要眼睛也能看见，为此试了两个方案，都删了：

**第一版：草地上撒光点。** 每一步在羊走过的地方留一个点，代表节奏。截图一看像噪点，
换四角星之后仍然糊——问题不在形状，在**位置**：草地是画面里最不该出现「界面元素」的地方，
在那里放任何几何形状都会被读成「画面脏了」。

**第二版：底部 12 格凹槽灯。** 每步点亮一格。位置偏（在舞台最下沿、离视线远）、对比弱、
而且和右下角「周期 ÷ 件」的仪表**语义重复**——两个都在表达「进度到哪了」。

两次失败之后看清了一件事：**不需要新元素，现有布局里有一个维度还没用——程序列亮几行。**

于是有了拖尾（`_trail`，最多 3 行，去重）：

```gdscript
func _push_trail(pc: int) -> void:
    if not _trail.is_empty() and int(_trail[0]) == pc:
        return            # 原地打转的循环只该亮一行，不该把整列都染绿
    _trail.push_front(pc)
    if _trail.size() > 3:
        _trail.resize(3)
```

去重这条不只是省性能。`JUMP a` → `JUMP a` 这种死循环，如果每步记一行，两行会交替亮成一片闪烁；
去重之后它稳定地亮一行，**看得出来它在原地打转**——顺手把一个调试信息送给了玩家。

拖尾的亮度分三档（`TRAIL_K = [0.62, 0.42, 0.24]`）：最近的一行最亮，第三行淡下去。
第一版写成「0.55 / 0.55 / 0.30」——最近两行一样亮，看上去就只是「有两行变绿了」，
读不出「一道往下走的痕迹」。上限不许到 1.0：那是「正在执行」的纯绿，拖尾只是刚踩过的脚印。
截图 `_shots/v23/trail_sixth.png` 里第 6 关跑到 `MOVETO 0`，行首 `▶` 落在第 5 行，
第 2 行比第 1 行更绿 —— 那两级就是 0.62 和 0.42。

### 32.5 色盲第二通道：征用行号，不新增一栏

红绿型色盲看「执行绿」和「出错红」是两个相近的黄褐，而这两个状态恰恰是运行时**唯一要紧**的信息。
四态里「出错」还有羊绊倒和一行字兜底，「正在执行」那一行却只有颜色——所以颜色之外得再给一个形状。

第一反应是加一列状态图标。代价：表头要加一格、缩进要重算、跳转线的车道要往右挪 14px。
为了一枚 12px 的箭头改动三条对齐规则，不值。

真正该问的是：**运行时哪一列最不重要？** 答案是没有争议的——行号。玩家在运行时不会去数「这是第几行」，
他数的是「跑到哪了」。

```gdscript
var want: String = "%02d" % (i + 1)
if is_err:
    want = "✕"; col = Kit.RED
elif is_pc:
    want = "▶"; col = Kit.GREEN
```

`▶` 和 `✕` 的形状差得足够远（一个是三角形、一个是对角交叉），在缩略图上也能分辨。
停止时换回 `01`，所以这一列在两种状态下的**宽度完全一样**，列宽不用动。

### 32.6 提示回看：把「记录」和「显示」拆开

原来的问题是：点了「看提示」，按钮就永久禁用——因为 `hint_stage` 同时承担了两件事：
记录「他看过第几级提示」（决定星数）和「现在贴在舞台上是哪张」。

拆成两个变量就解决了：

| 变量 | 语义 | 会不会让星数变少 |
|---|---|---|
| `hint_stage` | 记录：他最多看到过第几级。**只增不减** | 会，且只认这一条 |
| `hint_view` | 显示：现在舞台上是第几级 | 不会 |

回看就是改 `hint_view` 而不碰 `hint_stage`。星数判据读 `hint_stage`，所以来回翻看十次
和看一次的结果完全一样。按钮文案也跟着变成 `回看思路` / `看参考解说明 · 回看`，
告诉玩家「这东西是可以再打开的」。

顺便修了一处措辞：空程序时的占位行写着「把指令拖到右下角」，而指令面板在**右上**。
这种错是纯文字上的，但玩家会真的往右下角找——那里是「周期 ÷ 件」的仪表。

### 32.7 全三星：判据现算，不靠计数器

第 40 关打完和第三关打完，结算卡长得一模一样。四十关的故事没有结尾。

加一张「四十关 · 全三星」的卡，判据是**遍历现算**：

```gdscript
func _all_stars() -> bool:
    for i in levels.size():
        if _stars_of_idx(i) < 3:
            return false
    return true
```

不用累加计数器（`allstar_count += 1`）的理由：计数器会和现实脱钩。玩家删了档、我以后调整了
星的标准、或者存档只写进去了一半——计数器都会留下一个「他说过全三星」的假状态，而且永远不会自己纠正。
遍历 40 次的成本可以忽略。

`allstar_ack` 落盘只认一次（这张卡只该看一次）。`_claim_allstar()` 在 `demo_mode` 下直接返回 false——
截图不该改玩家进度。

**这张卡不能照搬单关那两行。** 第一版直接复用了「指令 / 速度」两行，结果打出来：

```
速度   0.00 / 30.75   ✕
```

因为 `target_speed` 是第 40 关的目标（周期÷件，极慢），而 `_show_win_card` 里 `vm` 是第 40 关的 VM。
**在一张「你全做完了」的卡上出现一个红叉，是最伤人的那种错。** 改成两行：

```
星数   120 / 120   ✓
关卡    40 / 40    ✓
```

徽章也清了——标题已经写了「四十关 · 全三星」，再挂一枚同样的徽章是废话。

### 32.8 新手引导：判据不需要存档字段

第一屏是空白编辑区 + 一块 Instruction 面板，没有任何东西告诉玩家「先点一块牌子」。

```gdscript
func _is_new_hand() -> bool:
    return li == 0 and program.is_empty() and saved_programs.is_empty()
```

之所以不新增存档字段（`has_played: bool`），是因为**这个判据本来就是可推导的**：
一关都没写过程序 = 新手。而且它天然带着一个好性质：玩家把程序删光时**不会再跳出来烦他**——
那时他已经会了，不需要再教。

做法是给指令面板的**第一块牌**做一次 0.62 秒的呼吸（`modulate` 提亮到 1.35, 1.3, 1.1）。
只点一块：把整片面板都点亮等于没点亮。同时把「未选中行」的提示改成
`点一下右边任意一块指令牌，它就会变成一行代码`。

第一版只有呼吸，验收时出了问题：**在一张静止的截图上，两块牌长得一模一样**，
我指不出「在呼吸的是哪一块」。呼吸是动画，而交付物是截图——凡是「只靠动效表达」的设计，
都要再补一个静态也能看见的通道。所以额外钉一圈琥珀描边（`_mark_guide()`：`border_color` 换
`Kit.AMBER`、`border_width` 1 → 2），不再是新手时再收回去。测试钉住这两头。

改描边而不是改形状，是为了守住全篇那条规矩：**状态只换颜色，不改形状**——
形状一变，整列就散成表格了。

### 32.9 设置：和语言共用一个文件，分 section

`settings.cfg` 原本只存语言。加音量时如果直接 `save()` 一个新配置，语言的 section 会被冲掉。

```ini
[i18n]
lang=zh_Hant

[audio]
volume=0.8
```

写之前必须 `load()` 一次（否则文件里其他 section 丢失），改自己那一节，再存。
测试钉住了这一条：改音量不会影响语言，改语言不会把音量打回 80%。

**滑条要长成游戏里的滑块，不能长成进度条。** 默认的白轨白点在深蓝面板上读起来像一枚控件：
轨道用凹槽（`Kit.well(Color("062c4b"), 5)`）、已走过的一段用金色填充（`Kit.well(Kit.AMBER, 5)`）——
凹下去 = 只读，填色 = 已经给出去的量，这是全篇一致的「凸起能按、凹下只读」语言。

浮层宽 392px 不是随手写的：卡片宽度由那句说明反推，而**繁中比简中长约 8%**。
按简中量出来的 300 让繁体那句只剩两个字掉到第二行（`樂。` 孤零零一行），所以量宽必须按最长的那门语言量。

## 三十三、三个补丁：静音的音箱、看不见的「空了」、还有 --fill

### 33.1 切语言后全程静音 —— 整屏重建拆掉了不该拆的东西

达叔实测发现：点一下语言切换，音效就全没了。

根因一句话：`_relocalize()` 的拆除是 `for c in get_children(): remove_child(c); c.queue_free()` ——
**它拆的是 main 的全部子节点，而 sfx 就挂在 main 上**。拆完 `sfx` 变量还指着那个（已释放的）节点，
之后每一次 `sfx.play()` 都打在一个死对象上：不报错（demo 环境）、也不出声。
「整屏重建」这个决定没错，错的是**拆除范围没有豁免名单** —— 界面要重建，音效池不要。

```gdscript
for c in get_children():
    if c == sfx:
        continue      # 音效层不重建：它持有 8 路 player 池和主音量
    remove_child(c)
    c.queue_free()
```

测试钉住：切一次语言，`sfx` 必须还活着、池里 8 个 player 一个都不能是 freed、音量不重置。
这类 bug 的麻烦在于**它不崩**——声音没了，玩家只会以为游戏本来就没有声音。

### 33.2 「羊圈是空的」—— 不是渲染 bug，是两种空没被区分

达叔报「有些关卡左侧看不到羊」。排查结果：数据是对的，问题在**表达**。

- 第 21/25/26/34/38/39 这类进阶段关卡，`inbox` 本来就只有 1 个数（题目是「给我 N，输出一串」，
  N 就是那一只羊）——羊圈里一只羊孤零零，是对的；
- **第 3 关「照抄一块」`inbox` 是空的**：这关只从木牌拿数（`COPYFROM 0` 循环），根本没有羊进来。

真正的错是：空羊圈上那行「空了」是 12px、无描边、灰蓝色，压在深绿草地上**几乎不可见**——
玩家看到的就是「羊圈坏了」。

修法是把两种空分开说，且都按「羊圈 INBOX」标题同款处理（深色描边才浮得出来）：

| 情况 | 文案 |
|---|---|
| 开局就空（题目不给羊） | `这关不用数羊` |
| 跑完才空（数完了） | `羊都数完啦` |

区分靠 `configure()` 时记一次 `pen_starts_empty`（开局时 `inbox_left` 是否为空）——
它是关卡属性，运行中不会变。en 文案：`No sheep to count tonight` / `Every sheep is counted`。

这一条顺便验证了 v22 的那套「原文即 key」流程：新加两句 → `--dump` 列出来 → 补 en →
`--check` 回到 157/157，两分钟的事。顺手的决定：**开发者日志（print）一律用英文**——
i18n 只收玩家看得到的文案，调试输出混进去只会让体检报一条假漏翻。

### 33.3 `--fill`：把参考解铺进存档（验关用）

达叔要手动跑 20–40 关看过程，一条条点不现实。加了：

```bash
...console.exe --path . --fill=20-40    # 范围；也支持 --fill=21 / --fill=all
```

把参考解 parse 成程序写进存档的「我的解」位置——打开那些关就是现成的答案，按运行就能看过程。
三个边界：

- **铺完自动退出**：这是批处理动作，不开窗口干等；
- **会覆盖玩家自己写的程序**，所以只做在命令行开关里，且打印一句提醒；
