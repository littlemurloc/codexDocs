# 2026-10-29

## Human Resource Machine 逆向 + Godot 复刻原型

**需求**：分析 Steam 版 HRM 工程目录，评估能否用 Godot 重构同类游戏。

**逆向结论（已验证）**
- 引擎：Tomorrow Corporation 自研 C++ 引擎，整个游戏只在单个 120MB exe 里，无外置资源文件。
- 资源包：`.rsrc` 里一项 `RCDATA type=20480 id=1`（119,798,208B）。
  pak 格式 = `u32 ver(1) | u32 count(1643)` + 1643×16B 索引 `(u32 hash, u32 flag, u32 offset, u32 chunkSize)`；
  chunk 64 字节对齐，`flag=1` 为 `(compSize, rawSize, zlib)`，`flag=0` 为 32B 头 + 裸 PCM(44100Hz)。实测 1482 zlib + 161 裸存。
- 节点格式 `u32 type | u32 headerSize | 字段`：type1=纹理 696 张（未压缩 RGBA8）、type8=音频 165、type7 含 5.6MB 位图字体（字形用 ASCII 字符画存）、DXBC 着色器 43、type19=语言索引（19 语言）。
- 语言表（548KB 节点）含全部关卡名与旁白，可完整读出；**关卡数值（in/out 流、允许指令、目标值）不在明文，编译进二进制节点，未提取**。
- 存档 `%APPDATA%\Human Resource Machine\profiles.bin` 15MB，首字节 `4B23E5A6`，加密/混淆不可直读。

**交付**
- `docs/HRM-拆解与Godot重构方案.md`：完整拆解 + 可行性 + 版权红线 + 里程碑。
- `hrm_godot/`：可运行 Godot 4.7 原型。`scripts/hrm_vm.gd` 实现 11 指令 VM（手/地板/收发箱/标签/周期），`data/levels.json` 11 关自研关卡（含 ref 参考解，SIZE/SPEED 目标自动算），`main.gd` 全代码 UI（拖拽编辑器 + 跑/单步/暂停），`tests/test_levels.gd` 37 项无头检查全绿。
- `_hrm_analysis/extract_pak.py`：可复现的资源包解析脚本 + game.pak + files/（约 240MB，可删）。

**踩坑记录**
- HRM 语义：`COPYTO` 会清空手；**没有"丢弃"指令**，扔掉一个值必须 `COPYTO` 到地板格。我最初的三倍房/零清除者解都因此跑不通，靠自建 VM 的报错定位。这条约束是原版难度的主要来源。
- `COPYTO 0 + ADD 0 + ADD 0` ≠ ×3，因为 ADD 加的是地板上原值 → 得 `COPYFROM 0` 捡回来。
- Godot 截图验收手法：`main.gd` 里解析 `--shot= / --level= / --run=` 参数，`await RenderingServer.frame_post_draw` 后 `get_viewport().get_texture().get_image().save_png()`。
- Godot 默认字体无 CJK，需要在 `_ready` 里 `FontFile.load_dynamic_font("C:/Windows/Fonts/msyh.ttc")` 塞进 Theme；未确认的符号字形（⏸⏭⟲✔✘）会渲染成方框，改用中文字/ASCII。
- 脚本改坏会导致 windowed 启动无输出被 SIGTERM（残留进程堆积），排查手段：先 `--headless --quit` 看解析错误。

**待用户决策**：定位（内部工具 vs 上架，决定是否必须换皮换关）、美术复用现有旅行/像素管线、关卡规模 20 还是 40+。

- 舞台坐标**不能用绝对像素**：`configure()` 在布局完成前调用，`size` 是 0，员工会停在 x=0 被裁掉。改成符号化目标 `target_key`（"inbox"/"outbox"/"slot:i"），绘制时再算 x，同时兼容窗口缩放。

**测试方式**：`--level=N --run=K --shot=path` 直接载入第 N 关跑 K 步截图；跑通全部关卡可批量 `for L in 1..4; do ... --run=200 ...` 生成存档。

## 第四轮：开发期免编译工作流（用户问"有没有直接用编辑器测试玩"）

**结论/口径**：Godot 工程目录本身就是源码，引擎直接解释执行，`--export-release` 出的 exe 只是分发快照。开发循环 = 改文件 → 重开一次（约 2 秒），不涉及导出。

**新增**
- `dev_game.bat`（根目录，CRLF）：用 **console 版**引擎跑工程，黑窗里能看到 `push_error` / `print` / 脚本解析错误。**改代码时首选这个**，GUI 版看不到报错。
- `start_game.bat` 保留（GUI 版，无黑窗，纯玩）。
- `main.gd` 加 **`L` 键热重载 `levels.json`**：`_reload_level_data()` 重读数据 → `load_level(原索引)`，关卡数与进度都保留。改关卡数值连重启都省了。导出后 `res://` 是打包内容，读到的仍是快照，只对跑工程有效（已在注释里写明）。
- `tests/test_ui.gd`：界面层冒烟测试 **10 项**（主场景能起 / 20 关 / 初始关 id / 参考解解析 / 状态栏构建 / 切关 / 热重载后索引与目标 SPEED 不变 / 越界索引夹到末关）。

**踩坑**
- `SceneTree` 脚本里 `_initialize()` 阶段 `add_child` 后 **`_ready` 尚未执行**（树未 ready，推迟到首帧），布局控件全是 null，断言会全挂且报一堆 "assignment to Nil"。**界面层断言必须放在第一次 `_process()` 里**。
- 另有真实健壮性隐患：`levels` 为空时 `load_level` 会 `levels[-1]` 越界（`clampi(0,0,-1)` 返回 -1）。正常流程有 `if levels.size() > 0` 保护，但 `_reload_level_data` 必须自己判空——已加。

## 第五轮：关卡设计方向探针（用户问"还能做哪些自有玩法"）

新增 `tests/test_ideas.gd`：把候选关卡方向先在 VM 里跑通再推荐，避免画饼。**4 个方向已验证可跑**：

| 方向 | 流形状 | 参考解 SIZE | 关键难点 |
|---|---|---|---|
| 过滤·只留正数 | N:M | 6 | 没有 DROP，丢弃必须 `COPYTO` 占一格 |
| 压缩·连续去重 | N:M | 13 | `SUB` 后手被污染，**必须先 `COPYTO` 清手才能 `COPYFROM` 捡值** |
| 展开·n 变 n 个 1 | 1:N | 10 | `BUMPDN` 会把手塞满，循环尾必须清手 |
| 滑窗·相邻求和 | N:N-1 | 10 | 必须"预读"：第一个值只存不输出 |

**指令集的硬边界（重要，决定了哪些玩法根本做不了）**
- 这套 VM 是**寄存器机，不是栈机**：`COPYFROM/COPYTO` 的参数只能是**常量**（`parse_program` 里 `arg = int(toks[1])`），不能让手里的值当地址；也没有计算跳转。→ **栈、数组、任意查表（按索引取 mem）全部不可行**。这也解释了原版为什么没有栈关。
- `_is_complete()` 要求 `inbox.is_empty()`，所以**"读到哨兵就收工、忽略剩余数据"做不了**（探针实测报"程序跑到底了，但任务还没完成"）。要做这类关卡必须先改判定。
- 推论：关卡设计必须满足「**最后一个输入恰好是要消费的那项**」，否则循环回 `INBOX` 会报"INBOX 已经空了"。

**发现的 3 个 UI 缺陷（本轮只记录，未改）**
1. **参考解预填**：`load_level` 里 `program = parse_program(level.ref)`，玩家打开任何一关编辑器里已经躺着标准答案，按运行就过关。当初是为自动化截图留的，对玩家是灾难。
2. **玩家的解不保存**：`_record_win` 只存 cleared/size/speed，无 `program` 字段；重进关卡看到的是参考解。
3. **报错不定位**：`_fail` 不记录 `pc`，UI 只说"第 N 个应该是 X"，不告诉哪一行崩的。

## 第六轮：HUD 与编辑手感（用户反馈：HUD 够不够 / 指令没法拖进程序只能尾部追加）

### 拖拽的真凶（重要教训）
`_select()` 原本走 `_rebuild.call_deferred()` —— **点选任意一行就销毁并重建全部行节点**。拖动起始行的瞬间 `gui_input` 触发 `_select` → 整列重建 → 被拖的节点被 `queue_free`，拖拽自然断掉，于是"只能用点击追加到末尾"。
修法：`_select` 只改配色（`_refresh_row_highlight()`），**绝不重建**。重建只发生在结构变化时（`_after_edit`）。

### 本轮改动
- **PC / 报错行高亮**：`hrm_vm.gd` 新增 `last_pc`（刚执行的指令下标）、`fail_pc`（报错定格行，在 `_fail` 里取 `last_pc`）。`prog_row.gd` 新增 `set_state(sel, pc, err)` 只改 StyleBox，绿框=执行中、红框=出错、蓝底=选中。
- **视野跟随**：`_refresh_row_highlight` 里 `scroll_rows.ensure_control_visible()`，PC 跑出可视区时自动滚。
- **拖放语义**：落在行**上半插到该行之前、下半插到之后**（`_can_drop_data` 里 `at_position.y > size.y*0.5`），拖动时用子节点 `ColorRect` 画 4px 金色指示线（**不要用重写 `_draw`** —— PanelContainer 的 stylebox 绘制与脚本 `_draw` 顺序不可靠）。
- **空程序可放置**：`_rebuild` 空程序时改为插入一个 ProgRow 占位（不是 Label），第一条指令能直接拖进去。
- **撤销/重做**：`undo_stack` / `redo_stack`，`_push_undo()` 在每次编辑**前**快照，上限 100 步。Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y。
- **Alt+↑↓ 移动行**、**Ctrl+D 复制行**（比拖拽精确，推荐路径）。
- **插入位提示**：面板上方动态显示"已选第 N 行 · 新指令插到第 M 行"，消除"只会在尾部追加"的误解。
- **SPEED 摊开**：底部显示 `14 周期 ÷ 3 件`，精度 1 位 → 2 位。
- 行高 38 → 34，SIZE 15 的程序可见行数从 8 增到 9。
- 新增调试参数 `--bad=1`：塞一条必失败的 `OUTBOX`，用来截图检查出错行标红。
- `test_ui.gd` 扩到 **25 项**（拖放链路、撤销重做、上下移动、空程序拖入、last_pc/fail_pc、SPEED 公式）。

### 已知未做
- 关卡打开仍是**参考解预填**（`load_level` 用 `level.ref`），玩家的解不保存。这两条是体验最大短板，等用户拍板再动。
- 「读出哨兵就收工」需改 `_is_complete()`，未做。

## 第七轮：空白开局 + 三级提示 + 数羊主题（用户两问）

### A. 按上一轮建议改掉的两处设计缺陷

- **空白开局**：`load_level` 不再读 `level.ref`，改成 `_program_from_save(key)`，只有玩家自己写过才有内容。
- **存自己的解**：存档升级到 `{ver:2, levels:{}, programs:{}}`。`_stash_program()` 在每次编辑后把 program 快照进 `saved_programs`；写盘**延迟 0.5s**（`_dirty` + `_save_cd`），避免每敲一下都写文件。切关前先 `_stash_program()`。
- **旧存档自动迁移**：顶层没有 `"levels"` 键就视为旧格式，原地接过来。
- **三级提示**（`hint` / `hint2` 字段 + 第 3 级填参考解）：卡满 60s 才生效，按钮常驻但半透明 + tooltip 显示剩余秒数。用过第 3 级的关卡标记从 `★` 变 `☆`。
- **`demo_mode`**：CLI 带 `--shot=` 时自动铺参考解且**不写存档**，否则截图会污染玩家进度。
- **测试存档隔离**：`SAVE_PATH` 改为变量 `save_path`，`test_ui.gd` 在 `add_child` 之前把它指到 `user://test_progress.json`（**必须赶在 `_ready` 前改**，否则 `_load_progress` 已经读了真实存档），跑完删文件。测试扩到 **43 项**。

### B. 主题改造：办公室 → 夜晚牧场（数羊）

映射：INBOX=羊圈牵羊、OUTBOX=推羊跳过栅栏、手=怀里抱的羊（编号浮头顶）、地板格=草地插的木牌、出错=被栅栏绊倒、过关=Zzz+月亮变亮。
11 条指令里 10 条能落到物件上，**只有控制流（JUMP/JUMPZ/JUMPN）无实体**，与原版一致，玩家不介意。

**两个必须接受的设计张力（已写进文档第八章）**
1. 数羊是顺序计数，游戏在做算术 → 设定成"数到半梦半醒、羊的编号开始自己翻倍了"，荒诞感即叙事资产。
2. 助眠情绪 vs 解谜紧张 → 不追求"真的催眠"，定位"失眠者的荒诞牧场"。

**这一轮踩的新坑（都是画出来才发现，纸上推演推不出）**
- **木牌不能立在地平线上**：角色和木牌都立在 `floor_y` 上必然互相遮挡。解法是把木牌**平铺到 `floor_y` 以下的草地前景**，角色站木牌后方。一次坐标分层解决。
- **`_handle_cli` 里 `stage.size` 是 0**：`_ready` 阶段布局未算，所有 `_key_x()` 返回负数（实测 `hop_from = -220`）。凡是在 `_ready` 里算坐标的，都得在 `await process_frame` **之后**按真实尺寸重算一次。
- **`--hop` 定帧失效**：`_process` 会把 `hop_t` 推进到结束。加 `pose_lock`，`pose_lock >= 0` 时 `_process` 不推进。
- **羊在 30px 尺度下不能靠细节**：一开始用 5 团羊毛 + 小眼睛，糊成白云。改成「大椭圆白身 + 深色描边 + 明显黑脸 + 白点眼 + 粗腿」，任何尺寸都认得出。
- **角色站位**：`OUTBOX` 目标从 `_fence_x()` 改成 `_fence_x() - 80`，否则角色站在栅栏正中把它挡住。

**其他**
- 工程改名 `HRM Clone Prototype` → `Sheep Counter`，`user://` 目录随之变化，加了 `_migrate_legacy_save()` 从旧目录搬存档。
- 窗口 760 → 800，程序行高 34 → 30（SIZE 15 的程序基本一屏可见）。
- 报错文案全部改牧场语境，保留技术名在括号里：`"怀里还抱着一只羊，腾不出手去羊圈牵（INBOX 要求手空）"`。
- 20 关全部改名（Mail Room → 第一只羊 / Tripler Room → 三只一堆）。
- 新增调试参数 `--hop=0~1`（钉住跳跃动画某一帧）。

## 第四轮：拖拽手感 + 羊圈可读性（主人反馈两点）

**主人的问题**
1. 拖拽还是要找非常精确的位置，不能直接放到底部，插入时上下行也不会让位。
2. 左侧小羊看不到编号，而且要删掉左侧栅栏（挡视野）。

**拖拽：根因不是阈值，是判定模型**
- 内建 DnD 只问"鼠标正下方那个控件 `can_drop_data`"，不往下也不往上问 → 4px 行缝、行内按钮/SpinBox、列表空白全是没有归属的死区。
- 改成自建状态机：`_input()`（早于 GUI）统一接管拖拽，命中判定放宽到**整块编辑器面板**（grow 40px），纵向位置换算成插入行号；列表下方空白 = 末尾。抬键 `set_input_as_handled()`，否则会误触行内 `×` 删除按钮。
- 判定用**还原掉空隙后的行坐标**（`i >= _gap_idx` 时减 `gap_h + ROW_SEP`），空隙长高、行下移的过程中判定点不跳。
- 插入位做成真实节点 `scripts/drag_gap.gd`（插进 VBox、高度 0→ROW_H），长高就把行真的挤下去，虚线框 + "放这里"。这才是"位置自己挪出来"。
- 附带坑：拖拽吞掉抬键 → `BaseButton.press_attempt` 不复位 → 指令面板按钮留下"按下去"的假象。解法是把面板按钮的 `pressed` 样式覆盖成 `normal`。
- 另有：边缘自动滚动、Esc 取消、幽灵卡片跟随、拖拽中切关先 `_clear_drag_nodes()`。

**羊圈**
- 栏杆是前景，横在羊身上挡编号 → 整段删除，只留一块土的暗示。
- 编号直接刷在羊毛中央（深棕 `#3a2f24` + `draw_string_outline` 浅描边），2/3 位自动缩字号；`PEN_SHOW=3`、间距 39→58px（防后一只的头挡前一只的编号）、`+N` 显示剩余、牧羊人站位后移（`PEN_X+70`）。
- 怀里抱的羊、跳跃中的羊也带编号。

**测试踩坑：headless 测不了 GUI 输入**

## 第七轮：COPYTO 该不该叫 PASTE（主人提问）

**结论：直觉抓对了「名字说谎」，但谎点不是缺 PASTE，而是它根本不是 copy。**
- 实测：`COPYFROM` = `hand = mem[n]`（木牌不变 → 源不消失 = 真复制）；`COPYTO` = `mem[n] = hand; hand_full = false`（手清空 → 源消失 = **搬运/存入**）。
- PASTE 会引入三重错误预期：① 粘贴不清空剪贴板，这里写完整只手就空（玩家会试着"粘两次"）；② 粘贴暗示剪贴板历史，这里源永远是明写的"手上的值"；③ PASTE 配不出对偶词形，而 FROM/TO 是同介词两端，配对自明。
- 精确命名应是 CPU 的 `LOAD/STORE`，但**不改名**：词形沿用原版（查攻略、对照 HRM 资料通用），含义补在界面。原则：**词形沿用原版，含义补在界面上**。
- 落地：`OP_HELP["COPYTO"]` 加"不是粘贴：粘贴完剪贴板里还留一份，这里写完手上就空了——是搬进去，不是复制一份"；`OP_HELP["COPYFROM"]` 加"木牌那份抄完还在——这一步才是真正的复制"；木牌分组标题加后缀"（FROM = 从木牌拿，TO = 搬进木牌）"。
- 提炼可复用原则：凡玩家会用日常软件心智模型套的地方，界面要显式否定。已处理三处：没有比较指令 / 粘贴不清空剪贴板 / 跳转跳的是标签不是行号。

**测试**：72 → 75（headless）/ 84（带窗口）。新增 3 条文案断言锁住"不是粘贴""手会空""COPYFROM 才是复制"。文档新增第十二章。截图 `_shots/v6-说明书弹窗.png` 改用第 16 关（同时有 COPYFROM 和 COPYTO，能看出对偶）。

## 第八轮：定名 COPYTO → MOVETO（主人给了这个词）

**结论**：`MOVETO` 成立，且比上一轮我自己推荐的 `STORE` 更好 —— 不冒用 copy，也不需要先知道 CPU 才看得懂。最终是一对**故意不对称**的词：
- `COPYFROM n`：抄到手上，木牌那份还在（真 copy）
- `MOVETO n`：搬进木牌，手空了（move）

不对称本身就是信息：`copy` vs `move` 的区别就是「源还在不在」，和 Unix 的 `cp` / `mv` 同一套直觉。说明书分组标题改成「copy 的源还在，move 的源没了 —— 和 cp / mv 一样」。牌面白话「写木牌」→「搬进木牌 · 手变空」（`搬` 自带搬完这边没了的暗示）。

**改名的真实成本在存档**：`saved_programs` 存的是 `{"op": "COPYTO"}` 字符串快照，只改字面量会让老程序在执行侧匹配不到分支、在 UI 侧 `op_tag()` 返回空串（行右侧一片空白）。

**做法：别名只在边界收敛一次**
- `hrm_vm.gd` 加 `OP_ALIAS = {"COPYTO": "MOVETO"}` + `static func canon_op()`
- 四个入口过一遍：`parse_program()` / `make_ins()` / `step()` 取 op 处（兜底任意老字典）/ `main._program_from_save()`（否则 UI 仍显示旧名）
- 内部永远只有一个名字，不出现「一半旧一半新」的中间态

**范围**：`levels.json` 里 20 关的 allowed/ref/hint/goal 全量改名（sed），`stage.gd` 的 MEM_OPS 判断、三个测试文件同步。

**测试**：75 → 79（headless）/ 88（带窗口）。新增 4 条迁移断言，其中一条是手工塞 `{"op":"COPYTO"}` 进 saved_programs 再 `_program_from_save` 必须返回 MOVETO。关卡 64 项全绿 = 改名没动任何参考解语义。

**文档**：第十二章标了「本结论已被第十三章推翻」，新增第十三章记录命名推导与迁移手法。截图更新为 `_shots/v7-指令牌.png`、`_shots/v7-说明书弹窗.png`。

## 第九轮：运行按钮「不见了」= 页面最小高度溢出（不是按钮丢了）
