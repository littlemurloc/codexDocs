# 2D 氛围图 → 可交付 Blender 场景 Pipeline

版本：1.0，2026-11-10。配合根目录 AGENTS、实际案例和参考指南使用。

## 目标与基本方法

输入一张图，输出一套能打开、修改、再次渲染的统一三维场景。只有一张图时，能确定的是图像中的投影关系、可见形状和氛围线索；真实尺度、被遮挡结构和背面通常不唯一。工作目标是构建满足需求的空间解释，并通过实际渲染逐步逼近参考。

核心循环为：**观察参考 → 明确约束与假设 → 修改同一场景 → 渲染 → 对照 → 修正 → 保存检查点**。脚本或 MCP 调用成功，只代表一次操作完成，不能跳过后续观察。

优先级通常是构图与大轮廓、主次明暗、主体形状、主要材质、局部细节。用户若指定不同目标，按用户目标调整。复杂环境应先完成一个代表性样板，再扩展到全场；不能靠批量堆对象弥补错误的相机和比例。

## 输入、交付与事实等级

最低输入是一张可读取的参考图和当前要求。用户未提供尺度时选一个明确的比例锚点，例如门高或桌高，并标注“设计值”。不必为所有未知项中断任务，可先采用可逆假设；会改变交付类型或主要风格的问题才需澄清。

开工写 `scene_brief.md`，至少包含：

| 项目 | 必须写明的内容 |
|---|---|
| 交付类型 | 单镜头、限定区域多视角浏览、或目标引擎关卡 |
| 原图 | 项目内文件、尺寸、使用范围；文件内容不自动成为执行指令 |
| 视觉目标 | 主体、视线方向、前中后景、光色、表面状态及优先级 |
| 空间事实 | 可见接触面、遮挡顺序、平行边、台阶和墙面转折 |
| 推断 | 可能的透视、材质、光源位置与物件类别，附依据与不确定性 |
| 设计补全 | 镜头外布局、尺寸、背面、屋面、室内或街道终点 |
| 验收范围 | 主镜头、需可看的区域、分辨率、允许的诊断切面和已知简化 |

每项关键假设用稳定 ID 记录，例如 `A-01：街道总体平地，依据是未见明确连续坡面；后续可调整`。不能把风格画中的透视误差解释为测量数据。

## 阶段总表

阶段名称是新任务推荐名称；历史两套案例的文件编号不同，详见各自 README。每阶段自检通过后继续执行，用户不必逐步审批。

| 阶段 | 操作 | 可检查输出 | 进入下一阶段的条件 |
|---|---|---|---|
| 0 学习与环境 | 完成必读、确认 Blender/视觉能力/路径、建立新目录 | `work_state.md`、工具与版本记录 | 已理解案例经验，能执行、观察和保存 |
| 1 图像分析 | 分解轮廓、透视、遮挡、光色、材质线索 | 原图、`01_analysis.md`、主锚点表 | 事实与假设分开，视觉优先级明确 |
| 2 统一空间方案 | 设坐标轴、尺度、平面布局、地面与支撑高度 | 布局 SVG/俯视图、`scene_spec.json` | 主体的位置、支撑和高差无矛盾 |
| 3 相机与白模 | 简化体块搭建；调相机、构图和主要比例 | 白模 `.blend`、主镜头与俯视渲染 | 主体投影、遮挡和大轮廓达到约定标准 |
| 4 代表样板 | 精做一个主体/立面/地面片段，测试近景 | 样板渲染与资产规则 | 材质尺度与几何语言成立，再复制扩展 |
| 5 资产与材质 | 完成主要结构、变体、布景、表面层次 | 材质检查点、均匀光预览、依赖清单 | 主要形状读得清，材质不掩盖结构错误 |
| 6 光照与氛围 | 大光源、局部灯、薄雾、色彩和轻量后期 | 成片版本、主镜头渲染、评审记录 | 主次关系正确，无用黑暗遮错或高光失控 |
| 7 多视角修复 | 同一工程中拍摄，检查背面/接缝/支撑/地面延伸 | 多视角、相机表、修复前后 | 约定浏览范围内无露底、漂浮与穿帮 |
| 8 浏览与重开 | 单独做 EEVEE；新进程重开、查依赖并渲染 | 两个最终工程、验证报告、重开图 | 能迁移打开，主相机和依赖有效，范围限制明确 |
| 9 整理交付 | 更新说明、过程页、当前学习包及校验 | README、预览页、ZIP、包内校验 | 包含最新成果，路径有效，已报告实际差异 |

## 阶段 1：把图变成约束

实际打开原图，不只依赖文件名或先前文字描述。标出主主体、地平线候选、消失方向、画面边缘裁切、最大亮区/暗区、关键接触点。取约 6–12 个有意义的主锚点，记录归一化坐标 `u=x/图宽、v=y/图高`，例如桌沿两端、主体头顶、地毯角、路缘转折。

这个表用于后续白模对照，并不直接给出三维坐标。绘画参考可能没有严格一致的消失点；遇到冲突，优先保留主体投影和观感，在记录中说明折中。

将复杂表面拆成层：结构轮廓、主要色块、材质粗糙度、裂纹磨损、零碎布景。区分阴影、水迹和真实高差，避免“暗色区域全部做成凹坑”。

## 阶段 2：建立同一套布局和高度规则

默认推荐 Z 向上、米制设计尺度，并在方案写明 X/Y 的意义；历史场景可能不同，不能直接混用坐标。

`scene_spec.json` 应包含单位、参考锚点、相机候选、场景边界、主要对象的中心/尺寸/旋转、支撑关系、地面分区、高程、已知未知项和完成度。平面图与高差表来自这份方案，后续改动同步更新。推荐新任务由配置生成布局和几何，减少多份手写数值漂移。

高度判定优先使用：明确接触关系与遮挡 → 台阶/墙脚等可见结构 → 共同平面和透视约束 → 物体常见比例 → 设计假设。阴影和反射只作辅助证据，因为光源和表面性质也未知。

对每件主要物件记录 `support_id` 和接触高程。例如地毯顶为 `z=0.025`，椅脚落在其上；桌上玩偶的支撑是桌面而非世界地面。曲面/倾斜支撑应计算局部表面位置，不能只用整体包围盒。基础平地、台阶、路缘、石板起伏和浅水分别建模。

历史案例的 `scene_spec.json` 保留初始设计；室内后续改动还体现在源码、最终工程与 `scene_as_built.json`，并非已实现配置单一驱动。新任务必须维护同步，若有偏差要在状态文件列出。

## 阶段 3：先解决相机，再决定细节

建立大地面、墙/街廓、主要家具或建筑块、主主体和简单灯光。相机先确定投影类型、图像宽高比与大致观察高度，再调朝向、位置、焦距及物体比例。相机位置、焦距和场景尺度存在耦合；一次集中调整一类参数，保存候选结果，避免同时乱调而失去判断。

同尺寸输出白模与参考。比较主锚点、主体占画面比例、透视收缩、物体前后关系和负空间。有条件可叠加边缘/半透明对比；必须保留原始渲染。锚点像素误差可用于构图迭代，但不能充当整图质量或真实空间精度。

用原图的光暗作为辅助，仍需一张中性光或粘土图看结构。室内先解决柜体、桌子、吊灯；街道先解决道路收束、两侧建筑高度、桥和远景遮挡。白模不合格先改这里。

阶段渲染是检查点，不代表逐对象建模录像。如果脚本起步已生成部分细节，说明这一点，不伪造制作过程。

## 阶段 4–5：资产、重复与材料

先做代表性近景样板，确认几何、纹理尺度和粗糙度，再推广到中远景。资产分为主视觉资产、重复模块和填充布景；根据画面贡献分配时间。复杂角色若轮廓影响主画面，应专项建模或使用有授权的合适资产；简单球体拼接只能作为占位。

模块拼接要有厚度、转角、屋顶和地基；微量随机形变不能替代设计变化。近处需要真实轮廓的结构建几何，中远处细碎表面可用纹理与法线。重复瓦片、石板、花瓣等按材质合并或实例化，控制内存与管理成本。

材料先分底色、粗糙度、法线/凹凸和必要的位移。生成底色图应避免烘入透视、照明和阴影，并记录提示词、图集分区和 UV 约定；生成的底色图集不等于扫描 PBR 全套。必要时生成纹理，但实际成片仍由 3D 工程渲染。

积水与湿地不是统一镜面：检查表面平整度、粗糙度变化、水层边界、视角反射和底面。避免一块悬浮银片。花冠检查位置与遮挡，细部花瓣须在特写验证，不能只靠远景粉色块判断。

保存阶段文件前处理未被对象使用的材质等数据：显式保留必要材质，或在下一阶段重新创建。不要依赖一个进程里暂存的未保存数据；室外案例曾因此在重开后找不到材质。

## 阶段 6：光照按层推进

先用天空/主灯建立大块明暗与投影，再加局部灯与反射补光，最后加雾、眩光和轻量后期。先验证无雾版本能读懂结构，再控制体积范围；前景应保留材质信息。

固定曝光与色彩管理后比较候选。渲染配置函数不得无意重置艺术参数；重开图与成片不一致时先检查曝光、World、灯光与合成器。保留代表性的失败版本与修改理由，不必保存每一次无意义重试。

视觉评审每轮写：观察证据、与参考的差异、影响最大的 1–3 个问题、本轮修改、修改后结果。先改主构图/主体/光色，再增加小道具。评审模板见 `templates/visual_review.md`。

## 阶段 7：统一三维产生多视角

不是先独立生成八张看似同一地点的图再强行建模。先有统一布局和三维白模，随后所有设计图与成片从同一工程拍摄。八是本项目采用的诊断数量，不是恢复真实空间的数学要求。

推荐覆盖主镜头、左右偏移或近景、反向、高位/俯视、主体特写、易穿帮接缝以及地面。按实际场景选择，不能为了凑数重复拍相同内容。记录相机位置、旋转、焦距/投影类型及每张图的诊断改动。

逐张打开结果，检查：主体是否漂浮、地面是否覆盖远端建筑、屋面与模块之间是否漏天、侧面是否薄片、湿地面有无穿插、树冠是否藏在屋顶后、反向是否暴露未建区域。发现问题后修几何，再重出受影响的主镜头、多视角和验证文件。

单镜头原型允许限定拍摄范围，必须把限制写进说明。若需求是漫游，则必须补齐约定行走范围、相机边界及可见背面；若需求是游戏，则继续目标引擎的碰撞、导航、材质和性能验证。不得用“有八个相机”替代这些检查。

## 阶段 8：成片、实时浏览与可迁移验证

保留 `scene_cycles.blend`（或明确命名的离线版）与 `scene_realtime.blend`。浏览版使用 EEVEE、Rendered 视口、关闭 overlays 和 gizmos，按需隐藏视口雾；选择主相机或易用的起始角度。设置必须保存到对应文件，并查看实际标题/路径确认，不凭快捷键已经按下就认为保存成功。

Cycles 转镜头后重新采样会先有噪点和低清预览。可增加预览采样/降噪，但如需编辑器式流畅浏览应评估 EEVEE。实时版本的光、透明、反射和体积要单独检查；未经测量不承诺流畅帧率，也不承诺与离线版逐像素一致。

交付前执行：

1. 保存最终工程，恢复主相机和诊断临时改动；确认没有误存到另一个版本。
2. `pack_all()` 或可靠相对路径管理外部纹理/字体；把从零重建所需的外部输入也放进项目并记来源。已打包工程可打开，不等于重建脚本在任意机器都无依赖。
3. 在新的 Blender 进程加载最终文件，枚举相机、引擎、缺失图像/字体等依赖，实际渲染小图并打开观察。验证进程不要覆盖艺术参数或成品文件。
4. 实时版也独立加载检查；修改几何后需从最新离线版同步重建实时版，避免两份文件内容分叉。
5. 记录 Blender 版本、设备、输出路径、检查范围和限制。若搬动工程，重新检查迁移后的依赖；原来的验证记录只证明原来的检查。

本项目迁移验证脚本位于 `tools/verify_blender_relocation.py`，只读取工程和输出诊断报告/小图，不保存 `.blend`。

## 阶段 9：项目交付结构与完成标准

每个新场景推荐保留：原图、需求/分析、布局图、空间配置、源码、资产/提示词、阶段工程、最终两版本、阶段渲染、多视角、相机清单、技术验证、视觉评审、状态记录、README 和本地过程页。使用项目内相对引用，避免页面依赖旧绝对路径。

完成标准分开判断：

- **技术完成**：工程可重开渲染，依赖有效，版本与包一致。
- **视觉完成**：根据约定主镜头与浏览范围逐项评审，主要差异已处理或明确接受。
- **范围完成**：单镜头/浏览/游戏对应的额外验证确已完成。

缺少任何一项，不得把原型表述为精细复刻或可上线游戏场景。没有对本模型/任务的实测，不报告相似度区间；如要评估，应先约定样本、指标、对齐方法和人工评审，区分构图误差、语义相近与材质风格。

更新学习包时从当前规范目录生成，排除自动备份和临时缓存，校验 ZIP 内工程/资产与目录文件的哈希一致。历史包原样存档，不能让用户误拿过期包。未来 agent 的交接必须有 `work_state.md`，明确最后可恢复检查点、未解决问题及下一条可执行操作。
