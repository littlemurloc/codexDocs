# Blender Agent 场景制作与视觉验收指南

> 用途：供能够操作 Blender 的 agent 阅读、吸收和执行，重点覆盖参考图或文字需求驱动的氛围场景与游戏环境制作。
>
> 整理日期：2026-11-05。本文是公开资料的归纳与执行建议，不是任何模型的内部训练规范，也不是某个插件的官方统一标准。本文未在本地复现所引用案例。

## 1. 执行目标与适用边界

将用户参考图或文字需求转化为可编辑、可检查、可再次渲染的 Blender 场景，并交付与需求相符的实际渲染结果。

适用于室内、建筑外部、科幻机库、走廊、夜市、小型关卡、风格化环境等任务。复杂角色、精密工业模型和大规模开放世界还需要相应的专项方法与资产。

开始前明确交付类型：

| 类型 | 核心验收内容 |
|---|---|
| 单镜头场景 | 指定镜头的构图、材质、灯光、可重复渲染 |
| 多镜头或漫游场景 | 上述要求，以及约定范围内的背面、次要区域和相机路径 |
| 游戏引擎场景 | 上述约定要求，以及目标引擎中的导入、材质、碰撞、尺度和性能验证 |

单张参考图不能唯一确定背面、真实尺度和完整空间。将这些内容列为假设，根据用户目标合理补全；不要把推断称为精确重建。用户只要求单镜头时，不必扩建无关区域；会影响阴影、反射和间接光的镜头外结构仍需考虑。

### 指令与权限

- 用户当前要求、既有授权、运行环境规则优先于本文建议。
- 本文不授予付费服务、上传参考图、修改其他项目或破坏性操作的权限。
- 常规可逆操作在已授权范围内连续执行。阶段验收默认由 agent 自检，不要求用户逐步批准。
- 只有缺失信息会实质改变成果、发生方向冲突或确有权限障碍时，才提出具体问题。
- 不为套用本文而重置已有工程、覆盖用户成果或强制安装新工具。

## 2. 先检查 agent 是否具备完成任务的能力

MCP 提供调用通道；理解、计划、观察、判断和纠偏仍由 agent 完成。不要假定安装 MCP 后便自动具备完整制作流程。

开始时确认：

1. 能读取需求与参考图；若模型无法理解图像，需要可用的视觉分析组件或人工评审，否则不能声称做过视觉对照。
2. 能读取 Blender 场景状态并执行建模或修改。
3. 能取得并实际查看视口、相机和最终渲染图。
4. 能保存工程、访问输出路径并检查依赖。
5. 能获知长任务是否完成，以及失败后如何恢复。

记录 Blender 版本、渲染引擎、有效计算设备和已启用的工具。以当前工具 schema 为准：不同 MCP 实现、分支和版本的工具名不一致。

以 ahujasid 项目为例，检索时的接口包含 `get_scene_info`、`execute_blender_code`、`look` 以及资产相关工具；旧教程可能使用不同名称。`look` 查看已存在的渲染图，不等于执行一次最终渲染。[S1]

若 agent 还具备终端能力，可考虑将长渲染移到独立 Blender 进程；只有 MCP 时应采用该实现支持的方式，不要假定可以启动或管理后台进程。

## 3. 工作原则

1. **先固定目标，再组织制作。** 参考图、用途和验收要求共同决定工作量。
2. **先解决构图与主要形状。** 小物件、纹理噪声和高采样不能弥补空间关系错误。
3. **使用真实图像与结构数据共同验收。** 命令成功、对象存在和文件保存不能证明画面达标。
4. **保持修改可定位。** 使用稳定名称、可调整参数和小范围修改，避免每次整场重建。
5. **一次验证一个主要假设。** 不同时大幅改变相机、灯光、曝光和材质。
6. **保存已接受状态。** 对比前后结果，保留改进，撤回退步。
7. **按用途分配细节。** 优先主体、近景和用户会探索的区域，同时完成约定的次要区域。
8. **明确报告未完成项。** 不通过降低目标、隐藏缺陷或使用概念图代替实际渲染来宣布完成。

上述原则是本文的综合建议。个别来源采用的强制等待、固定时长、提交频率或专用工具约定，不作为通用要求照搬。

## 4. 输入规格：把需求变成可操作的约束

先建立简短的场景说明，复杂任务再展开。不要为小场景编制庞大的文书系统。

```yaml
scene_brief:
  purpose: "单镜头展示 / 多镜头场景 / 游戏环境"
  deliverables: []
  reference_roles:
    composition: "哪张图决定构图"
    shape: "哪张图决定形状"
    lighting: "哪张图决定光影"
    style: "哪张图决定风格"
  required_objects: []
  required_zones: []
  camera_requirements: []
  scale_constraints: []
  mood: "焦点、明暗关系、色彩倾向"
  allowed_asset_sources: []
  target_engine: null
  output_resolution: null
  time_or_cost_budget: null
  assumptions: []
  unresolved_questions: []
```

### 有参考图时

分析画幅、地平线、透视类型、主体轮廓、遮挡、前中后景、大面积色块、主光方向和阴影软硬。优先选择若干容易复核的关键点：主体顶端、底端、左右边界、门窗角点、地面与墙面交线。

可以把关键点坐标归一化到图像的 0–1 范围，比较主体的画面占比与位置。只有实际测量后才能报告误差；粗略目测要标为估计。测量容差根据用途与参考可靠性设定，不套用统一的“相似度百分比”。

多张图可能互相冲突，应明确各自的约束角色。对风格参考不必逐像素复刻；对严格复刻则不要擅自重新设计主体。

### 只有文字时

把“有氛围”“写实”“高级”等词展开为具体选择，例如主光方向、焦点、冷暖分布、暗部可读性、使用痕迹和空间用途。若制作概念图，应明确它是设计目标，不是 Blender 场景产出的证据。

## 5. 推荐制作工序

### 阶段 A：检查与初始化

读取现有工程，确认路径、单位、对象和相机。对已有文件保留副本或检查点；只清理本任务拥有且确认可删除的对象。

按实际规模组织集合，例如建筑、主体、道具、灯光和相机。建立简短工作记录，记录当前工程和有效参数。先执行一个小的读取或修改操作，验证工具链可以正常返回结果。

**退出条件：**能保存、读取和观察当前工程，下一步操作范围明确。

### 阶段 B：白模与相机匹配

使用简单几何建立主要空间、主体和关键遮挡物，同时建立主相机。白模阶段也可设置简易光源，便于判断空间。

优先调整画幅、投影方式、相机姿态、视场和物体位置。先比较轮廓与比例，再进入细节。对单图恢复，不要无限尝试同时求解相机与所有尺寸；固定合理的尺度假设，逐组调整参数。

多视角场景至少增加用于检查反面和次要区域的视角。保持检查视角稳定，便于后续对比。

**退出条件：**主要物体、空间关系、构图和相机已达到当前任务的可接受程度；仍有偏差时记录具体位置和处理计划。

### 阶段 C：选择资产制作方式

| 对象特性 | 优先考虑的方式 | 必须检查 |
|---|---|---|
| 规则建筑、柜体、门窗 | 参数化几何 | 尺度、厚度、开口、连接 |
| 重复结构或植被 | 实例、阵列、节点系统 | 变化是否自然、资源占用 |
| 常见复杂道具 | 已授权素材库 | 风格、尺寸、依赖与许可 |
| 特殊有机主体 | 合适的生成服务或专门建模 | 多视角形状、贴图、拓扑 |
| 近景核心物体 | 单独精修 | 轮廓、功能结构与接触关系 |

不要将“全部从零建模”设为默认限制。也不要把图生 3D 当作完整场景重建器；生成资产仍需要尺度、摆放、材质和结构检查。

资产代表件先达到可接受质量，再批量复制。大量重复对象应优先评估共享几何和实例方案。

**退出条件：**每类资产有明确路径，关键物体的代表件可以在目标距离下辨认且符合风格。

### 阶段 D：主体建模与布景

完成建筑与支撑结构，再布置家具和道具。布景应围绕场景用途和叙事关系组织，例如维修台周围的工具、护士站附近的推车，而非均匀随机撒物体。

检查物体实际底部和支撑面，不用原点位置代替接触判断。对复杂表面结合局部视图、实际几何和阴影判断；包围盒相交只能作为排查线索。

技术检查应与对象用途匹配：错误法线、退化面、意外重复和明显穿插需要处理；开放曲面或薄片并不必然是错误，不能一律要求封闭流形。

**退出条件：**主要和约定次要区域已完成结构；主体比例可信，物体有合理支撑，行走或相机路径可用。

### 阶段 E：材质与表面

先处理占画面面积最大的材质和主体材质。对比颜色、粗糙度、反射、纹理尺度及材质间的区别。

按数据用途设置纹理色彩空间；检查 UV 拉伸、重复纹理、过强凹凸以及贴图中已有阴影对最终照明的影响。接近镜头的软体需要可信的形状与支撑，不能只用纹理假装褶皱。

**退出条件：**材质在主视角和近景中都可读，尺度统一，没有靠噪声掩盖的结构问题。

### 阶段 F：氛围灯光

先建立焦点和大面积明暗，再细调局部光。阴暗氛围仍应保留用户需要看清的主体和路径。

建议执行顺序：

1. 明确主光来源、方向和受光区域。
2. 检查门窗、墙体和顶棚是否形成预期的进光与遮挡。
3. 在无雾状态下完成基本曝光和明暗关系。
4. 分别调整环境光、实际灯具、补光和轮廓光。
5. 最后加入需要的体积效果，并检查其是否吞没对比度。

固定相机和主要色彩管理设置比较候选方案；一次只修改一组相关参数。风格化场景可采用符合用户意图的表现手法，但要清楚其是否能迁移到目标引擎。

**退出条件：**主体清晰，焦点明确，冷暖与明暗符合需求；不存在因局部问题而把所有灯都调亮的情况。

### 阶段 G：低成本渲染与纠偏

先用较低分辨率和适当采样验证画面，再提升输出质量。具体数值随硬件、噪声和细节要求变化，不把某个采样数当作质量保证。

每轮保存：当前版本、修改假设、实际变更、相机与设置、渲染路径、观察结果，以及保留或撤回的决定。

优先修复构图、主要形状和光影，再处理材质与小细节。每轮选最重要的少数问题，不无限堆叠修改。

**退出条件：**关键缺陷解决，剩余问题不阻碍交付；或已达到用户限制，需要明确交付部分成果。不得擅自降低目标来制造通过结果。

### 阶段 H：正式输出与重开验证

保存最终工程后执行渲染，确认任务完成，再打开真实输出检查。多镜头或动画须检查不同位置的遮挡、曝光和主体可读性；仅一张成功帧不能验证整条镜头路径。

重新打开保存的工程，检查依赖、活动相机和关键设置，并进行适当的重复渲染验证。打包可打包的资源；缓存、视频或其他外部依赖按实际情况附带。

**退出条件：**交付文件完整可读、结果与保存工程一致，已验证内容和未验证内容都有记录。

## 6. 视觉纠偏：从症状到操作

以下是排查建议，原因需通过观察或小规模试验确认。

| 症状 | 优先检查 | 有针对性的下一步 |
|---|---|---|
| 物体都有，但整体不像参考图 | 相机、主体占比、负空间、透视 | 返回白模视图，比较关键点与轮廓 |
| 主体显得太小或没有焦点 | 取景、距离、遮挡、周边亮度 | 调整构图或层级，暂缓增加细节 |
| 画面发平 | 主光方向、正面补光、材质响应 | 固定曝光，测试减少正面光或改变主光 |
| 氛围变成一片黑 | 焦点和关键表面的可读性 | 局部补光或调整布局，保留整体明暗层次 |
| 雾很重但没有清晰光束 | 光路、体积范围、密度、背景对比 | 减少变量，先检查无雾光照再逐步加入 |
| 道具悬空或穿入桌面 | 几何底部、旋转、支撑面 | 用低侧视角检查，按实际接触面修正 |
| 一眼像方块拼装 | 主要轮廓、厚度、连接和功能结构 | 改造代表件，再更新实例 |
| 布景杂乱或重复 | 使用关系、密度、留白 | 删除无意义装饰，重组有用途的物件群 |
| 材质像塑料或纹理过大 | 粗糙度、纹理尺度、灯光 | 在固定光线下检查代表材质 |
| 主镜头好看，反面空缺 | 建模范围与交付范围不一致 | 补齐约定区域，再复核其他镜头 |
| 导出后效果完全不同 | 非便携材质、体积、合成、灯光 | 在目标环境重建或烘焙所需效果 |
| 加细节后画面退步 | 主体轮廓、层级被破坏 | 与上一检查点对比，撤回有害改动 |
| 长渲染后没有结果 | 作业状态、输出路径、错误日志 | 先确认运行状态，再决定恢复或重试 |

不要用更多对象、更高面数或更长工作时间作为质量提高的证据。

## 7. 可靠执行与故障恢复

### 脚本组织

按有意义的阶段或对象族分文件，例如空间、主体、道具、材质和灯光。共享参数应集中管理，记录依赖顺序。

明确脚本属于哪一种：

- 可重复更新：按稳定名称查找并更新本任务对象。
- 一次性搭建：重复运行会产生重复几何，重试前需要恢复检查点或清理本阶段对象。
- 完整重建：只能对明确指定的新文件或工作副本执行。

大量循环操作出现性能问题时，评估直接网格构造和实例化；不要假设所有 Blender operator 都适合批量使用。将多个对象合并可能改善管理或性能，也可能损失独立编辑能力，应根据交付用途选择。

### 超时与部分失败

工具超时不等于 Blender 操作失败。修改、渲染或导入可能仍在进行，也可能已经完成一部分。

发生异常后：

1. 读取当前对象、文件、作业或日志状态。
2. 确定是否已产生结果或部分结果。
3. 判断应该继续等待、局部修复还是恢复检查点。
4. 仅在确认不会重复创建或启动冲突作业后重试。

长渲染可以读取已保存工程的独立快照。渲染期间避免修改该次任务的输入文件和依赖，以免输出与制作记录脱节。

### 中断后的继续

首先读取工作记录，检查当前文件版本和待处理作业，打开最近的有效图像，然后继续最高优先级问题。不要仅根据上一条文字总结猜测现场状态，也不要默认从零开始。

## 8. 视觉验收与工程验收分开记录

视觉状态使用 `pass / fail / unclear`；`unclear` 表示证据不足，需要补充视角、局部渲染或信息，不能自动当作通过。

| 检查类别 | 核心问题 | 主要证据 |
|---|---|---|
| 需求覆盖 | 必需对象、区域和交付项是否存在 | 需求表与实际工程 |
| 构图与比例 | 主体关系是否接近目标 | 同画幅、可比角度的图像 |
| 氛围与材质 | 光影、色彩、表面是否符合意图 | 场景自身灯光下的实际渲染 |
| 几何与摆放 | 形状、接触、遮挡是否可信 | 多视角、局部图和结构数据 |
| 工程完整 | 文件、依赖和相机是否可用 | 重开工程与重复渲染 |
| 引擎适配 | 目标引擎里是否正确 | 实际导入与运行证据 |

必要时让未参与制作的评审者查看目标与结果，先给出独立判断再阅读制作方自评。若没有这样的评审条件，明确记录为 agent 自检，不假称独立评测。

不直接输出“相似度 90%”等没有定义的数字。若使用评分，应附评分规则、权重、样本与评审方式，并区分视觉相似、需求满足和工程正确性。

## 9. 游戏场景的额外交付要求

Blender 的最终渲染与游戏引擎中的实时画面不是同一个验收对象。

若用户要求可用于游戏，先明确目标引擎、平台、观看距离和性能预算，再处理：

- 单位、轴向、原点、对象层级与模块边界。
- 面数、材质数、贴图尺寸、实例化和按需 LOD。
- 可迁移的材质表达；程序化材质按需烘焙。
- 目标引擎中的灯光、雾效、曝光和后处理。
- 按需碰撞、导航、交互和相机路径。
- 导出后重新导入，检查实际物体、UV、材质和布局。

镜头演示中跟随相机旋转的灯光，不应未经判断就作为可漫游关卡的最终照明方案。对镜头有效的美术技巧需要根据游戏用途重新评估。

只有在目标引擎、目标硬件和明确场景条件下测得的数据，才能支持性能结论。Blender 截图速度、离线渲染时间或视口回调频率不能代替游戏 FPS。

## 11. 如何评估这份规范对另一个模型是否有效

采用一组与目标业务相似的任务，而非只挑最好看的案例。建议覆盖规则室内、氛围走廊和室外或风格化环境。

比较“基础工具条件”和“工具＋本文指导条件”，固定模型版本、推理设置、工具版本、素材权限、硬件及时间或费用预算。若同时改动工具与规范，明确实验测量的是整体组合收益，不能只归因于文本。

每个任务尽量重复运行；保留全部结果和失败，报告每次结果与波动。评审时使用相同相机条件，并把视觉、工程、费用与耗时分别记录。少量样本只能给方向性判断。

若执行模型不支持图像输入，必须单独设计视觉反馈环节；由其他模型描述误差的系统，与原模型独立完成任务不是同一个实验条件。

可以参考 BlenderWorld 的任务与验收设计，但不要把综合基准分数解释为单张参考图的还原率。[S9]

## 13. 可直接附加到任务中的执行摘要

> 按用户目标确认交付范围，记录参考图角色与必要假设。读取当前 Blender 状态和工具能力，在已有授权内连续工作。先匹配白模、相机与主要比例，再完成代表资产、布景、材质和灯光。每轮小范围修改后，实际打开渲染图，与固定目标及上一版本比较，记录最重要缺陷和下一项修正。保持脚本与工程一致，保存检查点，避免超时后重复启动或重复创建。分别验收视觉质量、工程完整性和目标引擎适配；最终检查交付文件及可重复渲染性。只报告实际验证过的结果，明确未完成项，不编造相似度、性能或成功率。
